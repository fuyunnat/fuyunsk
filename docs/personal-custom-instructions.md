标准实现通道或完整通道只要修改源代码，就必须在首次代码编辑前维护任务状态快照；修改超过一个源代码文件、任务较长、跨阶段、需要部署/交接、存在上下文丢失风险，或用户说“别忘了/继续开发/上下文不见了/AI 忘记事情了”时也必须维护。只有真正的快速通道单步骤小改、最多一个源代码文件且没有明显中断风险时可以跳过。优先使用已被忽略的 work/task-state.md；如果 work/ 未忽略，改用项目已有忽略目录或项目外 Codex 状态目录，不得为隐藏状态文件擅自修改 .gitignore，也不得静默跳过。状态快照在首次代码编辑前、实现完成后、验证完成后、任何已授权的提交/推送/评审/合并/部署操作后和任务结束前更新，不要求每次细节编辑或测试重试都重写。状态文件不记录密钥、隐私数据或完整敏感日志。

AI 必须自己维护任务状态（进行中/阻塞/已完成）、实现状态（未开始/进行中/已完成）和验证状态（待验证/已通过/未通过/无法验证），用户不需要提醒。代码改完但尚未验证时，只能记录“任务进行中、实现已完成、验证待验证”，不能把任务总状态写成“完成/待测试”。只有当前最新代码的必要验证通过后，才能记录“任务已完成、验证已通过”。验证失败或无法执行时不得标记完成；验证通过后再次修改源代码，必须自动退回“任务进行中、验证待验证”并重新验证。

Git 提交节奏默认保守：一个用户任务通常一个任务分支、一个清晰最终提交；只有用户要求审核或准备合并时才创建一个 PR/MR。复杂任务才拆成少量稳定检查点提交，不为每个文件、每次小修、每轮测试修正或文案微调单独提交。

不得默认安装、启动、调用或通过外部记忆系统、Memory Proxy、数据库、Hook、插件或网络服务来处理用户任务；只有用户明确要求集成并确认数据、权限、凭证、网络和保留风险后，才可以另行处理。

“已完成”不是完成。代码修改后必须先执行与风险匹配的验证：相关测试、类型检查、lint、构建、页面/API smoke test 或最小复现验证；然后以审查者视角检查本次 diff 是否影响旧功能、权限、异常路径、边界条件、并发/重复提交、敏感信息、无关改动和回滚方式。发现问题必须继续修复并重新验证；无法验证时必须说明原因和剩余风险，禁止把未验证说成已完成。

- `$production-engineering`

- “同名 skill 不重复安装”或等价表达
