# 运行等待优化与验收

## 优化对象

目标是减少模型与工具间的串行往返，不是降低原文标准或节省 Token。原稿、锁、切片及必要测试不删；不改客户端模型、推理强度、API、MCP、权限或自动调用。新前端选型是用户另外明确授权的规则修改，见 `frontend-stack.md`，不是速度优化的副作用。

## 使用路径

读取一次技能入口后，根据已知阶段和领域，优先一次拿到条款并集和专项说明：

```bash
node "<技能目录>/scripts/read-rules.js" --stage 小改 --topic 内容
node "<技能目录>/scripts/read-rules.js" --stage 实现 --topic 前端,接口
node "<技能目录>/scripts/read-rules.js" --stage 只读 --topic 审计
node "<技能目录>/scripts/read-rules.js" --stage 提交
```

阶段只决定读取清单，不执行命令、不判断自然语言、不扩大授权。`小改` 必须先符合原文快速条件；只读不能变成写入。验证、提交等后续阶段假设同一任务已读过通用规则，新任务从中途开始时追加 `--topic 通用,适用方式`。多领域应取并集，额外专项用 `--reference`；未知领域再补查路由，不强制串行读入口、路由、索引、通道。

旧 `--topic` 和 `--id` 仍读取精确原文。JSON 仍是数组，旧字段和 `text` 不改；第九章额外附带 `amendments` 当前选型。阶段模式 JSON 是包含 `rules`、`references` 的对象，不能将两种格式混用。文本模式先说明新选型，再给出可追溯原文。

只复用仍在上下文且版本未变的条款。上下文压缩、输出截断、升级或内容丢失时补读缺失部分；不能把“已经发过工具调用”当作读完。批量内容过大时分段读完，不截掉适用规范。

独立只读检查可合并，确认没有共享写入或资源冲突时可并行；各项保留命令、退出码和结果。备份、修改、验证、提交有先后依赖，不能并行越过。状态只在原文要求的阶段边界更新。业务任务只跑业务项目的验证，不运行技能生成器或技能自检。

## 本地可重复对照

只在维护或排查时运行：

```bash
node scripts/benchmark-rule-loading.js --runs 9
```

比较“一次原文读取 + 每个专项单独读取”与“一次合并读取”，先断言内容相同，再交替顺序重复计时。旧命令本来支持多主题，因此不虚构旧版必须逐条原文串行读取。无专项的提交阶段不预设收益；能自行合并工具调用的客户端未必获得同样改善。前端新旧对照均包含当前选型修改，避免内容不同影响比较。

这个基准只覆盖 Node 进程与本地文件读取，不包含模型、网络、客户端初始化、项目执行或测试。不得把本地几十毫秒的差异宣传成 Codex 秒级改善。

## 本次本地实测（2026-09-05）

环境：Linux x64、Node.js v22.16.0；每组前后交替 9 次，均先确认输出内容一致。

| 场景 | 分开/合并进程数 | 分开中位数 | 合并中位数 |
| --- | --- | --- | --- |
| 局部文档修改 | 2 / 1 | 59.96 ms | 31.56 ms |
| 前端实现 | 4 / 1 | 109.57 ms | 34.15 ms |
| 只读安全审计 | 2 / 1 | 55.87 ms | 30.61 ms |
| 提交阶段 | 1 / 1 | 30.7 ms | 29.57 ms |

这是相同规则内容的本地读取对照，不是旧版/新版 Codex 的端到端对照。提交阶段本来只有一次读取，微小波动不能解释为稳定提速。当前尚无用户 Mac 的模型调用轨迹或真实页面任务性能验收。

## 真正的端到端验收

使用相同客户端、模型、推理设置、网络和无敏感数据的测试项目；前后交替运行普通问候、局部文案修改、前端实现、只读审计。记录用户提交时间、首个模型请求、首个实际内容、首次项目处理、每次工具调用、验证结束和最终完成时间。报告中位数与范围，同时记录缓存、错误、重试和输出量。

检查是否确实减少规则读取轮次、重复检查和无关初始化；同时检查中文交付、只读边界、旧行为、视觉验收和当前 shadcn/ui + Tailwind CSS 选型。仅凭文件变少、Token 变化或助手自称更快不能通过验收。没有实际本机轨迹时，明确端到端速度和模型遵循情况未验证。
