# 性能底线：写代码就要守住

2026-10-16 用户反馈：技能写的东西不考虑性能。本规则在写代码时与原文第十一章一起看。先判断这次改动会碰到多大量的数据、会不会被反复调用；碰不到，下面的具体做法就跳过，不要给小数据硬加分页、缓存或后台任务。目标是数据变多时仍然能用，不是提前做微优化。

## 一、先想清楚数据量

动手前对本次涉及的数据给出量级判断：现在多少、一年后大概多少（几十、几千、几十万、上千万）。判断不了就按“会变多”处理。数据量决定写法：几十条可以简单处理，几千条以上就要分页、索引、批处理。

## 二、后端与数据库

- **列表必须分页**，接口有默认每页数量和上限，不提供“一次取全部”。
- **不在循环里查数据库或调接口**（N+1）：用批量查询、`IN`、联表或预加载一次取齐。
- **新查询检查索引**：`where`、`order by`、`join` 用到的字段，数据会变多时要有索引；新增索引说明原因。
- **只取需要的字段和行**，不 `select *` 拉大字段，不把整张表读进内存再过滤。
- **大批量处理分批**：导入导出、批量更新用分批、流式或后台任务，不一次性占满内存或长时间锁表。
- **外部调用必须设超时**，重试有次数和退避；可以并行的独立调用不要串行等待。
- **重复的昂贵计算或查询考虑缓存**，并写清失效时机；统计类查询考虑预聚合或异步计算。
- **慢操作不放在请求里同步做**：发邮件、生成报表、处理大文件等放后台任务，接口先返回。

## 三、前端

- **大列表分页、懒加载或虚拟滚动**，不一次渲染成百上千行。
- **搜索、筛选、输入联想加防抖**，旧请求可取消，避免乱序覆盖。
- **不在渲染时做大量同步计算**；昂贵计算缓存结果（如 `useMemo`），避免无意义的重复渲染。
- **请求不串成瀑布**：互不依赖的请求并行发；首屏只加载核心数据，次要内容延后。
- **图片压缩、限制尺寸、懒加载**；大的第三方库按需引入或懒加载，不为一个小功能引入整包。
- **不无节制轮询**，轮询有间隔、页面不可见时暂停，能用推送就不轮询。
- 失败重试有上限，加载慢时给出进度反馈并防止重复提交。

## 四、改完怎么确认

- 自检一遍：本次代码里有没有循环查库、无分页列表、缺索引的新查询、没有超时的外部调用、一次渲染大量数据。
- 涉及大数据量、核心接口或用户反馈“慢”的地方，**实际测一下**：用接近真实规模的数据跑一次，记录耗时或查询次数（项目已有压测、性能测试或 `EXPLAIN` 就用上）。
- 测不了就如实说明“没有用大数据量验证”，并指出可能变慢的位置。
- 不做没有依据的微优化，不为了性能牺牲正确性和可读性；真正的性能问题按 `diagnosis-feedback-loop.md` 先测量再优化。

## 五、优化不要把原来的结果改掉

性能上的调整默认不改变原来的结果。改坏了怎么停、怎么恢复，见 `delivery-feedback.md`，这里不另写一套。

改被多处共用的路径时：先列出会走到这段逻辑的入口，改完抽查一条成功路径，以及一条这个项目真实存在的失败或空结果路径。说不清副作用怎么走，或没验到的范围，就不要当成已经完成。
