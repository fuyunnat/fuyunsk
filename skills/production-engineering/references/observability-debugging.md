# 日志要能找问题，报错先分清是哪一层

2026-10-13 用户反馈：程序日志不完整、找问题找不到位；套了 CDN 后，CDN 返回的错误源站完全不知道；项目缺日志时要主动补上。本规则在写代码、修 Bug、排查线上报错时都适用，与第十八章一起执行，不替代其中的审计与脱敏要求。

## 一、日志的目标：出了问题能直接定位

只写“失败了”“出错了”等于没写。新增或修改的功能，至少在下列位置留下能排查的记录：

- **入口**：哪个接口 / 页面动作 / 任务被触发，关键参数摘要（敏感值打码）。
- **关键分支**：走了哪条路（例如“余额不足，拒绝下单”“命中缓存”），以及做判断依据的值。
- **外部调用**：调用了什么服务或接口、耗时、状态码、重试次数、失败原因。
- **数据库写入与事务**：业务场景、影响对象 ID、失败阶段、是否已回滚。
- **错误**：错误类型或稳定错误码、脱敏后的原因和必要堆栈、出错上下文（请求编号、对象 ID 摘要、必要输入摘要）。原始错误须先脱敏，外部响应、命令参数和用户输入尤其不能原样写入。

每条日志带时间、级别、模块名，有请求时带请求编号（`request_id` / `trace_id`），同一个请求的日志能串起来。级别按第十八章：正常关键流程 info，可恢复异常 warn，功能失败 error，排查细节 debug。

接口、机器人、任务队列、文件处理等关键链路，沿用或生成同一操作编号，贯穿入口、关键阶段和最终结果。失败记录至少能回答失败阶段、哪个组件、原因类别和耗时；需要时再加状态码、尝试次数、是否会重试。保留可排查的原因摘要，区分等待、超时、主动取消和失败。终态记一次；长任务在阶段变化或明显超时时提示，避免循环刷屏。

**子进程与外部工具**：stdout 若是机器协议或结果流，保持原通道；stderr 另行接收并持续读取。故障记录包括启动/运行/退出等阶段、实际退出码或信号、是否超时或取消，以及经限量和脱敏的诊断摘要。原始内容无法安全过滤时只留可验证的错误类型、状态码和运行结果；不能靠整段输出、丢弃 stderr 或只写“连接中断”代替诊断。保留真正的失败退出，区分预期清理产生的退出。

## 二、项目缺日志就补上

先看项目现有的日志方式：有统一 logger、日志平台、request_id 中间件就沿用，不另起一套。

如果项目**没有日志或不够用来排查**，在本次改动涉及的范围内主动补齐，不需要用户另外要求：

- 没有 logger：用该语言最常见、最轻的方式建一个统一入口（例如 Node 用项目已有的 pino/winston 或标准 `console` 封装，Python 用标准 `logging`，Go 用 `log/slog`），不引入大型监控平台或付费服务。
- 没有请求编号：在请求入口生成或沿用上游传来的编号，写进日志并放进响应头，方便用户报错时提供。
- **日志默认写到项目根目录下的 `log/` 文件夹**（2026-10-17 用户要求；项目已有 `logs/` 或统一日志目录则沿用）。目录不存在就创建；把 `log/`（或实际目录）加入 `.gitignore`，不要把日志文件提交进仓库。
- **每次进程启动新建一份带时间戳的日志文件**，不要追加到上一次启动的文件里。文件名含启动时间，例如 `log/app-20261017-143052.log`（精确到秒即可；多进程可再加 pid）。同一进程内的日志都写进这一份；重启后再开新文件。开发时仍可同时打到终端，但文件是默认落点。
- 启动时报告本次运行日志的绝对路径、工作目录、环境及运行编号或进程号；分多个文件时说明各自用途。区分启动中和就绪，实际监听或连接成功后才报就绪。文件未打开或写入失败时，从仍可用的安全输出说明原因及当前落点；不能把预计路径当已写入的文件。部署平台需要标准输出时可同时输出，一处输出失败不应阻断仍可用的另一处。
- 旧日志文件保留，不主动整目录清空；目录明显过大时再按项目约定清理或轮转，并向不清库一样先说明。
- 补日志只覆盖本次涉及且确实缺证据的关键路径。纯文案、样式等小改沿用原日志，不要求新增日志设施。

完成后用人话告诉用户：本次启动的日志文件完整路径、怎么看、出问题时把哪几行发给 AI。

**日志交付怎么测**：日志本身有改动，或本次涉及关键故障链时，在安全隔离环境按实际入口执行一次相关成功路径和一次可控失败，打开本次实际写入的日志文件，核对同一编号、失败阶段、原因和终态。涉及启动落盘就重启一次，确认路径不同且旧文件保留；涉及脱敏就用假密钥或假隐私值验证它们不出现于文件与终端输出。只测适用项，缺环境时说明哪段没测；编译通过或调用了 logger 不算验证落盘。

## 三、前端也要记

- 全局捕获未处理的报错和 Promise 拒绝（框架的错误边界 / `window.onerror` / `unhandledrejection`），记下页面、操作和错误信息。
- 接口请求失败时记录：请求地址、方法、状态码、返回内容摘要、请求编号（响应头里有就带上），以及返回的是不是 CDN 的错误页（见第五节）。
- 生产环境不在控制台刷大量调试信息；项目已有错误上报就接入，没有就至少保证开发环境能看清。

## 四、修 Bug 时先看日志够不够

1. 先读现有日志、报错和堆栈。能直接定位就去修。
2. 日志不够判断原因时，**先在出问题的路径上补日志**，复现一次，读日志找到原因，再改代码。不要在没有证据时连续猜改。
3. 修好后，对以后排查仍有用的日志保留下来，调整到合适级别；只有纯临时的打印（如带 `[DIAG-xxxx]` 标记的）才删除。

**环境要对上问题现场**：用户指向的是线上、生产、远端服务器，或已经给出那边的日志/路径时，先用这些现场证据排查；本机开发日志只作对照，不能单独当结论。用户明确说本机日志对不上时，改去要对应环境的路径、进程信息或同一时段的现场日志，不在错误环境里空转。用户给了说明材料时，按 `delivery-feedback.md` 先对照，不在这里重复。

## 五、线上报错：先分清是哪一层

常见链路：`用户浏览器 → CDN / WAF（如 Cloudflare）→ 反向代理（如 Nginx）→ 应用 → 数据库 / 外部服务`。错误可能是任何一层自己返回的，源站日志里可能根本没有这次请求。

**先判断层级，再看代码**（只读检查，不改配置）。项目没有网关、CDN 或代理，就跳过本节；下面的名称和状态码是常见例子，不是每个项目都会出现。

- 看响应头：`Server`、`CF-Ray`、`cf-cache-status`、`X-Cache`、`Via`、`Age`、自定义请求编号。带 CDN 标记且源站日志查不到同一请求，基本是 CDN 或回源之间的问题。
- 看错误页样式：CDN / 代理的默认错误页和应用自己的错误响应不一样。
- 绕过 CDN 直接访问源站对比（例如 `curl` 指定源站 IP 并带上原域名的 `Host` 头），源站正常而走 CDN 异常，就锁定在 CDN 层。
- 用 CDN 请求编号（如 `CF-Ray`）和时间去对照源站与代理日志。

**常见原因清单**（Cloudflare 为例，其他 CDN 同理）：

| 现象 | 常见原因 |
| --- | --- |
| 502 / 520 / 521 | 源站拒绝连接、进程挂了、源站防火墙屏蔽了 CDN 的 IP、返回了不合法的响应头 |
| 522 / 504 / 524 | 源站处理太慢，超过 CDN 等待时间（Cloudflare 默认约 100 秒）；连接建立超时 |
| 525 / 526 | CDN 的 SSL 模式与源站证书不匹配（证书过期、自签、域名不符） |
| 403 / 1020 | CDN 防火墙 / WAF 规则、机器人防护、地区限制拦截 |
| 429 | CDN 限流 |
| 413 | 上传体积超出 CDN 或代理限制 |
| 内容是旧的 / 错误页被反复返回 | CDN 缓存了旧文件或错误响应，需要按路径清缓存或调整缓存规则 |
| WebSocket / 长连接断开 | CDN 未开启 WebSocket、空闲超时 |

**源站日志要能和 CDN 对上**：

- 每个请求记录请求编号、方法、路径、状态码、耗时；把 CDN 带来的请求编号（如 `CF-Ray`）一并记录。
- 用户真实 IP 只在确认请求来自 CDN / 可信代理时，才从 `CF-Connecting-IP`、`X-Forwarded-For` 等头取，并配置可信代理范围；否则这些头可被伪造。
- 反向代理（Nginx 等）的访问日志与错误日志也要开启并能找到，记录上游耗时与上游状态码。

**修改 CDN、WAF、DNS、SSL 或代理配置属于线上变更，需要用户明确同意**；可以给出具体改法，但不擅自操作。最后用人话告诉用户：问题出在 CDN、代理、源站还是外部服务，依据是什么。

## 六、脱敏不变

密码、完整令牌、密钥、Cookie、授权头、完整手机号/身份证/银行卡、隐私原文、大段请求体一律不写进日志，按第十八章执行。
