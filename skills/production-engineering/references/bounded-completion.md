# 有边界的执行与收尾

位置/状态/篇幅见 `workflow-checklist.md`，授权例外见 `source-policy.md`。本规则统一 Bug、同步、代理执行和评审的完成条件；不缩减用户已确认目标，不撤销必要验证，也不扩大 Git、数据或外部写入授权。

## 本批范围与用户补充

开工先用已有短卡或清单写清本批范围：要交付的可用结果、具体必做 ID、必要验收、明确不含的工作和停止条件。大目标按能独立查看与验收的模块组织，不把“整站所有可能问题消失”当终点。用户明确要求完整目标时保留完整范围和执行节奏，不能擅自只做一批就报完成。

用户中途补充不能遗漏，也不能仅凭“还有/另外”就升级任务。分清并记入原任务：

- **纠错或澄清**：修正当前要求或补清同一结果，更新原项，不重复建项；同一文件的简单补充说明不自动变成复杂任务。
- **替换要求**：按最新指令更新目标，原项注明被替换，不把相互冲突的新旧要求同时当必做。
- **新增需求**：说明对本批交付、工作量和验收的影响；明确要求一起做就加入本批，明确后续处理就保留下一批。未指定批次时，清楚、相关且已授权的新增继续落实并更新剩余范围，不擅自搁置、不重复索要同一授权；影响交付结果的批次歧义才用人话问。

小改仅因实际影响扩大到清单触发条件才升级，沿用 `workflow-checklist.md`。用户需求与 AI 建议分别记录；需求变更不能自动授权部署、生产写入或范围外操作。完成当前确认范围及必要交付后停止；未完成如实列具体缺口，用户明确暂停立即服从。

## 固定验收范围

开工或恢复时，在当前任务区块核实用户目标、固定来源版本/提交、必做事项及验收、受保护行为、停止条件。已有方案沿用，不每轮再写一份。用户要求完整 17 项，就保留这 17 项；每项关联明确子项和证据，不以“所有可能问题都消失”为验收。

多模块目标先固定模块/能力 ID、各自必需检查和适用环境组合；沿用已有记录，不另建审批流程。用户明确要求的完整覆盖照做，其余按实际影响选有限组合，不在执行中不断增加设备、语言或场景排列。必要补漏记清对应原目标、发现证据与新增验收；用户改变要求记录变更依据，不拿“已冻结”拒绝用户补充，也不靠拆细条目虚增完成数。

AI 自己的新增发现先分类，再决定是否成为完成条件；用户补充按上一节处理，不当作建议丢弃：

- **必要缺口**：能够指出对应用户目标/原验收或本次改动破坏的原行为，以及源码、失败场景或明确依赖证据。不修会导致目标不可用或验收失败，加入对应原编号或明确子项，按已有授权推进；关键成功、失败、兼容、安全边界不能漏。
- **非阻塞建议**：额外功能、换风格、无关重构、推测性风险和不影响目标的优化，只放“待后续建议”，不算必做分母、不阻塞交付、不自动实施。
- **阻塞条件**：无法自行查明的产品选择、缺失账号/环境或高风险授权，写出具体未完成项与恢复条件，继续其他独立已授权工作。

“新发现”“review 提了”“上游还有更新”都不是新增必做的充分依据。新增验收必须有上述目标关联；用户改变目标时记录版本/依据，不能悄悄更换上游 SHA 或测试范围。必要遗漏无需逐项审批；范围外建议不能因记入清单获得授权。

## 冻结工作量与有限审查

**固定来源不等于冻结工作量。** 区分用户要求的审查边界与实施清单：前者限定比较区间、模块或候选 ID 与总数，后者限定本轮要改变的结果。候选数量不是缺失补丁数量；“发现所有问题”“继续检查其余”不能单独作为无限任务。

- 指定修复/已选清单：只核对所选项与有证据的必要依赖，不把全历史搜索作为交付前提。
- 笼统上游补丁目标：按用户上下文核实有限比较区间，先固定候选，完成语义分类后冻结实施清单，再实施与验证；不边审边补、每完成一项就从更大范围搜下一项。源码能查清的边界自行确定；会改变用户结果的歧义才问，不机械要求用户审批每项。
- 用户明确要求完整审查/完整版本范围：不得自行缩减完整审查、任意限为若干补丁或交付已完成部分冒充整个目标完成。按固定集合推进，可分批执行但不改总分母。

**内部批次不是暂停点。** 用户授权固定目标做到完成时，自行按依赖分批，不等待用户回复“继续”；进度汇报不等于暂停。用户明确要求逐批确认/本批结束后停止则服从，最新目标取代旧批次节奏。单项阻塞记录原因和恢复条件，其他独立已授权项继续；全部已授权项处理后如实报告未完成项并停止，不通过扩范围或重试消除所有可能阻塞。

审查续作保留已分类 K/N、剩余候选索引和当前阶段，实施续作保留已验数量及未完 ID；在原清单就地更新。恢复只从未分类或真实失效项继续，不重扫已分类集合。剩余集合清空后结束审查，冻结必做清单；后续仅允许用户新增需求或有证据的必要缺口，发现其他独立上游修复不自动加入本轮。

用户明确改为本批收尾（如“停止扫描，只交付已完成补丁”）时，立即停止旧审查，在原任务区块记录最新目标及变更依据。未覆盖候选标“本轮不做 / 未覆盖”，保留原记录，不伪造原审查完成；按新目标处理当前未完项，不再实施新项。复用有效证据，完成最终差异核对及仍必要的验证后停止。若本批存在实际回归仍修复或明确阻塞，不能拿收尾免除验证；不得要求先扫完旧范围才接受新目标。

## 按模块验收，缺条件单列

- **各自结项**：按原 ID 核对本模块全部适用检查，通过即标已完成/verified，记录版本、范围和证据；不等无关模块、整站或外部服务全部齐全才回填。必要共享依赖未验或失败时，相关模块仍待验证，不能为结项跳过。
- **局部证据及时入账**：模块尚未全过时，在原条目旁记录已通过、失败、未测、缺条件的检查 ID；父项列具体剩余 ID。分别报告模块结项数和检查结果，不把局部通过提升为父项完成，也不把已通过的检查一直混作“完全未测”。不另造一套待办或重复累计父子进度。
- **独立推进**：一个模块缺条件，继续其他可做项；已结项模块只因相关实现、配置、环境或共享依赖变化而重开受影响检查，不因切换模块或更新记录而重开。

每个模块的剩余检查固定到具体 ID；完成一块就展示可用结果并更新原状态。不能用“还要全面检查”不断续开尾项，也不把本机可用、全部适用验收通过、正式环境已生效混成一个完成状态。

缺条件在原清单设独立摘要，沿用【阻塞】及现有台账状态，不用“待做”掩盖原因。每项写：**事项/检查 ID、已测范围、没测范围、缺什么及已查事实、影响哪些结果、条件到位后的第一步**。AI 能自行查明或准备的继续做；只向用户要确实必须由用户提供的账号、环境、选择或授权。模拟通过不能代替真实外部成功，缺条件不等于通过、不适用或用户批准省略，也不影响无关模块独立结项。

所有独立可做项处理完后，明确汇报剩余阻塞和恢复条件，按宿主目标状态规则等待/报告阻塞；不擅自标整体完成，不反复跑同一模拟链或扩大找 Bug 来填满等待。仍能推进的必要工作继续，用户要求逐批确认或暂停时服从。

## 证据按实际影响失效

证据须对应声明、相关代码、配置、测试或环境。相关内容未变且结果可核对时复用；新补丁只重验受影响路径及直接消费者，修改共享模块须覆盖受影响声明。实际失败必须处理，不能用较小测试替换失败的必要验收。

状态回填、补证据链接、切换下一任务或上下文压缩，不自动使全部业务证据过期。状态助手指纹变化仍按原 `check` / `finalize` 机制核实文档和源码差异，不伪造通过、不排除文件绕过；不能为了一个勾重跑所有业务测试。环境、构建产物或测试夹具不匹配先纠正验证条件，不立即当作生产 Bug 叠补丁。

测试失败先用最小证据区分产品缺陷、测试定位/预期错误、环境或数据不匹配。只改已证实的原因，保留原失败及必要业务断言；修测试不能删除失败用例、放宽提交值/权限标准或冒充产品已修。测试或诊断次数本身不算验收进展，反复纠正前提仍受下节无进展规则约束。

只有项目明确要求或真实不稳定/并发风险需要，才重复多轮相同测试；说明轮数与原因。基线已有且未被本次引入的失败保留证据和交付限制，不借此无休止修整个仓库；若它使本次必要验收无效，标明真实阻塞。

## 停止重复修复和评审

一次修复依据一个可区分的原因，改后立刻跑对应验证。按同一验收目标累计修产品、修测试和调整环境的尝试；两轮没有实质进展，就停止同一路径修改和复跑，转一次有边界诊断，写清待区分假设、最小实验及退出条件。新增截图、日志、定位或静态通过本身不算验收进展；须指出哪个原失败已消除、哪个待查假设被实证排除或哪个检查已通过。仅换脚本、代理、日志或“最终验收”标题不能重置次数。

持续任务在现有记录里约定时间检查点或模块交付检查点，用户给定时限优先；无指定时根据影响给粗估区间和下一检查点，不许诺固定耗时、不新建计时服务。到检查点报告新增已验结果、累计耗时、具体卡点和剩余量；小改以受影响真实检查完成为点，不加定时汇报流程。反复有零碎新证据但仍未结项时也要调整方法，不无限延长同一条尝试。

诊断仍无突破，记清实际失败或缺失条件与恢复第一步；不能虚构“缺用户材料”来掩盖 AI 自身未解问题。其他独立已授权项继续；完整目标、宿主目标状态及暂停权限照原授权执行。时间或次数到了不等于完成，不降验收标准、不把失败改通过，也不擅自取消有实质推进的必要工作。

最终做一次范围内最终复核。修复具体阻塞后只复核该发现和修复影响，不重开整分支审查；新实证阻塞仍需处理，次要意见记建议。前端按适用的代表页面/状态、多视口和语言验收，不在每个局部修复后重新遍历所有无关页面。

当前确认的固定必做事项及适用验收全部通过，完成已授权交付后，报告结果并停止。用户要求“跑起来给我测试”时，只提供可安全运行的隔离入口与启动状态，然后等待用户反馈；不能自动开始新优化、新审计、合并或部署。未完成时如实列缺口，不将“本切片通过”写成父项或整个项目完成。

## 状态与历史的收尾要求

每个任务一个唯一当前状态，续作在原条目最小局部更新；完整位置、篇幅和历史规则只在 workflow-checklist 定义。父项未完成列未完成子项 ID，不只重复“整体没完成”。证据留短摘要和索引。

写前读取最新文件，更新后核对只动了预定区块；原历史区块保持原样，当前授权原文恢复/归档例外以 source-policy 为准。疑似丢历史只从 Git 历史或备份找准确片段，不凭记忆重建；只有当前快照不能证明具体删除。普通续作不得整体覆盖用户改动，不把恢复/备份要求反向用于阻止用户已明确授权的恢复。
