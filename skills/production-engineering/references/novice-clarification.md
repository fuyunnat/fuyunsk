# 小白友好反问与结果确认

本规则用于所有 `production-engineering` 工程任务。目标不是多问，而是避免用户不懂技术时被迫替 AI 做技术决策，同时防止 AI 在真正影响结果的歧义上擅自猜。

## 一、反问什么，不反问什么

**必须反问的是“结果会不会变”的歧义。** 当存在两种以上合理理解，而且会明显改变最终页面、功能、数据、副作用、范围或交付方式时，先暂停受影响部分并确认。

典型情况：
- “重写 UI / 优化 UI / 改好看点”同时可能表示原样迁移、保留功能重做视觉、或只精修现有结构。
- “重写 / 重构 / 重做”可能涉及只改实现、改变架构、删除旧能力或改变外部行为。
- “把这个修了”存在多个真实目标，且源码/运行证据不能确定用户指的是哪一个。
- 用户要求可能触及删除、生产、支付、权限、数据库结构、外部消息、主线合并等高风险结果。
- 两个可行方案会让用户以后看到或使用到明显不同的产品行为，而当前材料无法决定。

**不应反问的是 AI 自己能查明的技术事实。** 文件路径、框架版本、组件位置、依赖、启动命令、测试命令、Git 状态、接口位置、现有 Design System、源码已明确的字段和业务规则，应先查项目；不要问用户“你用 Vue 几”“文件在哪”“要不要 Pinia”“测试怎么跑”这类可自行核实的问题。

用户已经明确结果时直接执行，不为了“确认一下”重复问同一问题。

## 二、反问必须让不懂技术的人也能选

一次只聚焦当前真正阻塞结果的问题；优先给 2–3 个**结果选项**，每项描述用户最终会看到什么，不堆术语。必要时给一个推荐并用一句话解释原因。

示例：

> 你说“后台 UI 全重写”，这里有三种结果：
> A. 样子基本保持，只换实现；
> B. 功能全部保留，但视觉和布局重新设计；
> C. 保留现在结构，只把它做漂亮、统一。
> 我建议 B，因为“全重写 UI”通常指保留业务、重做视觉。你选 A/B/C 就行。

不要问：

> 你要 Vue 还是 React？要不要 shadcn-vue？组件拆成多少个？用哪种状态管理？

这些属于 AI 应结合项目和已确认结果自行决定的实现问题。

## 三、先查再问，问完就记住

反问前先做安全只读查证：源码、演示站、配置、Git、已有工作清单、当前运行结果能回答的，不再问用户。

用户回答后，把该决定作为当前任务约束写入适当的项目工作清单/任务状态（不得记录秘密），后续同一任务不得反复询问。新要求与旧决定冲突时，以最新明确要求为准，并只重新确认真正冲突的部分。

## 四、“随便 / 你看着办”不是无限授权

用户说“随便”“你决定”“你看着办”“自由发挥”时，只表示 AI 可以在**已经明确的功能、项目、风险和设计范围内**自行选择实现与视觉细节。

它不自动授权：
- 删除或放弃旧功能；
- 改变业务规则、权限或数据语义；
- 切换用户已指定的技术框架；
- 跨项目写入；
- 生产、支付、数据库破坏性变更等高风险动作；
- 合并主线、强推或其他需要单独授权的 Git 操作。

## 五、长任务不要因为一个问题全部停住

只有受歧义影响的部分暂停。与该选择独立的后端、测试、盘点、只读分析或其他模块可以继续时继续推进，并在清单里标出阻塞点。

如果用户暂时没回答，不能偷偷任选一个会改变结果的方案；也不要用默认模板把空白补掉。

## 六、UI 重写专用判断

- “照原站做 / 样子别变 / 只换 Vue / 原样重写” → 忠实迁移，视觉也是基线。
- “UI 全重写 / 重新设计 / 换一套界面，功能别动” → 功能和流程来自旧系统，视觉进入新设计模式。
- “优化一下 / 做漂亮点 / 去 AI 味” → 若结构是否保留会显著影响结果且上下文未明确，先按 A/B/C 的人话选项反问。
- 同时给了源码/演示站并不自动等于必须保留旧视觉；要看用户最新明确要求。若“有旧站”与“重写 UI”并存且范围不清，必须反问是“视觉也保留”还是“只保留功能”。

反问的目的，是让用户选择产品结果，而不是要求用户先学会工程实现。
