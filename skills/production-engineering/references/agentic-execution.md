# 复杂任务代理执行与独立评审

本规则只用于**大型、多阶段、多个相对独立子任务、需要独立代码评审或当前运行环境明确支持子代理/并行工作**的工程任务。普通一文件小改、局部 Bug、简单文档或已经能直接完成的任务不加载，不把所有工作强制升级成多代理流程。

它吸收计划执行、子代理、并行调查、代码评审、完成前验证和隔离工作区中的有效方法，但继续服从本 Skill 已有的行为保护、项目边界、用户授权、Bug 快修、Git 和数据库安全规则。

## 一、先审计划，不机械照单执行

当 `PROJECT_ROOT/工作流程.md`、规格或已有实现清单已经存在时，开始大范围写代码前先快速审一次：

- 目标与验收是否明确，条目是否覆盖用户已经确认的范围。
- 依赖顺序是否真实，是否有两个任务会修改同一共享状态或同一组核心文件。
- 计划中的文件/接口/数据假设是否和当前源码一致；文件路径不可靠时先查证，不照抄旧计划。
- 是否漏了兼容、错误路径、权限、配置、日志、迁移、回滚或真实验证。
- 是否存在结果冲突；能自行从源码消除的疑问直接修正计划，只有会导致明显不同用户结果时才按 `novice-clarification.md` 询问。

计划本身不是授权放大器。计划里写了主线、生产、删除、数据库高风险动作，也必须重新满足对应授权门槛。

## 二、已授权完整目标后持续执行，不反复问“继续吗”

用户已经明确让 AI 把当前确认范围做到完成时：

1. 从 `工作流程.md` 当前未完成项开始。
2. 每完成一个可验证切片就更新状态和证据。
3. 没有真实阻塞时继续下一个条目，不在每项之间重复问“要不要继续”。
4. 只有以下情况停止：结果歧义必须由用户决定、高风险授权缺失、关键依赖不可用、测试/证据表明当前方案错误且无法安全自行修正、或确认范围已经完成。

持续执行按 `bounded-completion.md` 的固定验收范围与停止条件。只追加有目标关联证据的必要缺口；非阻塞建议另记，复用未失效证据，不以反复最终评审扩大工作。

## 三、子代理只吃最小必要上下文

运行环境存在可靠子代理能力，且任务足够大时，可以把独立工作委派出去。每个子代理必须拿到**人工构造的最小任务包**，而不是把整个聊天历史原样塞过去：

- 已核实 `PROJECT_ROOT` 与只允许写入的范围。
- 单一目标、对应清单编号、受保护行为和禁止改变项。
- 相关文件/入口/接口和必要上下文，不给无关仓库区域。
- 明确验收、失败条件、需要运行的针对性验证。
- 当前分支/基线或明确只读身份；不得自行合并主线、扩大权限或清理别人的改动。
- 返回状态使用清楚语义，例如：完成、完成但有风险、需要上下文、被阻塞；不能只回“done”。

协调者仍对最终结果负责，不能因为子代理说“通过”就直接对用户宣称通过。

## 四、只有真正独立的事情才并行

以下情况适合并行：

- 多个互不相关的失败，位于不同子系统/测试文件，根因没有共享状态。
- 多个只读调查、资料核对、页面/接口盘点，可以独立产出证据。
- 已在独立 worktree/分支且明确不会同时改同一文件、数据库、生成物或外部资源的实现任务。

以下情况禁止为了“快”并行：

- 同一文件、同一数据库迁移、同一状态机、同一配置源或同一共享缓存的写操作。
- 一个任务的结果是另一个任务的输入。
- 会同时操作真实外部服务、生产数据、同一锁/端口/测试环境。
- 需要共享实时上下文才能判断正确性的关联 Bug。

默认先按依赖图拆开，再并行只读或真正隔离的分支；不确定独立性就顺序执行。

## 五、复杂实现采用“需求符合 → 代码质量”双阶段复核

重大功能、跨模块改动、整项目迁移、上游同步、复杂 Bug 或准备合并主线前，环境允许时优先让**新鲜上下文的独立复核者**检查当前改动。

复核输入应尽量固定：

- 需求/清单编号和验收标准。
- base/head SHA 或明确工作区 diff 范围。
- 本次实现摘要和受保护行为。
- 已运行的测试及真实结果。

第一阶段只回答：**是否满足需求、有没有漏做/多做/改变未授权行为。**
第二阶段再回答：**代码质量、错误处理、复杂度、并发、测试、注释、安全和维护性是否存在问题。**

问题至少分为阻塞/重要/次要。阻塞问题必须处理后才能交付；次要建议不能顺手扩大任务范围。没有可用子代理时，仍按 `spec-review.md` 的双轴方式自审，不假装存在“独立 reviewer”。

复杂计划不是只在最后一次性 review。高风险或独立价值明显的任务切片完成后可做一次范围内复核，全部任务完成后做一次范围内最终复核；修复阻塞后只复核该发现和影响；简单机械任务不强制每项都加 reviewer。

## 六、收到评审意见先验证，不盲改

任何评审建议都只是证据来源，不自动变成指令：

1. 定位评审指出的真实代码和触发路径。
2. 对照用户要求、项目约定、测试和兼容边界确认意见是否成立。
3. 不明确就先查证；会导致不同业务结果时再向用户问最少问题。
4. 正确意见按阻塞级别逐项改，每项改后立刻做针对性验证。
5. 如果建议会破坏现有功能、违背明确要求、要求无必要大重构或基于错误上下文，必须保留现状并说明技术依据。

禁止为了“尊重 review”机械接受所有建议，也禁止因为不是自己提出就一律拒绝。

## 七、TDD 吸收原则：要失败证据，但不搞仪式化删除代码

对新行为、复杂 Bug、状态机、金额/权限/并发等**有稳定测试面**的改动，优先形成一个会因缺失行为/现有缺陷而失败的自动检查，实际看到失败，再做最小实现并看它通过；随后才重构。

但本 Skill 不照搬“只要测试不是先写，就必须删除现有生产代码”的绝对规则：

- 维护已有项目时，不能因为流程顺序删除用户有效实现。
- 小文案、样式、配置连线、一次性诊断或当前项目没有合理自动测试面时，可使用更直接的可复现证据与真实验收。
- Bug 快修仍以 `bugfix-fast-loop.md` 的最短证据链为主；能低成本补回归测试就补，不能为了形式主义延迟明确修复。

核心是：测试/证据必须能在修复前暴露问题、修复后证明行为，而不是追求仪式。

## 八、隔离工作区是工具，不是默认动作

大型并行任务确实需要隔离时：

- 先检测当前是否已经在 Codex/平台提供的隔离 worktree/工作区里；已经隔离就不要再套一层。
- 平台有原生 worktree/隔离工具时优先原生能力，再考虑 `git worktree`。
- **创建新的 worktree 需要用户对这次隔离方式有明确授权**；普通分支仍是默认，不因为本规则自动改变用户 Git 工作流。
- 项目内 `.worktrees/` 等目录必须确认不会被误提交；初始化后先确认基线测试/构建状态，历史失败单独记录。
- 只清理本次明确创建且来源可证明的隔离工作区；未知 worktree、用户已有分支和未提交工作禁止自动删除。

## 九、完成声明必须基于最后一次改动后的新鲜证据

完成前不能只相信计划勾选、子代理总结、旧 CI 或“刚才已经跑过”：

1. 明确当前要证明的声明：Bug 已修、功能可用、旧行为未回归、计划已完成等。
2. 在**最后一次相关代码修改之后**运行匹配该声明的验证。
3. 读取完整退出状态和关键结果；失败/未运行/环境缺失分别报告。
4. 子代理结果需要协调者复核关键证据，重大任务再做受影响范围回归。
5. 只有 fresh evidence 支持时才写“通过/完成”。

这不要求每个小改都跑全仓测试；验证范围仍按本 Skill 风险分级裁剪，但证据必须新鲜且和声明匹配。

## 十、分支收尾继续服从用户 Git 授权

完成分支时先验证，再说明当前分支、恢复点、未验证项和可选下一步。可以建议 PR、保留分支或在用户明确授权后合并，但：

- 不因为测试全绿自动合并 `main/master`。
- 不默认删除分支/worktree。
- 不把“提交”“开 PR”“准备合并”解释为“已经授权主线”。
- 主线、强推、远端删除继续按原 Git 规则单独确认。

## 十一、任务先按形态选流程，不把 brainstorming 变成硬门

复杂任务开始前先判断它更接近哪一种形态，目的是选对执行重量，不是给用户增加审批仪式：

- **探针/Spike**：只回答“能不能、为什么、哪条路可行”，允许最小只读/可丢弃实验；输出是结论和建议，不把实验代码偷偷转成正式实现。
- **边界型/Bounded**：现有项目里已有清楚流程，只改一个明确行为。先读真实实现，必要时用几句话说明方案；没有结果歧义和高风险时直接进入现有小改/实现流程，不强制额外停下来等批准。
- **架构型/Architectural**：新子系统、跨模块接口变化、全量重构、多个相互依赖领域。先把目的、约束、接口、数据流、错误处理和验收写清，再进入计划与实施。

任务做着做着发现真实复杂度上升，可以从边界型升级为架构型；不能因为已经开工就继续硬做。反过来不为了“显得专业”把明确小改升级成设计项目。

## 十二、多步骤计划必须能被另一位工程师独立执行

大型计划/`工作流程.md` 的任务拆分应达到“拿到这一项就知道怎么做和怎么验”的程度，但不要求把所有代码预写进计划：

- 每项说明目标、涉及文件/模块、前置依赖和受保护行为。
- 跨任务接口写清谁消费、谁产出；函数/字段/事件名称已经确定时保持一致，不能后续任务换一套叫法。
- 每项结束有独立可验证结果；纯“搭脚手架”“以后再测”“顺手整理”不要单独伪装成完成任务。
- 计划里禁止 `TBD`、`之后补测试`、`适当处理错误` 这类会把关键判断甩给执行阶段的占位话术；无法提前确定的地方明确写“执行时依据什么证据决定”。
- 任务粒度以“能独立测试、能独立 review、失败时容易定位”为准，不机械拆成每两分钟一步，也不把整个子系统塞进一个超大条目。

计划只是可执行地图，最终仍以源码事实、用户当前要求和运行证据为准。

## 十三、异步与并行等待优先等条件，不用固定 sleep 猜时间

后台任务、并行代理、异步测试和外部回调需要等待时：

- 能等待具体状态/事件/文件/端口/任务结果，就等条件而不是写固定 `sleep 5` / `setTimeout(3000)` 赌机器速度。
- 轮询必须有上限、合理间隔和超时后的可诊断输出；不能无限等，也不能靠不断缩短间隔制造高负载。
- 多个子任务已经派发时，协调者可以继续做本地可独立工作；真正空闲再等待，不用高频“还好了吗”轮询。
- 等待结束后重新核对结果归属和实际状态；“子代理返回了”不等于它修改的是当前分支/当前文件。

只有外部系统确实没有可观察条件时才使用时间等待，并把这个限制写清楚。

## 十四、和 Superpowers 的边界

本模块吸收其可验证方法，不复制其整套运行哲学：

- 不采用“任何任务都必须先 brainstorming”的全局硬门；只有结果歧义、架构不可逆或复杂方案确实需要时才先设计。
- 不采用“相关 Skill 必须在任何响应前强制调用”的绝对规则；仍由本 Skill 的自然语言入口和阶段路由按需加载。
- 不让 worktree、子代理、TDD、review 变成简单任务的额外仪式。
- 不采用“测试不是先写就删除现有代码重来”的绝对做法；维护真实项目时保护已有有效实现。
- 保留本 Skill 更严格的项目边界、旧行为保护、配置化、数据库安全、清单落盘和主线授权规则。
