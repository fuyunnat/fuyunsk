# 原文执行路由

入口定通用边界，仅作领域补查，无需每次串行读；不替代原文。已知阶段与领域时先一次取齐原文和专项说明；未知条款才查 `rules-index.md`：

```bash
node <技能目录>/scripts/read-rules.js --stage 实现 --topic 前端
node <技能目录>/scripts/read-rules.js --topic 接口,数据库
node <技能目录>/scripts/read-rules.js --id 04-04
```

没有 Node.js 时直接按索引读文件，不安装运行环境。助手只读本技能条款，不扫描项目、不联网、不执行 Git、不恢复状态。`--stage` 按下表扩展领域并集并一并返回专项文件，不只取单章；旧 `--topic` / `--id` 的条款与原始文本不变；第九章附带 `amendments` 当前选型，不能只取原文旧默认。额外专项可用 `--reference design-testing.md` 同批读取。

阶段由模型依据任务模式、风险和授权选择，不由读取器猜测。只读不写入；小改必须满足全部快速条件，不能用参数降级高风险。验证、提交等阶段只取当前阶段；新任务从中途开始需同批追加 `--topic 通用,适用方式`。只有内容仍在上下文且版本未变才不重读；截断、压缩丢失或升级后重新读取所缺部分。

## 写代码默认应用专业代码工艺

`code-craft.md` 在“小改”和“实现”阶段自动加载，凡真正写可执行代码都要应用；纯只读、纯文档、验证/提交阶段不额外加载。它补充命名、职责边界、类型/契约、业务不变量、错误分层、依赖方向、复杂度、并发、可测试性和注释要求，但不能借“科班/最佳实践”扩大范围或改变原业务。

注释是代码交付的一部分：非显而易见业务规则、兼容分支、金额/精度/时区/单位、状态机、并发/锁/幂等/事务、缓存一致性、安全/权限、外部协议、性能反直觉写法以及重要 workaround 必须留下维护者能理解的“为什么/约束/移除条件”。简单代码不写逐行翻译式废话注释；逻辑变化时同步更新注释，禁止让旧注释继续误导。

## 大型多阶段任务按需进入代理执行

`agentic-execution.md` 不是普通工程任务的常驻层。只有任务足够大、存在多个相对独立子任务、环境明确支持子代理/并行，或重大改动确实需要独立复核时，才使用 `代理执行` topic。

用户已经授权把确认范围做到完成时，不在每个清单项之间反复问“继续吗”；无阻塞就持续推进并更新 `工作流程.md`。如果使用子代理，给每个子代理人工构造的最小上下文，不直接灌入整段会话历史；只有真正独立、无共享写入和无依赖关系的任务才并行。

重大实现优先按“需求符合 → 代码质量”双阶段复核；review 意见必须先对照源码、需求和测试确认，再逐项实现。完成声明必须基于最后一次相关修改后的新鲜验证，不能只信子代理总结、旧 CI 或计划勾选。

worktree 只在确有隔离价值且用户对本次隔离方式有明确授权时使用；优先平台原生隔离能力，普通分支仍是默认。普通 Bug、小改、简单文档不因为支持子代理就加载这一层。

## 派生项目上游同步是选择性吸收，不是追平官方

用户已经二开了原项目，又要求“同步官方/上游某个 Bug 修复、新功能、PR、commit”时，优先读取 `upstream-sync.md`。默认流程是：**建立派生项目恢复点 → 新分支 → 读上游真实 diff → 找到当前派生代码里的等价逻辑 → 补丁式吸收 → 真实测试上游目标 → 回归二开能力 → 启动给用户测试 → 报告影响路径 → 停止。**

不得把“同步官方”解释成整仓覆盖、重置成本地官方版、默认 merge `upstream/main` 或整仓 rebase。上游同名文件只是证据，不自动拥有覆盖派生文件的权限；上游删除功能也不自动授权删除二开功能。只有目标 commit 足够独立、历史关系明确且 diff 证明不会破坏派生改动时才考虑直接 cherry-pick，否则按当前派生结构做语义补丁。

如果上游改动同时触及前端、后端、接口、数据库、配置、依赖、安全等领域，再追加对应 topic；不要为了上游同步预读全部领域。普通本地 Bug 修复不因为存在上游仓库就自动加载本规则。

## SEO 是开发能力，但按公开页面与明确目标加载

`seo-engineering.md` 分两层：公开且希望被搜索引擎发现的前台页面在新建、重写、迁移或大改模板时只做轻量 SEO Guard；用户明确说“SEO、收录、Google、sitemap、Schema、多语言 SEO、商品 SEO、GEO/AI 搜索”等时才进入完整 SEO Engineering。后台、登录后页面和普通 Bug 不因为项目有网站就自动做全站审计。

用户不需要知道 canonical、hreflang、robots、JSON-LD 或 Core Web Vitals。能从源码、页面响应和当前官方资料判断的技术方案由 AI 自查。SEO 规则有时效性：Schema 支持、富媒体资格、AI 搜索、Crawler、CWV 和搜索引擎政策等以执行时 Google Search Central / web.dev / Schema.org / 对应搜索引擎官方资料为准，不能把 Skill 内旧知识当最新事实。

公开页面模板、路由、SSR/SSG、多语言 URL、商品/分类模板等发生明显变化时，修改前后要做受影响范围的 SEO Drift 对比；不能只看 build 或页面 200。批量 URL、canonical、noindex、robots、hreflang、sitemap 范围和结构化数据体系变化属于高影响 SEO 变更，继续受行为锁和高风险确认约束。

## 前端模板二开是并行新增，不是覆盖改版

用户要求“重新二开一套前端模板、旧模板不要动、V1 保留再做 V2、功能不能漏”时，读取 `parallel-template-development.md`，并使用 `模板二开` topic。旧模板目录默认只读作为行为基线，新模板使用独立目录/入口并行开发；共享业务层可以复用，但任何共享层变化都要回归旧模板。

实现前先建立固定功能分母：页面、路由、导航、交互、loading/empty/error、表单、API、权限、副作用、响应式、多语言、公开 SEO 和资源都要交叉盘点。每个能力有稳定编号；开发中发现遗漏只能追加，不能删掉旧条目让完成率变好。只有 `verified` 或用户明确批准的 `approved-omit` 才进入完成分子；`implemented` 仍算未完成。

这不是整项目迁移：普通模板 V2 不自动加载 `project-migration.md`。如果用户实际要求整个项目换语言/全量架构重写，再切到整项目迁移。公开可索引模板追加 SEO Guard；后台/私有模板不因此加载完整 SEO。普通页面小改、单组件换皮和 Bug 修复不加载模板二开专项。

## 配置化和前台多语言不是“把一切塞进 .env”

`configuration-localization.md` 负责区分启动级基础设施和运行时运营配置：应用自身的 MySQL、Redis 等启动前就必须可用的连接信息优先放部署 Secret / `.env`；SMTP、支付、短信、对象存储、第三方 API 以及站点/业务参数，只要项目架构允许运行时修改，优先后台配置，敏感值必须加密存储、脱敏展示并受权限与审计保护。

前台新建、重写或新增功能默认按多语言友好方式实现，除非用户明确要求单语言或当前任务是严格原样迁移。静态用户文案不散落硬编码，动态运营内容按项目现有数据模型支持翻译/fallback；后台本身不因此强制多语言，但需要能维护前台各语言内容。旧 `.env`、旧单语言数据和旧配置迁移继续遵守兼容优先，不能一刀切。

## 生产日志是交付能力，不是额外装饰

第十八章已经定义日志、错误日志和可观测性要求。执行时再补三条门槛，防止“规则写了但程序没有日志”：

- 新建后端、重大后端功能、整项目迁移或生产部署，不能在关键失败路径完全无日志；必须沿用项目 logger，让启动/关闭、关键请求失败、数据库/事务失败、外部依赖失败、后台任务失败能留下可定位上下文。
- 普通小修复不重做日志体系；如果本次修改新增或改变了错误路径，就复用现有 logger 留下必要的 `warn/error` 和 request/trace/task ID。没有现成 logger 时，只在确实需要的生产代码补轻量方案，不为一个小改引入大型监控依赖。
- “buglog”不强制一定是单独文件：容器/平台用 stdout/stderr、结构化日志或 APM 时可按 level/query 分离；传统文件部署可分别查看并轮转运行日志与错误日志。无论形式如何，异常必须可查，且不得记录密码、Token、Cookie、密钥和隐私原文。

## Git 按阶段读取

第四章拆为 `04-00.md` 至 `04-10.md`：00 是通用交付边界，01 按逻辑提交，02 提交前测试，03 推送和分支，04 中文提交格式，05 提交前检查，06 远端风险，07 评审协作，08 回滚，09 CI，10 测试证据。

到对应步骤前读取对应条款；提交至少覆盖 00、01、02、04、05、10；推送另读 03、06、09；评审另读 07；回滚读 08 及实际影响领域。合并、主线直写和其他高风险操作不能由“默认交付”代替确认。

## 非原文方法

普通 Bug 修复先读取 `bugfix-fast-loop.md`；只有难复现、偶发、跨边界、连续两次最小修复失败或高风险时才升级读取 `diagnosis-feedback-loop.md`。设计与测试读取 `design-testing.md`；规格与双轴评审读取 `spec-review.md`。

`proven-engineering-methods.md` 只提供已审查的非冲突补充：影响优先、When NOT to Use、审查范围预算、blast radius 与 Skill 维护方法。它的优先级低于用户当前要求和本 Skill 现有规则；普通 Bug、小改、已明确任务不得因为它升级流程。需要时可用 `--topic 工程增强` 或 `--reference proven-engineering-methods.md` 同批读取。

这些方法只补充执行方法，不覆盖本次原文。`upstream-notes.md` 只在维护来源时读取。

## 补充稿

`rules-speed/01-01.md`、`rules-speed/01-02.md` 保留单职责与回归保护补充；Bug 前置在速度稿第二章第三节。需要时读取，不全篇注入。冲突遵守 `source-policy.md`，不把不一致偷偷变成新规范。

`整项目迁移` 仅整项目重写时加载，局部重构不加载；实现前绑定台账，恢复读当前模块，完成前逐项验收；涉及新后端或后端迁移时同时应用第十八章日志要求，并按 `configuration-localization.md` 避免把业务/运营配置和前台文案写死。
