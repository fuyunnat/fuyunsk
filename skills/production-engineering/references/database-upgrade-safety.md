# 线上数据库增量升级与数据保护

本规则用于程序升级、部署、版本迁移和数据库结构变更。目标是：**程序可以安全升级数据库结构，但绝不能把线上数据库当成可重建的临时文件。** 默认保留现有数据库、表、字段和业务数据，只做完成新版本所必需的兼容性增量迁移。

## 零、清库硬限制与隐式副作用

**本 Skill 不执行清库、全表清空或重建现有数据库。** 不因用户催促、备份存在、环境名叫“测试”、命令失败或 AI 认为“重来更快”而放开；备份不构成清库授权。禁止直接运行，也禁止编写会在启动、部署、测试、回滚时自动执行的清库路径，包括 `DROP DATABASE`、`TRUNCATE`、无范围的 DELETE、ORM `force sync` / `reset` / `fresh`、删除 SQLite 文件、删除数据库数据目录或 `docker compose down -v` 等删除持久卷操作，以及“清库重试”。复制、导入或恢复操作也不得覆盖现有库。用户要求清空时只做只读影响分析和可审核方案，不代为执行；对明确指定的少量记录做定向删除属于另一类任务，仍须核对目标、范围、授权和恢复方式。

**启动或测试前**检查启动脚本、ORM 初始化、容器命令和环境配置：启动命令可能隐式迁移。核实真实环境身份、连接目标、迁移版本与将触发的 SQL；无法排除对现有库的写入时，不启动连接该库的服务，不以“先试一下”代替预检。纯只读排查不得写数据库。UI 小改、版本信息页、更新日志等无关页面改动不触发 migration；需要预览时使用明确隔离的全新临时预览库或 mock，不借用现有业务库，也不把临时库误报为线上库。

**迁移日志不等于实际迁移。** 遇到“检查/迁移数据库”字样，先查代码路径、连接目标、执行记录和变更前后 schema；没有证据不推断清库，也不声称线上绝对安全。清楚区分“程序具备启动迁移机制”“本次启动实际执行了迁移”“数据库中的数据发生改变”，向用户报告已观察到的事实和未验证部分。

## 一、默认采用增量迁移，不重建数据库

线上升级时，先读取当前真实 schema、迁移记录和目标版本需要的结构差异，再生成或执行版本化 migration。默认顺序是：

1. 保留现有数据库和全部历史数据。
2. 检查缺失的表、字段、索引、约束或兼容结构。
3. 仅执行已审查的非破坏性增量变更。
4. 记录迁移版本与执行结果。
5. 新版本程序在迁移成功后再继续启动或切换流量。

不得因为“新版本 schema 不一致”“初始化更省事”“测试库是这样做的”就重新建库、重新导入全量 SQL 或覆盖线上数据库。

## 二、可自动执行的升级必须是非破坏性、可重复、可验证

在项目和数据库实际支持、锁表/性能风险已评估的前提下，可把以下**新增型**变化做成自动 migration：

- 创建缺失的新表。
- 添加新字段，优先兼容旧版本的 nullable 或安全默认值策略。
- 创建新索引或其他不会删除现有数据的结构。
- 创建迁移版本表或等价记录。
- 对新增字段做明确、受限、可恢复的数据回填。

自动 migration 必须具备幂等或版本保护：已经成功执行过的版本不能在每次启动时重复乱改 schema。多实例部署时必须使用单一迁移执行者、数据库锁或框架等价机制，避免多个实例同时执行同一 DDL。

“自动补字段”指**自动执行已随版本发布并经过审查的 migration**，不是让 ORM 在生产环境根据模型差异随意同步、删除或重建 schema。

## 三、这些操作默认禁止

以下操作默认禁止；其中整库或全表清空、重建现有数据库受上述硬限制，不能靠普通部署授权放开。其他破坏性结构变更必须另立任务并取得本次具体授权，禁止执行或生成会被自动执行的：

- `DROP DATABASE`。
- `DROP TABLE`。
- `DROP COLUMN`。
- `TRUNCATE`。
- 无明确范围的全表 `DELETE`。
- 删除现有索引/约束后不保留兼容路径的破坏性改动。
- reset、recreate、fresh、force sync、schema replace 等重置数据库操作。
- 用新 SQL dump、空库、开发库、测试库覆盖线上数据库。
- 删除数据库文件、数据目录、volume 或持久化存储后重新初始化。
- 失败后以“重建数据库”作为自动恢复方案。

即使工具、ORM 或框架提供 `auto migrate`、`sync`、`reset`、`fresh`、`force` 等快捷能力，也必须先确认它在当前版本是否可能删除、重建或改写现有结构；不能只看命令名称判断安全。

## 四、字段修改和删除走 expand / contract，不一步破坏

以下变化默认视为可能损数据或破坏旧版本兼容，不能直接自动执行：

- 字段重命名。
- 字段类型缩窄或可能截断数据的类型修改。
- nullable 改为 NOT NULL 且旧数据未满足约束。
- 改变默认值会影响旧请求语义。
- 删除字段、表、索引或旧结构。
- 大规模数据改写。

优先采用 expand / contract：

1. **Expand**：先新增兼容字段/表/结构，不删旧结构。
2. 新旧程序在过渡期都能工作，必要时双写/兼容读取；不能只保证新版能读，而让仍在线的旧版马上失效。
3. 分批回填并验证数据完整性，同时确认旧数据可被新版读取、新数据不会让仍受支持的旧版异常。
4. 新版本稳定后，再评估旧结构是否可以下线。
5. 真正删除旧字段/表必须作为单独高风险变更，再次明确授权；不能把它夹在普通发布里自动完成。

如果应用/API/配置和数据库同时升级，必须把兼容窗口作为一个整体设计：schema 兼容不等于应用兼容，不能出现“库没删数据，但旧程序已经读不了”的假兼容。

用户不懂技术时，不要求用户选择 DDL 方案；只需用人话说明结果，例如“保留旧字段兼容一段时间”与“现在永久删除旧字段”的区别，并按 `novice-clarification.md` 让用户选择结果。

## 五、生产升级前必须知道连的是哪个库

任何线上 migration 前必须核实：

- 数据库主机、端口、库名和环境身份。
- 当前 schema 版本/迁移版本。
- 当前应用版本与目标版本。
- 是否存在可恢复的备份或快照，以及恢复路径是否真实可用。
- 当前 migration 会改哪些表/字段、预计影响和锁表风险。
- 发布期间是否会有旧实例、旧任务、旧客户端继续访问该库；如果有，迁移必须证明它们仍能工作或先采用兼容发布顺序。

不能根据 `.env.example`、默认库名、旧项目配置或另一个项目的数据库连接推断生产目标。无法确认真实数据库身份时，停止写操作。

## 六、迁移失败时停止发布，不拿数据冒险

迁移失败、超时、锁等待异常、数据校验失败或 schema 与预期不一致时：

- 停止继续执行后续 migration。
- 不启动依赖新 schema 的新版本，或停止切换流量。
- 保留失败证据和当前数据库状态。
- 不自动 DROP / reset / restore 覆盖来“修复”。
- 根据已审查的回滚方案、向前修复 migration 或用户明确授权处理。

数据库 DDL 的“回滚”不等于随手执行破坏性的 down migration。若 down 会删除新数据或旧数据，应优先停住并采用向前修复；恢复备份属于高风险生产操作，必须另行确认。

## 七、上线验证

完成增量迁移后至少验证：

- 原有表和关键历史数据仍存在。
- 新字段/新表/新索引已经按目标出现。
- migration 版本记录正确，重复运行不会重复修改。
- 旧业务路径和新业务路径都能读取已有数据。
- 涉及滚动发布或新旧版本并存时，至少验证一个仍受支持的旧版本路径和一个新版本路径都能正常访问迁移后的数据库。
- 新增字段的空值、默认值、回填结果与程序逻辑一致。
- 没有未经授权的 DROP/TRUNCATE/全量 DELETE/重建动作。

只有“程序启动成功”或“migration 命令返回 0”不能证明线上数据安全，也不能证明新旧版本真正兼容。

## 八、和原有行为锁的关系

本规则是 `behavior-preservation.md` 中“兼容优先：旧新先共存”的数据库具体化：程序升级默认保护已有数据、schema、旧调用和业务语义。用户要求“更新线上版本”“升级程序”“发布新版本”“连接新数据库”只授权完成该目标所需的兼容升级，不自动授权清库、覆盖数据库、删除表/字段、改变旧数据语义、永久清理旧结构或让仍受支持的旧版本失效。
