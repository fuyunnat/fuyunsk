# 专业代码实现规范（Code Craft）

用于所有真正写可执行代码的实现、小改和 Bug 修复。目标不是把简单代码写复杂，而是让代码在功能正确之外，长期可读、可改、可测、可定位问题。纯只读、纯文档、只改说明文字时跳过不适用部分。

本规范低于用户当前明确要求、现有项目约定和本 Skill 的行为保护/兼容/安全规则；不能借“代码更漂亮”扩大业务范围、重写无关模块或改变既有行为。

## 一、先按职责和变化原因组织代码

- 模块、类、组件、函数优先围绕单一职责和同一变化原因组织；避免一个文件同时承担请求、校验、业务规则、持久化、格式化、UI 状态等多种无关职责。
- 代码过长只是风险信号，不机械按行数拆分。只有拆分后边界更清楚、依赖更少、测试更容易时才拆。
- 避免 God Object / God Function、超大组件、万能工具类和无边界 `utils`；共享逻辑应按领域或能力归位。
- 一个函数应尽量在一个抽象层级完成一件事；复杂流程用有业务含义的小步骤表达，而不是堆连续深层嵌套。
- 优先早返回、守卫条件和清晰状态转换，减少不必要的 `if/else` 金字塔。
- 不为了“优雅”提前造框架、抽象层、插件系统或通用引擎；出现真实重复和稳定变化轴后再抽象。

## 二、命名表达领域含义，不让读者猜

- 名称描述业务含义和单位，不用 `data`、`temp`、`info`、`handle`、`process` 等泛词掩盖真实职责；局部极短生命周期变量可按语言惯例简写。
- 布尔值体现真假语义，如 `isEnabled`、`hasPermission`、`canRetry`；集合使用复数或集合含义。
- 时间、金额、比例、长度、分页、状态码等容易混淆的值，在类型或命名中明确单位/语义，例如毫秒与秒、分与元、含税与未税。
- 同一概念在 API、领域层、数据库和前端尽量保持一致命名；确需映射时集中转换，不让别名散落全仓。
- 不随手改公共名称追求“更顺眼”；公共重命名属于兼容变化，按影响范围处理。

## 三、契约、类型和边界要明确

- 在系统边界验证不可信输入：HTTP、消息、文件、第三方 API、数据库反序列化、用户表单等；进入可信领域层后避免重复无意义校验。
- 语言支持静态类型时优先使用准确类型、枚举/联合/值对象表达有限状态，减少 `any`、裸字符串、魔法数字和弱类型字典在核心逻辑中传播。
- 不用 `null` / `undefined` / 零值同时表达多种业务状态；有“缺失、未知、未加载、无权限”等不同含义时显式区分。
- 函数和接口要让调用方能看出输入、输出、错误和副作用；隐藏副作用越少越好。
- 公开接口、事件、数据库字段、配置键的契约变化继续遵守兼容优先，不能因类型更漂亮直接破坏旧调用。

## 四、把业务不变量写进代码结构

- 金额、库存、额度、次数、权限、状态机、幂等键、唯一性等关键规则应集中在明确位置，不复制到多个控制器/页面各写一份。
- 非法状态应尽量在创建或状态转换边界被阻止，而不是到流程末尾才发现。
- 跨多步写操作时明确事务/补偿/幂等边界；不能让“半成功”成为默认状态。
- 状态转换应能回答“谁允许从 A 到 B、失败后是什么状态、重复请求会怎样”。
- 业务规则来自现有代码或用户要求；不能把个人觉得更合理的规则写成新的不变量。

## 五、错误处理分层，不能吞异常

- 区分用户输入/业务拒绝、依赖失败、临时故障、程序错误；不要所有失败都变成一个模糊的 `500` 或 `false`。
- 捕获异常必须有目的：补上下文、转换边界错误、清理资源或执行明确恢复。禁止空 `catch`、无条件吞错、只打印后继续假装成功。
- 重新抛出/包装错误时保留原始 cause 或可追踪信息，避免丢失根因。
- 对外错误不泄漏密钥、SQL、堆栈和内部路径；内部日志保留必要上下文但继续遵守脱敏要求。
- 重试只用于明确可重试故障，并有次数、退避、幂等与超时边界；不能用无限重试掩盖逻辑错误。

## 六、依赖方向与副作用要可控

- 核心业务规则不要直接依赖 UI、HTTP 框架、数据库驱动或第三方 SDK 的具体细节；通过项目现有边界/适配层隔离易变依赖。
- 不为了“依赖倒置”机械新增接口；只有存在真实替换、测试或边界价值时抽象。
- 避免隐藏的全局可变状态、隐式单例、副作用构造器和导入即执行的重要业务逻辑。
- 时间、随机数、外部服务、文件系统、网络等影响可测试性的依赖，按项目现有方式提供可替换边界。
- 公共工具不能偷偷写数据库、发消息或改全局状态；副作用名称和调用位置要显眼。

## 七、数据结构与复杂度要有意识

- 根据访问方式选择结构：频繁查找/去重优先合适的 Map/Set/索引，不为方便反复线性扫描大集合。
- 写循环、嵌套查询、批处理、树/图遍历时判断数量级；明显热路径避免无意的 O(n²)、N+1 查询和重复序列化/解析。
- 不为小数据提前微优化；性能规则仍以真实测量为准。
- 大数据、分页、流式处理、并发任务要考虑内存上限、背压、超时、取消和资源释放。
- 并发代码必须说明共享状态、竞争条件、锁/原子边界、顺序要求和幂等策略；“本地测试没撞上”不算正确。

## 八、让代码天然可测试

- 纯计算逻辑和副作用边界尽量分开，使关键业务规则可以独立测试。
- 不把数据库、HTTP、时间、随机、文件系统调用散落进每个分支，导致只能端到端才能验证最小规则。
- 新增重要分支时至少考虑成功、关键失败、边界值和重复调用；已有测试风格优先沿用。
- 测试固定对外行为和业务不变量，不把私有实现细节锁死到无法重构。
- 不能为了让测试好写而改变生产行为；必要的可测试性改造也要保持原契约。

## 九、注释是维护契约，不是逐行翻译

**写代码时需要注释，但注释必须解释代码本身无法可靠表达的内容。** 默认遵循项目现有语言和注释风格；项目没有约定时，业务说明优先中文，协议字段、标准术语、标识符保持原文。

以下情况原则上必须有就近注释或语言惯用的 doc comment：

- 非显而易见的业务规则、历史兼容原因、状态机限制和“为什么不能简化”的逻辑。
- 金额/精度/舍入、时区、单位换算、排序稳定性、边界值等容易被后人误改的约束。
- 并发、锁、幂等、重试、事务、补偿、缓存一致性和副作用顺序。
- 安全、权限、签名、加密、回调校验、外部协议或第三方平台的特殊要求。
- 为兼容旧客户端/旧数据/上游 Bug 而保留的看似多余分支，注明保留原因和安全删除条件。
- 性能上反直觉但有证据的写法，注明约束或测量依据。
- 公开导出的函数、类、组件、Hook、接口在名称和类型不足以表达契约时，说明用途、重要参数、返回/错误、副作用或调用前提。
- 临时 workaround / TODO 如果必须保留，应写明原因、触发条件和移除条件；不能只写 `TODO fix later`。

以下注释禁止滥用：

- `i++ // i 加一`、`if user == nil // 判断用户为空` 这种逐行翻译代码的废话。
- 与代码已经不一致的旧注释；改逻辑时必须同步改注释或删除失效注释。
- 用大段注释解释本应通过命名/拆函数就能表达的混乱代码。
- 在注释里留下密码、Token、真实个人信息、生产数据或敏感内部地址。
- 注释掉的大段旧代码长期留在文件里；有 Git 历史时删除无用死代码，除非项目有明确保留理由。

注释质量检查只有一个标准：**半年后的维护者只看当前代码和注释，能否理解关键“为什么”和不可破坏的约束。**

## 十、重复、常量和配置要有边界

- 两段代码只是表面相似但业务变化原因不同，不强行抽象；真正同一业务规则重复时应收敛到单一来源。
- 魔法数字/字符串如果承载业务或协议含义，提升为有名称的常量、枚举或配置；局部显而易见的 `0/1` 不机械常量化。
- 可运营配置继续按 `configuration-localization.md`：运行时需要调整的业务参数优先后台管理，部署基础设施用 Secret/.env，真正代码不变量留代码。
- 不把所有值都配置化，也不把安全边界交给可随意编辑的自由文本。

## 十一、提交前做代码工艺自检

对本次修改范围逐项检查，不做无关全仓整改：

1. 能否从命名和结构看懂主流程，是否存在明显巨型函数/组件或深层嵌套。
2. 新增公共契约、状态、错误和副作用是否清楚，旧兼容是否保持。
3. 是否出现新的 `any`/裸字符串/魔法数字/复制业务规则，若存在是否有合理原因。
4. 复杂度、数据库访问、循环和并发是否存在明显数量级问题。
5. 关键“为什么”是否有必要注释，注释是否与实现一致；是否存在废话注释或被注释掉的死代码。
6. 是否能对关键逻辑做定向测试，错误路径和边界条件是否覆盖。
7. 每个 diff 是否都能对应当前需求、兼容适配或必要工程改造；无关“顺手优化”必须移除。

## 十二、保持务实，不把科班变成仪式

专业代码不是设计模式越多越好。一个清楚的函数优于五层抽象，一个明确的数据结构优于通用框架，一个必要注释优于满屏注释。小改保持小，复杂问题才使用相应复杂度；优先让下一位维护者更容易正确修改，而不是让代码看起来“高级”。
