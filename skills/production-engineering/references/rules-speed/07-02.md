
### 2. 模块化与文件体量

禁止为了快速完成，把多个不同功能、不同业务概念、不同层级职责集中塞进一个大文件。

解耦的目标是降低不同职责之间的相互影响，不是为了增加文件数量；只有不同功能、不同业务概念、不同层级职责互相缠绕时才需要拆分。

写代码前必须阅读当前项目真实结构，判断：

- 路由、页面、组件、状态管理、业务服务、数据库访问、外部 API 客户端、类型定义、工具函数、测试分别放在哪里。
- 当前要写的代码属于哪个单一职责或功能闭环。
- 当前任务是应该落到已有模块，还是需要新增模块。
- 是否会把不同功能、不同业务概念、不同层级职责混进同一个文件。
- 项目是否已有分层习惯，必须优先沿用现有习惯。

行数只是风险信号，不是唯一拆分标准：

- 普通业务文件、组件文件、页面文件建议不超过 300 行。
- 复杂页面、复杂服务、复杂状态模块超过 400 行必须评估职责是否仍然单一。
- 任意手写源代码文件超过 600 行，视为高风险信号，必须重点检查是否混入不同功能或不同层级职责。
- 单次修改让某个手写源代码文件新增超过 300 行时，必须停下来评估职责边界。
- 禁止产出 1000 行以上多功能混杂型手写业务大文件。
- 不得为了满足行数阈值机械拆分；如果代码仍是一个清晰功能闭环，拆分会造成大量参数透传、上下文跳转或维护成本上升，可以保留，并说明职责仍然单一。

出现以下情况，必须拆文件或拆函数：

- 一个文件同时包含路由注册、权限判断、业务规则、数据库查询、外部请求和响应拼装。
- 一个前端文件同时包含页面布局、弹窗、表单校验、接口请求、状态管理、复杂样式和多个大组件。
- 同一文件里出现 3 个以上彼此独立的业务概念。
- 同一文件里同时实现多个互不依赖的功能入口。
- 为了完成新需求需要不断向文件底部追加代码。
- 新增代码里出现大量重复片段、重复表单、重复请求、重复校验、重复状态处理。
- 文件已经让人难以快速定位入口、数据流、错误处理或测试点。

可以不拆的情况：

- 代码属于同一个功能闭环。
- 拆出去后只会产生大量参数透传、回调转发、上下文跳转，反而降低可读性。
- 文件虽然偏长，但内部只有一个入口、一个主流程、一个业务概念，分段清楚，测试点明确。
- 大部分行数来自同一职责下的配置、字段定义、校验规则、映射表或 UI 片段。

函数规范：

- 单个函数超过 80 行时必须评估复杂度。
- 如果函数包含多个独立业务阶段，优先拆成小函数。
- 如果函数只是同一个线性流程，拆分会打断阅读，可以保留，但必须用清晰命名、局部分段、早返回或小辅助函数控制复杂度。
