
## 八、后端实现规范

必须先识别并沿用项目现有后端架构及其职责边界。Router、Controller、Service、Model、Repository、DAO、DTO、Validator、Client 只是常见职责名称，不要求项目必须同时具备这些层，也禁止为了满足清单新增没有实际价值的空壳层。

当项目采用对应分层或当前复杂度确实需要时，职责边界参考如下：

- route/router：只负责注册路由和绑定中间件。
- controller/handler：只负责请求接入、参数校验、调用 service、返回响应。
- service：负责业务编排、事务边界、权限业务判断、状态流转和幂等控制。
- model/entity：负责数据结构定义。
- repository/dao：负责数据库查询和持久化。
- dto/request/response：负责请求和响应类型。
- validator：负责复杂输入校验。
- client/provider：负责第三方服务调用。
- middleware：负责鉴权、限流、上下文注入等横切逻辑。
- utils/helpers：只放通用无业务副作用工具函数。

后端禁止：

- Controller / Handler 直接写复杂业务逻辑。
- Controller / Handler 直接拼 SQL 或直接操作数据库，除非当前项目架构明确如此且无法安全调整。
- Service 处理 HTTP 请求对象和响应对象，除非当前框架约定如此。
- Repository / DAO 中混入角色判断、权限判断、状态流转和第三方调用。
- 把核心业务逻辑藏进 utils、helpers、common 这类模糊目录。
- 为了赶进度复制粘贴相同业务逻辑。
- 新增一个巨大文件承载完整功能。

后端必须：

- 输入必须校验。
- API 输出必须按数据敏感级别脱敏。
- 密码、token、密钥、验证码、私钥、Cookie、Authorization、支付凭证等禁止返回。
- 错误响应不得返回数据库错误、堆栈、第三方完整响应、内部路径、环境变量、密钥片段。
- 错误必须可追踪。
- 禁止空 `catch`、忽略 Promise/异步错误、记录错误后仍返回成功，或用默认值静默掩盖关键失败。
- 重试必须有次数、退避和可重试条件，禁止无限重试或对非幂等写操作盲目重试。
- 事务必须有失败日志和回滚处理。
- 安全关键逻辑必须有明确权限判断和测试覆盖。
- 禁止新增隐藏入口、隐藏参数、万能口令、调试后门。
