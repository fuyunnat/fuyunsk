
### 6. 远端操作风险边界

本规范在满足前述 GitHub 交付条件时要求“测试通过后提交并推送 GitHub 任务分支”，但只能推送当前任务分支，不能理解为允许任意远端操作。

完整通道且远端预检通过后，允许自动执行的远端操作：

- 从稳定主线创建任务分支。
- 测试通过后推送当前任务分支。
- 更新当前任务分支上的当前任务提交。
- 为当前任务分支创建或更新一个 Pull Request。
- 读取当前任务 PR 和 CI / Actions 的状态与失败日志。

首次远端写入前必须执行预检：

- 确认 GitHub 仓库所有者、仓库名、远端 URL、写入远端、PR base/head 和仓库可见性（public/private/internal）。
- 对 fork 工作流，必须明确任务分支推送到个人 fork，PR 指向正确的上游仓库和稳定主线。
- 再次检查待推送 commit、文件列表、敏感信息、大文件和计划外改动。
- 如果目标仓库是公开仓库，或可见性无法确认，并且代码、配置、业务逻辑可能包含内部或敏感信息，必须停止推送并等待用户确认。
- 完整通道的普通低中风险任务在预检通过后可以按本规范自动推送任务分支和创建 PR，但必须在操作前给出简短预告；快速通道按最小交付执行，高风险任务仍需明确确认。

必须额外等待用户确认的远端操作：

- 直接推送 `main`、`master`、`production`。
- 合并 Pull Request。
- 删除远端分支。
- 强制推送。
- 覆盖远端历史。
- 修改 GitHub 仓库设置、Actions secrets、Deploy keys、Webhook、Branch protection。
- 修改生产部署分支、发布分支或线上环境配置。

完整通道的普通功能、普通修复、普通文档变更，在测试通过后可以自动提交并推送任务分支；快速通道的小改不默认推送。

涉及数据库、生产配置、密钥、支付、余额、订单、鉴权、权限、安全策略、CI/CD、部署流程的高风险任务，即使只是推送任务分支，也必须先说明风险、测试证据、回滚方式，并等待用户确认。
