
## 二十、测试、验证与质量证据

交付前必须尽可能执行项目已有验证：

- lint
- typecheck
- unit test
- build
- API smoke test
- 页面访问验证
- 数据库 migration 验证
- 安全相关单元测试或集成测试
- 权限边界验证
- 漏洞修复复现验证

验证证据必须按任务通道和风险裁剪。快速通道只需要能证明本次局部改动正确的最小证据，例如 diff、关键词检查、局部命令、局部页面检查或输出文件检查；完整通道、中高风险任务、共享模块、生产相关、安全相关和需要提交推送的任务，才展开完整验证和回归证据。

验证结果必须按适用性明确写出；快速通道不涉及安全、权限、CI 或复杂失败场景时，不需要强行汇报这些项目：

- 执行了什么命令。
- 成功还是失败。
- 失败是否与本次改动有关。
- 是否存在剩余风险。
- 涉及时，哪些安全边界已经验证。
- 涉及时，哪些安全边界没有条件验证。

如果无法执行，必须说明原因，不得假装已测试。

质量证据必须具体：

- 不能只写“已测试”“流程没问题”“构建正常”。
- 必须贴出关键命令和结果摘要。
- 必须说明本次功能的成功路径如何验证。
- 必须说明失败路径如何验证。
- 涉及时，必须说明权限不足、未登录、参数错误、资源不存在等边界是否验证。
- 涉及时，必须说明是否检查 GitHub CI / Actions。
- 涉及时，必须说明 CI 通过、失败、未配置或无法访问。

回归证据必须具体：

- 必须说明修改前确定了哪些改动边界和必须保持不变的行为。
- 必须说明修改后重新执行了哪些已有测试、旧接口、旧页面或旧业务流程。
- 修改共享代码时，必须列出已检查或验证的主要使用方。
- 必须说明是否发现计划外文件、意外格式化、批量改写或无法解释的差异。
- 必须说明哪些关联功能因缺少环境、账号、数据或服务无法完成回归验证。
- 没有完成对应回归验证时，禁止写“未影响其他功能”“完全兼容”“没有回归”。

测试完整性与环境安全：

- 修复 bug 时，只要项目具备合适测试基础，就必须补充能够复现原问题的回归测试。
- 禁止为了让检查通过而删除测试、跳过测试、弱化断言、降低覆盖率门槛、关闭 lint/typecheck、扩大 ignore、滥用 `any` 或吞掉错误。
- 禁止未核对差异就批量更新 snapshot、golden file、fixture 或基准结果。更新这些文件时必须说明行为为什么应该改变。
- 修改测试代码时必须确认生产实现确实正确，禁止只改测试去迎合错误实现。
- 测试优先使用本地、测试环境、mock、sandbox、合成数据或专用测试账号。
- 禁止测试过程中触发真实支付、真实扣费、真实短信、真实邮件、真实推送、真实用户操作、真实生产回调或不可逆外部副作用。
- 执行 API smoke test、迁移或脚本前必须确认目标环境、数据库和服务地址，防止误连生产。
- 测试产生的临时数据、进程、容器、文件和账号必须按项目规则清理；不得删除用户原有数据。
- 遇到 flaky test 时必须记录失败和重试情况，分析是否与本次改动有关，禁止通过无限重试掩盖不稳定。

如果需要用户手动验收，必须给出可复制步骤：

- 打开哪个页面或调用哪个接口。
- 使用什么测试账号、测试数据或参数。
- 点什么按钮或执行什么命令。
- 预期看到什么结果。
- 如何确认失败场景正常。
- 如何确认权限和安全边界没有被破坏。
