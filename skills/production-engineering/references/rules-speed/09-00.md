
## 九、前端实现规范

二开已有项目时，必须跟随当前项目真实前端技术栈和目录结构，不得擅自迁移。

新建后台页面、管理端、配置页或运营后台，且用户没有指定其他技术栈时，默认优先以下选型，但只安装当前功能实际需要的依赖：

- 基础：Vue 3 + Vite，使用包管理器可解析的兼容稳定版本，并锁定依赖版本；只有用户要求最新版本或版本选择会影响交付时，才需要额外查证最新版本。
- UI 组件：Ant Design Vue。后台页面优先使用其表格、表单、弹窗、抽屉、菜单、分页、提示和状态组件，避免重复手写基础控件。
- 状态管理：Pinia。只有存在明确跨页面、跨模块或后台全局状态时才使用，局部状态优先放在页面或组件内。
- 路由：Vue Router。有多页面、菜单导航、详情页或后台权限路由需求时使用。
- 代码形态：普通 `.vue` / `.js`，不是 TypeScript 项目；不得为了套默认选型把后台项目改成 TypeScript。
- 请求：优先项目现有封装；新项目需要统一拦截、鉴权刷新、取消请求或错误处理时使用现有请求方案或轻量封装，否则原生 `fetch` 也可以。
- CSS：优先沿用 Ant Design Vue 和项目已有样式体系；只在必要时补充少量可维护的局部样式。
- 动画：只有真实交互需求时才引入动画库，禁止仅为装饰安装动画依赖。
- 图标：优先使用 Ant Design Vue 生态中已启用的图标方案；项目没有图标方案且确有需要时，再选择轻量图标方案。

普通用户端页面、营销页、独立工具或非后台前端，如果用户没有指定技术栈，应先结合项目真实上下文选择最小可维护方案，不强制套用后台页面栈。

禁止把上述推荐理解为必须安装的依赖清单，也禁止在提示词中长期锁死可能过期的具体大版本。

前端通用交付原则：

- UI 是一级交付要求。前端任务不能只满足“功能能用”；视觉质量、交互细节、一致性、状态完整性和响应式可用性都属于完成标准。
- 实现页面前必须理解产品用途、信息层级、用户主要操作、已有视觉语言、Design System、组件体系、页面密度和桌面/移动端使用场景。
- 禁止把页面简单做成“几个 Card 加几个 Button”；后台和管理端应优先信息密度、扫描效率、批量操作、状态识别和错误恢复，用户端应优先清晰路径和低学习成本。
- 禁止默认使用到处渐变、毛玻璃、巨大圆角、过量阴影、高饱和随机颜色、无意义动画、巨大 Hero、过量留白、装饰性图标堆砌或随机紫蓝渐变来制造所谓高级感。
- UI 风格必须来源于产品定位、已有 Design System、用户任务、信息结构和状态语义，而不是 AI 临时发挥。

前端 UI 决策优先级：

1. 项目现有 Design System。
2. UI Framework 官方能力。
3. Theme / Design Tokens。
4. 官方 Styling API。
5. 业务组件封装。
6. Tailwind、class、CSS Modules、局部样式等外围调整。
7. 直接 CSS 强制覆盖。

使用 UI 组件库时：

- 一旦项目使用 HeroUI、Radix、shadcn/ui、MUI、Ant Design、Ant Design Vue 等组件系统，组件框架负责组件自身视觉和交互，业务样式主要负责页面布局与业务组合。
- 定制组件优先使用组件官方 API，例如 variant、color、size、radius、appearance、orientation、placement、disabled、loading 和官方 props。
- 全局品牌调整优先使用 Theme Provider、CSS Variables、Design Tokens、官方 theme 配置或全局组件主题。
- 只有官方 API、主题和官方暴露的样式入口无法满足需求时，才使用局部 CSS、class、Tailwind 或样式模块调整组件视觉。
- 使用框架特殊能力前，必须先通过 `package.json`、lockfile、类型定义、项目现有写法或对应版本官方文档确认当前版本 API；不得把其他版本文档或记忆中的旧 API 直接套用。
- 不得习惯性重新定义 Button、Input、Select、Modal、Table 等组件的完整视觉；如果大部分组件都需要完全覆盖，应重新判断是否该定制主题、封装项目级 variant、继续使用该 UI Library 或改用 headless component。

Tailwind / class / CSS 使用边界：

- Tailwind、class、CSS Modules 或局部 CSS 主要用于布局、Grid/Flex、Gap、Padding/Margin、Responsive、页面级视觉组合和自定义业务组件。
- 它们不是绕过 Design System 或 UI Component Library 的工具。
- 优先使用项目已有 spacing scale、color tokens、radius、typography、breakpoint 和样式工具。
- 减少无设计依据的 arbitrary values，例如 `w-[437px]`、`mt-[17px]`、`rounded-[13px]`、`text-[15.5px]`。
- 大量重复样式应考虑提取组件、variant、utility function、样式函数、局部样式模块或项目已有 `cn` / CVA / tailwind-variants 等工具；但不要为了两个简单元素过度抽象。

二开已有项目时：

- 必须先识别真实前端技术栈。
- 必须跟随当前项目的框架、构建工具、路由、状态管理、请求封装、CSS 方案和组件体系。
- 禁止擅自替换 UI 组件体系、CSS 方案、路由方案或状态管理方案。
- 禁止为了套用默认选型而迁移现有项目。
- 只有用户明确要求迁移时，才可以提出迁移方案。

前端职责边界：

- page：页面入口，只负责组合模块和接入页面级状态。
- components：展示组件和局部交互组件。
- composables/hooks：状态、副作用、查询参数、表单状态等可复用逻辑。
- services/api：请求封装。
- types：类型定义；非 TypeScript 项目可用 JSDoc、字段常量或接口文档表达，简单场景可以不单独建类型文件。
- utils：无业务副作用的通用工具函数。
- constants：常量配置。
- schemas/validators：复杂表单校验规则。
- stores：全局或模块级状态管理；后台 Vue 项目默认使用 Pinia。

前端禁止：

- 把复杂页面写成超大单文件。
- 页面里直接堆接口请求、数据转换、复杂表单逻辑和弹窗逻辑。
- 一个组件同时承担列表、详情、编辑、上传、审核、导出等多个职责。
- 把接口请求散落在页面和组件中。
- 把类型定义、接口封装、表单规则、复杂数据转换全部写在页面文件里。
- 为了快速出效果直接套大型 UI 组件库。
- 引入 Element、MUI、Chakra UI、Naive UI、Arco Design 等大型 UI 库，除非用户明确确认。后台页面按本规范默认使用 Ant Design Vue 时，不属于本条禁止范围。
- 绕开项目样式体系写大量零散内联样式。
- 业务代码散落 `console.log`。
- 在前端存放密钥、管理员 token、后端私有配置。
- 把完整 token、敏感响应、用户隐私打印到控制台或埋点。

前端必须：

- API 请求走统一封装。
- 涉及异步数据的页面必须处理 initial、loading、empty、success、error、retry、disabled、submitting、readonly。
- 涉及身份时必须处理 unauthorized、forbidden、session expired；涉及网络时必要时处理 offline、timeout。
- 用户关键操作失败必须有反馈。
- 新增文案遵守项目 i18n 方案；如果项目没有 i18n，沿用现有文案风格。
- 页面结构清楚、视觉统一、间距稳定、状态完整、响应式可用。
- 后台界面优先信息密度、扫描效率、批量操作、状态识别和错误恢复。

前端布局整洁规整硬要求：

- 页面必须有清晰的信息层级：标题、说明、主操作、次操作、筛选区、内容区、分页、危险操作必须容易区分。
- 页面主轴必须对齐，禁止标题、按钮、筛选框、表格、卡片、分页各自漂浮。
- 同一页面的左右边距、区块间距、表单间距、列表间距必须统一，不能凭感觉随手写不同间距。
- 同类按钮、输入框、下拉框、标签、状态徽标、卡片、表格工具栏必须统一高度、圆角、边框、字号、图标尺寸和 hover / active / disabled 状态。
- 字体系统必须统一：标题、正文、辅助说明、表格文字、按钮文字、标签文字必须有清楚层级，字号、行高、字重、颜色和间距不能混乱；同一语义的文字在同一页面中必须保持一致。
- 按钮必须工整：主按钮、次按钮、危险按钮、文字按钮、图标按钮要有明确优先级；同组按钮高度、间距、图标尺寸、文字长度和禁用/加载状态必须稳定，不能出现挤压、错位、乱换行或主次不清。
- 标签、状态徽标、提示文本、表单 label、单位、前后缀必须对齐且可读；颜色和形状必须表达稳定语义，不能随意新增相近但含义不清的样式。
- 筛选区、操作区、表格区、分页区必须位置稳定，数据变化、加载状态、错误状态、空状态不能导致布局明显跳动。
- 表单必须规整：label、输入框、帮助文本、错误提示、单位、前后缀、按钮区必须对齐；长表单必须分组，禁止一屏无结构堆到底。
- 表单必须关注 Required 状态、Help text、Error text、Placeholder、Disabled、Readonly、Focus、Keyboard、Submit loading 和防重复提交；字段错误应靠近对应字段，不能只用 Toast 表达所有表单错误。
- 表格和列表必须规整：关键列优先，列宽稳定，数字对齐，空值统一，长文本截断或提供 Tooltip/Detail，Loading、Empty、Error、Pagination、Sorting、Filtering、Row actions、Bulk actions 完整，操作列不能随数据变化跳动。
- 手机端不要强行压缩复杂桌面表格，应根据情况改为横向滚动、卡片列表、简化列或详情抽屉。
- 弹窗、抽屉、Popover、确认框必须规整：标题明确，内容层级清楚，关闭行为、Escape、Focus management、Loading、Submit disabled、防重复提交、危险操作确认、小屏滚动和 Footer 可见性都必须处理。
- 优先使用成熟 UI Library 自带的 focus trap、keyboard navigation、ARIA、overlay 和 placement，不要轻易自己重写。
- loading、empty、error、success、disabled、readonly、permission denied、offline、timeout、登录失效、提交中、局部刷新必须有一致的 UI 表达。
- 响应式必须真实可用：桌面、普通笔记本、平板、手机宽度下不得出现明显错位、遮挡、横向溢出、文字挤压、按钮错行、弹窗超出屏幕。
- 移动端不能只是缩小桌面端；必要时表格改成横向滚动容器、卡片列表、折叠筛选或底部操作栏。
- 不得用随机渐变、随机阴影、随机毛玻璃、随机高饱和颜色、随机动画掩盖布局问题。
- 后台、管理端、配置页禁止做成营销落地页风格，必须优先信息密度、可读性、批量操作效率和错误恢复。
- 文本必须可读，颜色对比度必须足够，字号和行高不能过小过挤，按钮文字不能溢出。
- 图标按钮必须有 tooltip 或 aria-label，焦点态必须可见，不能只靠颜色表达状态。
- 无障碍不得被破坏：Keyboard navigation、Focus visible、ARIA、Label association、Escape behavior、Screen reader semantics 必须尽量沿用组件库能力；状态不能只靠颜色区分，文本和背景必须有足够可读性。
- 如果同一类 UI 已出现明确共享契约、跨页面复用价值或第三次重复，必须优先复用项目已有组件或抽成局部组件；两处仅外观相似但业务语义不同的实现，不得为了形式统一强行抽象。
- 样式命名和条件样式必须可维护；重复长 class/className、复杂条件样式、跨页面复用样式，应抽成组件、样式函数、常量、局部样式模块或项目已有样式工具。

前端视觉验收必须检查：

快速通道只检查受影响区域及其相邻布局；完整通道、后台页面新增、复杂页面改动或共享组件改动才需要展开完整视觉验收。

- 桌面宽屏。
- 普通笔记本宽度。
- 平板宽度。
- 手机宽度。
- 页面是否对齐。
- 间距是否一致。
- 重复组件是否统一。
- 文字是否溢出。
- 表单 label、输入框、错误提示、按钮区是否对齐。
- 表格列宽、状态、空值、操作列、分页、筛选是否稳定可用。
- 弹窗和抽屉是否可滚动。
- 底部操作是否被遮挡。
- Hover、Focus、Keyboard 和禁用/提交中状态是否正常。
- loading、empty、error、disabled、权限不足、登录失效状态是否完整。
- 是否存在横向溢出、按钮换行错乱、表格压扁不可读、文字挤压、遮挡、错位、跳动、风格不统一。
- 管理后台是否保持信息密度和快速扫描能力，用户端页面是否保持清晰路径和低学习成本。

如果无法运行或截图，必须明确说明未完成前端视觉验收，并列出剩余风险。
