# 配置化优先与前台多语言

本规则用于避免把本应运营配置、后台维护或国际化的数据写死在代码中。目标是：**能运行时配置的优先配置化；真正启动级基础设施留在部署配置；前台默认按多语言友好方式实现。** 不为了“可配置”把所有常量都搬进后台，也不为了省事把经常变化的业务参数硬编码。

## 一、先判断它属于哪一类

新增配置前先判断真实生命周期，而不是机械地全部塞进 `.env` 或全部塞进后台：

1. **启动级基础设施**：应用在数据库/后台配置系统可用之前就必须知道的值，优先使用 `.env`、部署平台 Secret 或等价秘密管理。典型包括应用自身的 MySQL、Redis 连接、监听端口、部署环境标识、用于解密后台秘密的主密钥等。
2. **运行时业务/运营配置**：运营人员可能需要修改，而且修改后不应重新构建或发布程序，优先通过后台配置并持久化。
3. **协议常量、安全边界、内部不变量**：确实属于代码契约的值保留在代码，不为了“后台可配”降低安全或让核心规则可随意修改。
4. 项目已有成熟配置中心、Secret Manager、后台配置模块或多语言方案时优先沿用，不重复造第二套。

## 二、能后台配置的，不默认写死

以下内容只要项目架构允许运行时修改，默认优先做后台配置，而不是散落硬编码或无必要塞进 `.env`：

- SMTP 主机、端口、发件人、账号、启停和发送策略。
- 支付、短信、对象存储、Captcha、地图、推送、AI、第三方 API 等供应商配置和密钥。
- 网站名称、Logo、客服信息、SEO、公告、Banner、页脚、联系方式等运营内容。
- 功能开关、业务比例、额度、次数、展示规则、模板、国家/地区、币种等确实会运营调整的业务参数。
- **同步/轮询/刷新/清理/重算/对账等后台任务的执行间隔、业务重试次数、保留天数、批量大小、阈值、限额、比例和业务超时时间**，只要管理员有合理调整需求，就按运行时配置处理，不能把 `5 * 60`、`30`、`100` 等值散落在调度器或业务代码里。

“优先后台配置”不是强制所有项目都新建配置中心。先检查当前项目是否已有设置表、配置服务、后台设置页、缓存刷新和权限模型；能复用就复用。一个永远不会变、又属于内部实现的值不必为了形式主义做成后台字段。

## 三、业务硬编码门禁：写代码前先给每个值定身份

只要本次实现新增或修改了**带业务含义的字面量、默认值、阈值、间隔、次数、比例、容量、金额、时间长度或文本标识**，写入生产代码前必须先判断它属于哪一类：

1. **运行时可运营值**：管理员/运营可能修改，且修改不应重新发版。必须接现有后台配置/配置中心，业务代码读取统一配置源。
2. **部署值**：不同环境可能不同，但运行期间不由运营修改。放部署 Secret / `.env` / 平台配置。
3. **代码不变量**：协议标准、安全底线、算法定义或真正不应被运营修改的内部约束。可以留在代码，但必须用清楚的命名常量/类型表达；非显而易见原因按 `code-craft.md` 注释“为什么不能配置”。
4. **局部实现细节**：如数组起始索引、显而易见的 `0/1`、只影响局部算法且没有业务语义的值，可以直接保留，不做无意义配置化。

**没有完成分类前，不允许为了赶进度先写一个数字再说以后配置化。** 如果需求里出现“后台可设置、全局参数、管理员配置、以后可调整、同步频率、刷新频率、间隔、阈值、额度、比例、重试次数、保留天数”等表述，应默认进入第 1 类，除非源码证据表明它是协议/安全不变量。

### 默认值可以存在，但只能有一个权威来源

运行时配置通常仍需要默认值；“禁止写死”不是禁止默认值，而是禁止**多个隐藏默认值**：

- 默认值集中在配置定义/迁移/配置服务的一个权威位置，业务执行代码不得再复制一个同义字面量。
- 读取顺序必须明确，例如 `后台值 → 兼容旧配置 → 集中默认值`；不能调度器一套、后台表单一套、API 校验又一套。
- 最小值/最大值如果是安全或业务边界，可以作为命名约束集中定义；不要在前端、后端、任务代码分别散落 `1`、`1440` 等同一边界。
- 如果后台页面显示“默认 5 分钟”，调度器就必须通过同一个配置键得到 5 分钟，而不是自己再写 `300` 秒。

### “可配置”必须真的控制运行行为

不能只做一个后台输入框而运行逻辑仍使用旧常量。新增/迁移运行时配置时至少核对：

- 配置键、存储位置、类型、单位、默认值、合法范围、权限和审计。
- **实际消费方**是谁：调度器、任务、API、页面或服务必须从统一配置读取。
- 修改后的**生效语义**：立即生效、下一轮任务生效、缓存刷新后生效，还是明确需要重启。若用户要求运行时可调，不能偷偷只在进程启动时读取一次。
- 多实例/多进程时缓存如何失效或同步，不能出现 A 实例 5 分钟、B 实例 10 分钟的长期漂移。
- 无效值、读取失败和配置缺失时的 fallback 行为必须确定，不得静默退回散落硬编码。

涉及周期任务时，优先让任务在每轮调度边界读取当前有效配置，或使用项目现有动态重调度机制；不要为了“即时生效”重复注册任务或产生并发双跑。

### 写完代码必须做一次硬编码扫描

对本次 diff 和受影响调用链搜索新引入的业务数字/字符串及旧默认值，确认：

- 同一业务参数没有在多个文件复制；
- 后台配置实际被消费；
- 旧硬编码只作为明确兼容 fallback 时才暂留，并有迁移/删除条件；
- 不能用“提取成 `const DEFAULT_SYNC_MINUTES = 5`”冒充配置化——如果它本质是运营值，命名常量仍然是硬编码，只能作为集中 fallback。

## 四、SMTP 和第三方密钥可以后台配，但必须安全

后台管理敏感配置时：

- Secret/API Key/SMTP 密码必须**加密存储**，不能明文落库；用于解密这些秘密的主密钥不能再放在同一数据库里，优先来自部署 Secret / `.env` / KMS。
- 后台读取接口不得返回完整秘密；页面只显示脱敏值，修改时重新输入或采用明确的保留旧值语义。
- 配置修改必须有最小权限控制和审计记录；支付、短信等高风险供应商配置按项目现有高风险规则执行。
- 有条件时提供“测试连接/测试发送/验证凭据”，验证通过再启用；修改失败要能回退到上一份有效配置。
- 日志、错误信息、请求追踪和审计日志不得记录完整密码、Token、Cookie、私钥或第三方 Secret。

若某第三方能力本身就是应用启动前的硬依赖，或者后台配置存储在不可用时无法启动，则可以使用部署 Secret；不要为了遵守“后台配置”制造启动死锁。

## 五、从 `.env`/硬编码迁到后台时必须兼容

已有项目不能一刀切：

1. 先确认旧值来源和现有使用方。
2. 新增后台配置读取后，明确“后台值 / 旧 `.env` / 默认值”的优先级和 fallback；不能出现两边同时存在却行为随机。
3. 迁移期间旧 `.env` 或旧配置继续可用，直到新配置已保存、验证并稳定运行。
4. 真正删除旧环境变量、旧字段或旧读取逻辑属于单独清理阶段，继续遵守 `behavior-preservation.md` 的兼容优先原则。

## 六、前台默认多语言友好

用户面向的前台在**新建、重写或新增功能**时，除非用户明确要求单语言或正在做严格原样迁移，默认按多语言友好方式实现；后台管理端本身不自动要求多语言，但涉及前台内容管理时应支持维护各语言内容。

- 静态用户可见文案优先进入项目现有 i18n/locale 体系，使用稳定翻译 key；不要在组件、模板、JS/TS 中散落中文/英文硬编码，也不要大量写 `lang === 'en' ? ... : ...`。
- 有默认语言和 fallback 语言；语言切换遵循项目现有 URL、账号偏好、本地存储或浏览器策略，不擅自重做路由。
- 日期、时间、数字、货币、百分比按 locale 格式化；品牌名、型号、代码、订单号等不应被误翻译。
- 后端返回的公告、Banner、商品描述、文章、SEO 等动态内容如果本次功能确实要求多语言，优先使用项目已有翻译表/本地化字段/内容模型；不要简单把某一种语言永久写死成唯一字段。
- 旧项目只有单语言内容时，该旧内容作为默认语言/fallback 保持可读；新增语言不能让旧数据变空或旧页面报错。
- 不自动机器翻译用户内容并写回数据库，除非用户明确要求并有审核机制。

## 七、验证

涉及配置化时至少验证：

- 默认值和旧配置 fallback；
- 后台保存/读取、权限、秘密脱敏、无效配置和回滚；
- **把一个运行时业务参数改成非默认值后，真实消费方按约定时机采用新值**；如果承诺无需重启，必须实际证明不重启也生效；
- 重启后配置仍存在且行为一致；多实例场景按项目能力验证或明确未验证；
- 搜索本次影响范围，确认没有第二份同义硬编码继续控制行为。

涉及前台多语言时至少检查默认语言、另一种语言、fallback、长文本、日期/金额格式，以及切换语言后核心功能和路由不丢状态。

“代码里没有常量”不等于配置设计正确；“后台出现输入框”也不等于运行逻辑已经配置化；“能切换语言”也不等于动态内容、格式化和旧数据已经兼容。
