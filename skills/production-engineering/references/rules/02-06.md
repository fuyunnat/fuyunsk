
### 6. 上下文续航与任务状态记录

完整通道、长任务、跨多文件任务、分阶段开发、需要提交/推送/部署的任务，不能只依赖聊天上下文记忆。必须把关键状态落到可读取的任务状态快照中，防止上下文压缩、模型切换、任务中断或继续开发时遗忘关键约束。

默认做法：

- 默认在当前工作区维护 `work/task-state.md`；如果项目已有等价任务记录文件，可以沿用，但必须说明路径。
- 任务状态快照不是最终报告，也不是 Git 替代品；Git 负责代码版本、审计和回滚，任务状态快照只负责 AI 任务记忆、断点恢复和约束保留。
- 如果状态文件放在 Git 仓库内，必须明确它是否应该提交；默认不得混入业务提交，除非项目明确要求或用户明确要求把任务记录纳入交付。
- 状态文件只记录任务恢复所需信息，禁止记录密钥、token、密码、隐私数据、完整敏感日志、真实用户数据、生产凭证或可复原的敏感配置。

任务状态快照至少记录：

- 当前用户目标和最新明确要求。
- 当前任务模式：只读、实现、安全审计或高风险。
- 当前任务通道：快速通道或完整通道，以及选择原因。
- 已确认的项目入口、技术栈、运行命令和验证命令。
- 已做决策、选择原因、拒绝或暂缓的方案。
- 已修改文件、计划修改文件和不得触碰的文件。
- 已执行命令和结果摘要。
- 当前 Git 分支、稳定点、用户已有改动、本次改动边界。
- 已完成事项、仍待完成事项、阻塞点、风险和禁止操作。

触发规则：

- 任务开始前：完整通道、中高风险、长任务、多阶段任务、跨多文件任务、需要提交/推送/部署的任务，必须先创建或更新状态快照。
- 修改代码前：记录当前 Git 分支、稳定点、用户已有改动、本次计划修改文件和不得触碰范围。
- 每完成一个阶段后：记录已修改文件、已完成内容、验证命令、结果摘要、下一步和剩余风险。
- 提交、推送、创建 PR、部署前后：记录 commit、分支、PR、CI、部署目标、回滚方式和未覆盖风险。
- 任务完成时：把状态标记为完成，并记录最终交付、验证证据、回滚方式和未覆盖风险。
- 快速通道默认不创建任务状态快照；但只要任务开始变长、跨多个阶段、出现中断风险，或用户要求“最稳”“别忘了”“继续开发”，必须立即创建或更新。
- 发生上下文压缩、任务中断、模型切换、继续开发或用户询问“现在做到哪了”时，必须先读取任务状态快照、真实文件内容、Git 状态和当前 diff，再继续或汇报。
- 如果状态快照与用户最新要求、真实文件内容、Git diff 或线上只读证据冲突，必须以真实当前状态和用户最新要求为准，并说明冲突；不得按过期快照继续执行。
