
### 7. Pull Request 与团队协作要求

完整通道推送任务分支后，如果仓库支持 Pull Request，并且具备 GitHub CLI、API 或页面操作能力，默认创建或更新当前任务的 PR；如果没有相应能力，必须准备可直接复制的 PR 标题、描述和创建步骤，不得假装已创建。快速通道只有在用户要求、仓库协作需要或任务进入评审状态时才创建 PR。

PR 创建要求：

- base 必须是已确认的稳定主线，head 必须是当前任务分支。
- 一个任务分支对应一个 PR；后续修复继续更新同一个 PR，禁止重复创建多个同义 PR。
- 本地验证已完成且准备评审时创建普通 PR；仍明确需要早期讨论或用户要求草稿时创建 Draft PR。
- 创建前必须再次检查 `base...head` 的文件列表和差异，确认 PR 没有混入其他功能、用户改动或计划外提交。
- PR 标题必须清楚表达任务结果，并与提交内容一致。
- 仓库没有明确英文要求时，PR 标题和描述默认使用中文，让用户能直接看懂修复、新增和影响范围。
- 最终交付必须提供 PR 链接；无法创建时提供分支链接或明确说明阻塞条件。

合并主线的判断：

- 只有用户明确说“合并 PR”“合并到主库”“合并到 main/master/production”或仓库维护者在平台上完成合并时，才进入合并主线流程。
- 用户只说“提交”“推送”“上传仓库”“保存到 GitHub”，默认不是合并主线。
- 合并前必须确认 PR 分支只包含当前任务改动、必要验证通过、CI 状态已检查、目标主线正确、没有敏感信息和无关文件。
- 如果用户要求合并但验证失败、CI 失败、影响范围不清、存在用户未审 diff、涉及高风险变更或主线保护规则不清，必须说明原因并等待进一步确认，不能机械合并。
- AI 未经明确授权不得自动点击 GitHub Merge、不得直接推主线模拟合并、不得用强推或改历史绕过评审。

PR 描述必须包含：

- 修复了什么问题，原来的表现是什么。
- 新增了什么功能或能力。
- 主要修改了什么代码、页面、接口、配置或数据库内容。
- 本次提交包含哪些核心改动。
- 为什么改。
- 影响范围。
- 哪些原有行为明确保持不变。
- 测试命令和结果。
- 手工验证流程。
- 前端截图或页面验证结果，如果涉及前端。
- API 请求和响应示例，如果涉及后端接口。
- 数据库影响。
- 部署影响。
- 鉴权、权限、安全边界影响。
- 回滚方式。
- 剩余风险。

PR 规则：

- 一个 PR 只包含一个清晰任务或一组强相关改动。
- 禁止把多个无关功能塞进同一个 PR。
- 禁止把临时文件、日志、缓存、构建产物、密钥、本地配置放进 PR。
- CI 未通过不得标记为完成。
- 未经用户明确要求，不得自动合并 PR。
- 未经用户明确要求，不得自动删除远端分支。
- 合并方式必须跟随仓库现有约定或分支保护规则，禁止自行决定 squash、rebase 或 merge。
- PR 合并后需要清理分支时，必须先确认已合并、稳定点可恢复，并取得用户授权。
- 已合并改动出现问题时，默认通过 revert 对应 commit 或 PR 回滚，禁止通过强制推送改写共享历史。
