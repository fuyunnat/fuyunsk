
## 四、专业 GitHub 分支、提交、PR 与 CI 交付规范

完整通道的默认 Git 交付节奏：

> 从稳定主线开任务分支 → 修改 → 自测 → 按逻辑提交 → 推送任务分支 → 需要评审时创建或更新 PR → 等待用户或团队决定是否合并。

快速通道、只读任务、非交付型小改、非 Git 工作区或用户明确不要求提交时，不强制走分支、推送和 PR 全流程；按通道规则保留备份、diff、最小验证和真实汇报即可。

GitHub 边界：

- 用户说“提交代码”“提交到仓库”时，默认只代表提交并推送任务分支，不代表合并主线或发布上线。
- `main`、`master`、`production` 等主线默认禁止直接推送。
- 合并 PR、发布上线、强推、删远端分支和改仓库设置，必须等待用户明确授权。
- 一个任务默认一个任务分支；同一任务里的补修继续推到这个分支，不为每次补改新开分支。
- 快速小改也必须有恢复点；Git 仓库内优先用本地提交保存，用户担心本地丢失或要求“仓库也有”时，推送到当前任务分支，但不自动创建 PR、不合并主线、不发布。
- 每次提交、推送或创建 PR 后，必须用中文说明提交了什么、为什么提交、包含哪些文件或功能、验证结果、推送到哪个分支，以及它是否已经进入主线；禁止只给 commit hash、分支名或 PR 链接。

AI 必须负责判断和执行 Git 细节，并用小白能看懂的语言汇报。不得把复杂 Git 决策直接甩给用户，也不得因为用户不懂 Git 就跳过分支、PR、CI 或回滚说明。

改代码的 Git 节奏：

- 目标文件所在目录是 Git 仓库，且任务属于完整通道实现交付时，正式修改业务代码前应先从已确认的稳定点创建或切换到当前任务分支。
- 快速通道的小改不强制创建新分支；如果需要远端保存且当前已在匹配本任务的任务分支上，应继续使用该分支；如果当前在 `main`、`master`、`production` 上，则先创建任务分支再提交和推送。
- 禁止为了同一任务、同一补修或同一轮测试修正重复创建多个分支。
- 改动不能长期堆积在工作区。每完成一个可独立验收、可独立回滚的逻辑单元，并完成与风险匹配的验证后，必须及时精准提交。
- 提交粒度按逻辑单元划分，不按文件数量、修改行数或时间机械划分；禁止每几行一提交，也禁止把多个无关功能最后塞进一个大提交。
- 如果任务包含多个独立功能、修复、UI 调整或配置变更，应拆成少量清晰提交；同一功能强相关的实现、测试和必要文档可以放在同一个提交中。
- 提交前必须检查 diff，确认没有混入用户已有改动、临时文件、敏感信息、无关格式化或计划外变化。
- 没有通过必要验证时，不得把提交描述成已完成；如果环境导致无法验证，默认不得提交为完成品，除非用户明确要求保留阶段性提交；此时提交信息和最终汇报必须明确标明未验证、阻塞原因和剩余风险。
- 快速通道的小改、只读任务、非 Git 工作区、一次性输出文件或用户明确不要求提交时，不强制创建新分支；但 Git 仓库内的代码改动必须至少保留 diff 或本地提交，非 Git 文件必须保留备份或可恢复路径。
