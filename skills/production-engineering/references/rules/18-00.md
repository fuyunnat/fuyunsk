
## 十八、日志、审计与可观测性

本节主要适用于本次新增或修改的关键业务流程、安全事件、外部调用、事务和后台任务。禁止为了一个无关小改动顺手重做全项目日志体系。

以下事件在适用时必须记录：

- 外部服务调用：服务名、接口、耗时、结果、错误原因。
- 事务失败或回滚：业务场景、失败原因、request_id。
- 后台任务：开始、结束、失败、耗时、处理数量。
- 鉴权事件：登录、退出、鉴权失败、越权访问、关键数据变更。
- 安全事件：权限拒绝、异常登录、敏感操作、疑似攻击、重复回调、签名失败。
- 管理员操作：操作者、目标对象、动作、结果、时间、request_id。

可观测性要求：

- 关键请求必须能通过 request_id 或 trace_id 串起前端、后端、数据库、外部服务调用日志。
- API 错误必须记录可定位的错误码、业务场景、请求路径、用户身份摘要和 request_id。
- 后台任务必须记录任务 ID、开始时间、结束时间、耗时、处理总数、成功数、失败数、跳过数。
- 外部服务调用必须记录服务名、接口名、耗时、超时、重试次数、降级结果。
- 数据库事务失败必须记录业务场景、失败阶段、错误原因和是否已回滚。
- 权限拒绝必须记录用户身份摘要、目标资源、动作、拒绝原因和 request_id。
- Webhook 或第三方回调必须记录来源、签名校验结果、幂等键、业务对象 ID 和处理结果。
- 关键失败必须能从日志定位到代码路径、输入摘要和外部依赖状态。
- 日志必须服务于排查，禁止只写“失败了”“异常了”这类无法定位的问题描述。

如果项目已有 metrics、tracing、APM 或日志平台：

- 必须沿用现有方案。
- 新增关键流程必须接入现有 request_id、trace_id、logger、metrics 命名规范。
- 不得另起一套重复日志或指标体系。

如果项目没有可观测性基础：

- 至少必须补充结构化日志或清晰的上下文日志。
- 不得为了小功能引入大型监控依赖，除非用户明确确认。

日志级别：

- debug：开发排查，生产默认关闭。
- info：正常关键流程。
- warn：可恢复异常、权限拒绝、参数异常、外部服务不稳定。
- error：功能失败、系统异常、数据库异常、外部依赖失败。
- audit：登录、鉴权、越权、关键数据变更、管理员操作、安全事件。

日志禁止出现：

- 明文密码。
- 完整 token。
- 完整密钥。
- 完整手机号。
- 完整身份证号。
- 完整银行卡号。
- 用户隐私原文。
- 大段请求体。
- 大文件内容。
- 未脱敏第三方响应。
- 完整 Cookie。
- 完整 Authorization header。
- 私钥、助记词、支付凭证。
