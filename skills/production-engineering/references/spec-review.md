# 规格、任务拆分与双轴审查

用于整理规格、划分可验证工作、规划大任务或审查分支与工作区差异。原文验收、只读、授权和验证规则优先。

## 先整理已有证据

从当前对话、真实仓库、已有议题、规格、术语与决策记录提炼，不重复盘问已经回答的问题。只有业务行为、验收、兼容、风险或授权仍有关键歧义时再问。

规格写清问题与使用者、目标结果、可观察验收及失败路径、已经确定的接口/数据/集成决定、公开测试边界、范围外事项，以及必要风险和回滚。优先稳定行为约定，不编造文件路径或实现细节。

## 按可验证行为拆分

每项贯穿必要层次，交付一个狭窄但完整的行为，能独立演示或验证。记录标题、结果、验收、真实阻塞关系、受保护行为与兼容约束。不要拆成三项互不工作的“数据库、接口、界面任务”。

宽范围机械重构可采用 `design-testing.md` 的扩展、迁移、收缩。预重构必须确实使当前需求更安全或简单，不能顺手改造架构。议题系统可选；未获授权不创建议题或本地文档，仅在对话中给方案。

## 大任务决策图

只维护目标、已决定及证据、目前能明确的问题、尚不明确但在范围内的部分，以及范围外事项。从当前可推进的问题开始，每次解决一个决定，不把模糊区域硬拆成虚构任务。规划默认只读，产品实现和外部记录写入分别授权。

已有计划准备执行时先做一次**计划审查**：核对当前源码、依赖关系、验收、受保护行为和高风险动作。过时文件路径、已能从源码纠正的小问题直接修正计划；会改变用户最终结果的冲突才按新手友好方式询问。计划不是授权放大器，主线、生产、删除和数据库高风险动作仍需单独满足权限规则。

## 固定审查范围

确认用户指定提交、标签、分支或安全可确定的基线。分支审查按仓库约定比较共同基点，例如 `git diff <base>...HEAD` 并记录 `git log <base>..HEAD --oneline`。无效引用或空差异先说明，不凭空生成发现。

工作区审查必须另外包含未提交、暂存与未跟踪的本次改动；分支提交差异不能冒充当前工作区差异。找不到可靠基线时只问真正缺失的一项。

## 寻找需求和规范来源

依次查提交或分支关联议题、用户给定路径、项目规格/方案/决策和当前对话验收。没有来源就写“没有可用规格”，不虚构需求。代码规范来自最近的 `AGENTS.md`、贡献文档、约定、测试、工具与架构决定；不要重复报告工具已强制处理的格式噪声。

## 两个维度分别结论

**规范与质量**：项目规则是否遵守，命名是否含糊，是否重复逻辑/数据群/分支判断、改动分散、一个文件承担无关职责、过度抽象、无价值转发或测试耦合实现。没有明确项目条款时，这些是需判断的信号，不是自动违规。

**需求与意图**：是否漏做或半做需求、增加未授权行为、实现与验收矛盾、遗漏失败/兼容/回滚，测试是否真正证明结果。一个维度通过不能掩盖另一个失败。

## 环境允许时使用新鲜上下文复核

重大功能、复杂 Bug、跨模块改动、迁移、上游同步或准备合并主线前，如果当前运行环境可靠支持子代理/独立 reviewer，可把复核交给**不继承当前会话历史的新鲜上下文**。给 reviewer 的输入只包含：

- 需求/工作清单编号与验收标准；
- base/head SHA 或明确 diff 范围；
- 本次实现摘要、受保护行为和已知风险；
- 已运行验证及真实结果。

先做“需求符合审查”，只检查漏做、多做、未授权行为和验收冲突；再做“代码质量审查”，检查正确性、错误处理、并发、安全、复杂度、测试、注释和可维护性。没有子代理时按同样双轴自审，不能假称独立复核。

发现按严重性区分：**阻塞**（必须修完才能交付）、**重要**（本范围内应修）、**次要**（不阻塞，可记录）。评审不能因为“看起来专业”扩大到无关重构。

## 收到评审意见先验证，再实现

评审意见不是自动指令。逐条处理时：

1. 找到意见对应的真实代码和触发路径。
2. 对照用户要求、项目约定、兼容边界和测试确认意见是否成立。
3. 不明确但能从代码查明的先自查；只有结果冲突才问用户。
4. 正确意见按阻塞级别逐项修，每项修后立刻做针对性验证。
5. 如果意见会破坏现有功能、违反明确需求、要求无必要大重构或基于错误上下文，保留现状并写清技术依据。

不能为了“配合 review”盲改，也不能因为建议来自外部就机械拒绝。

## 复核修复本身带来的影响

复杂评审修复、公共返回值/参数、共享类型、缓存/状态机、数据库访问或跨模块边界被修改后，不只重新看原 finding；还要检查该修复对主要消费者和直接相邻调用链造成的新影响。测试只覆盖它观察到的结果，不能把“原问题测试绿了”当作所有消费者都安全。

## 输出

每个维度内按严重性列证据位置、影响和触发条件、最小修复、必要验证。分别汇报规范与质量、需求与意图、覆盖缺口、各维度发现数量和最严重问题。没有规格要直接说明。环境支持时可并行审查，但只有互不依赖的只读检查才并行；共享写入仍顺序执行。
