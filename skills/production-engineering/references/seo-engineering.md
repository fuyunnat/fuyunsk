# SEO 工程与收录保护

本文件用于把 SEO 作为真实开发能力处理，而不是把用户变成 SEO 专家。用户可以只说“帮我把网站 SEO 搞好”“这个页面为什么不收录”“多语言 SEO 一起做好”；框架、标签、Schema、canonical、hreflang、sitemap 等技术细节由 AI 根据项目和当前官方资料自行判断。

SEO 只对**公开、希望被搜索引擎发现的页面**生效。后台、登录后页面、内部工具、支付回调、管理接口等不因为本规则强行做 SEO；若这些私有入口意外公开可索引，按风险报告并处理。

## 一、两层模式：公开前台轻保护，明确 SEO 再深挖

### A. SEO Guard：公开前台的轻量保护

新建、重写、迁移或明显改动公开可索引页面时，即使用户没说 SEO，也只做与本次页面直接相关的轻量保护，不能把普通前端任务升级成全站 SEO 审计：

- 页面返回正确 HTTP 状态；重要内容不是只有报错、空壳或登录墙。
- 标题、主要标题、描述和页面主题一致；不复制一套模板标题到所有页面。
- 不意外出现 `noindex`、错误 canonical、错误 robots 规则或会把正式页指向其他页面的配置。
- 新增公开路由时检查是否需要进入现有 sitemap、导航或内部链接体系；不为了 SEO 自动重构全站信息架构。
- 公开页面重要文本、标题和关键 SEO 元素不能只存在于客户端临时状态；对 CSR/SPA 项目检查原始响应与渲染后结果，按现有技术栈选择 SSR/SSG、预渲染或等价方案，不因 SEO 擅自换框架。
- 图片有真实语义时补合适的 `alt`；装饰图不堆关键词。
- 页面类型明确且项目已有结构化数据能力时，检查 Schema 是否继续匹配真实可见内容；没有必要时不强行加 Schema。
- 多语言公开页面按第六节检查语言版本关系；后台自身不因此强制多语言 SEO。

### B. SEO Engineering：明确要求 SEO / 收录 / 搜索优化时

用户提到 SEO、Google/Bing 收录、robots、sitemap、canonical、Schema、结构化数据、富媒体结果、关键词、Core Web Vitals、GEO/AI 搜索、多语言 SEO、hreflang、商品 SEO、自然流量下降等时，进入完整 SEO 工程流程。根据实际目标只加载相关领域，不为一个 canonical 问题扫描所有外链和本地 SEO。

## 二、对新手的交互规则

用户不会 SEO 不是阻塞项。默认先从源码、路由、部署配置、页面实际响应和允许访问的线上结果里判断：

- 哪些页面应该公开收录、哪些不应该；
- 网站是单语言、多语言、商城、内容站、SaaS、本地服务还是混合类型；
- 是否已有 sitemap、robots、canonical、Schema、SSR/SSG、SEO 插件或后台 SEO 配置；
- 页面 URL、业务名称、商品/分类/文章等真实数据从哪里来。

只有**业务结果**真的不明确才问用户，例如“这个预览页要不要出现在 Google”“中文和英文是同一市场还是不同国家版本”。不要把“canonical 应该怎么写”“该用哪种 Schema”“hreflang 怎么配”这种技术题甩给用户。

## 三、技术 SEO：先保证能抓、能理解、不会误伤

完整检查按实际影响裁剪，核心顺序是：

1. **可访问与状态码**：正式页面、重定向、404/410、软 404、认证和错误页是否符合预期。
2. **抓取控制**：`robots.txt`、meta robots、`X-Robots-Tag`、CDN/WAF 是否意外阻挡重要页面或资源。
3. **索引与 canonical**：重复 URL、参数页、协议/域名/尾斜杠变体、分页/筛选、规范 URL 是否一致。`rel=canonical` 是给搜索引擎的规范化信号，不当成强制保证。
4. **重定向和 URL 稳定性**：永久迁移优先保留旧 URL 到新 URL 的可验证跳转，避免链式跳转和把大量旧链接直接打成 404。公开 URL/slug 大规模变化属于高影响 SEO 变更，见第九节。
5. **站点地图**：只列希望进入搜索结果的规范 URL，使用绝对 URL；大型站点按协议限制拆分。提交 sitemap 是发现/抓取信号，不承诺一定收录。
6. **内部发现**：重要页面应能通过真实导航/内部链接发现；不要依赖用户必须搜索、提交表单或运行特殊脚本后才能找到。
7. **JavaScript 渲染**：检查原始 HTML 和真实渲染结果是否在 title、canonical、robots、主要文本、结构化数据上出现冲突。关键 SEO 信息能稳定服务端输出时优先稳定输出，但不因此无授权重写前端架构。

## 四、页面与内容 SEO：具体、真实，不做关键词堆砌

页面优化先满足搜索意图和用户可读性，再处理关键词表达：

- title、H1、正文主题应一致，但不要求逐字相同，也不机械重复关键词。
- meta description 用于准确概括页面和改善搜索摘要可读性，不承诺直接提升排名。
- H1/H2/H3 服务内容结构，不为“SEO 分数”硬凑层级。
- 内链锚文本描述目标页面，不批量堆精确匹配关键词。
- 内容不足时先判断页面是否真的需要独立存在；不能通过注水字数制造“厚内容”。
- E-E-A-T 只按可观察证据检查：作者/组织信息、真实经验或来源、更新与责任信息、联系方式、退换/隐私/服务政策等与页面类型匹配的信任信号。没有证据不能给“专家度 95 分”之类假精确结论。
- 写新 SEO 文案时同时遵守 `content-writing-quality.md`；用户明确要自然化/去模板感时再叠加 `writing-polish.md`（若当前安装版本存在该文件）。

关键词研究、搜索量、竞争度、SERP 难度如果没有实时数据源，不凭模型猜数字。可以做主题/意图分析，但必须把“推断”与“真实搜索数据”分开。

## 五、结构化数据：匹配页面事实，不造富媒体资格

Schema / JSON-LD 的原则：

- 只标记页面真实存在、用户可看到或业务真实提供的信息。
- 不伪造评分、评论、价格、库存、作者、门店、活动、FAQ、商品属性等来追求富媒体结果。
- 优先使用项目容易稳定维护的 JSON-LD；生成后必须能解析，并按当前 Google Search Central / Schema.org 要求验证对应类型。
- Schema.org 类型“存在”不等于 Google 当前仍支持对应富媒体展示；任何“哪些类型可用/已弃用/有限制”的结论属于时效信息，执行时先查当前官方资料。
- 结构化数据应与页面可见内容和后端真实业务数据一致，商城价格/库存/币种变化时不能让 JSON-LD 长期写死成旧值。

## 六、多语言与国际 SEO：和 i18n 一起设计

前台多语言是本 Skill 的默认工程偏好，因此公开多语言页面同时考虑国际 SEO：

- 每个语言/地区版本使用稳定、可抓取的 URL；不要只靠前端切换语言但 URL 永远不变。
- 页面声明正确的文档语言；本地化页面的 title、description、正文、Schema 可本地化字段也要对应当前语言。
- 需要 `hreflang` 时，每个页面列出自己和对应的其他语言/地区版本，并保证关系可回查；canonical 与 hreflang 的目标不能互相打架。
- `x-default` 只在确实存在合适的默认/语言选择入口时使用，不能写成所有网站强制要求。
- HTML、HTTP Header、XML sitemap 都可以承载 hreflang；选择一种最适合当前项目维护的主方法，不为了“保险”同时维护三套互相漂移的配置。
- 语言/地区代码按当前 Google 支持规范验证，不凭记忆编造代码。
- 翻译存在不等于 SEO 完成；还要检查各语言页面是否缺页、主要内容是否错配、货币/日期/单位/链接和 Schema 是否仍指向另一语言。

## 七、电商 SEO：商品、分类、变体和筛选必须接真实业务数据

商城项目额外检查：

- 商品页、分类页、品牌页哪些应该索引，筛选/排序/搜索参数页哪些不应造成大量重复索引。
- Product / Offer / ProductGroup / Breadcrumb 等结构化数据是否适合当前页面，并直接来自真实商品、价格、币种、库存和变体数据。
- 商品售罄、下架、替代商品、永久删除分别使用与业务相符的状态和跳转策略，不统一把所有旧商品跳首页。
- 分类/商品 URL 改名时先建立旧 URL 映射和回滚方案，避免二开或迁移把已有自然流量入口直接切断。
- 多语言商城同步检查 localized URL、hreflang、商品名称/描述、币种和结构化数据一致性。
- SEO 可运营字段（页面 SEO 标题/描述、分享图、商品/分类 SEO 文案等）如果运营可能调整，优先后台配置；但 canonical 生成、路由约束、禁止索引的安全边界等系统规则不要变成可随意误操作的自由文本。

## 八、性能与 AI 搜索：以真实指标和当前官方规则为准

Core Web Vitals 当前重点看 LCP、INP、CLS；有真实字段数据时优先 CrUX / PageSpeed / Search Console 等实测证据，没有字段数据时可以用 Lighthouse/浏览器实验数据辅助，但必须标明不是实际用户数据。当前官方“良好”参考值是 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1，并以第 75 百分位评估；若官方标准以后变化，以执行时最新官方文档为准。

AI Overviews / AI Mode / 其他 AI 搜索不要单独发明一套玄学：

- 先满足经典 SEO 基础：页面可索引、可抓取、重要内容是文本、内链清楚、体验良好、结构化数据与可见内容一致。
- 可以提升答案段落的自包含程度、实体清晰度、来源透明度和原始信息价值，但不能承诺“这样就会被 AI 引用”。
- 不默认添加 `llms.txt`、所谓 AI 专用 Schema、隐藏关键词或机器专用内容；若用户专门询问这类新标准，先查当前官方/一手来源再决定。

## 九、SEO 高风险变更：不能为了“优化”直接一刀切

以下属于可能影响收录和自然流量的高影响改动，除非用户已经明确授权对应结果，否则先说明影响与回滚，再确认：

- 批量改公开 URL、slug、域名、目录结构或协议；
- 大面积新增 `noindex` / robots 禁止抓取；
- 批量修改 canonical 指向；
- 删除 sitemap 中大量 URL 或改变 sitemap 生成范围；
- 删除/替换已存在的结构化数据体系；
- 批量改 hreflang 目标或语言 URL 规则；
- 把大量旧 URL 统一重定向到首页/单页；
- 为 SEO 批量重写现有业务内容、标题或商品数据。

SEO 不能绕过 `behavior-preservation.md`。公开 URL、索引状态、结构化数据、SEO 后台配置和多语言路径本身也是需要保护的可观察行为。

禁止黑帽/欺骗性做法：隐藏文字、关键词堆砌、门页、伪造评价/评分、与可见页面不一致的 Schema、cloaking、批量垃圾外链、为了搜索引擎展示与用户不同内容。

## 十、SEO Drift：公开页面改造前后要防回归

当任务会明显改变公开页面模板、路由、SSR/SSG、head 管理、商品/分类模板、多语言路径或站点结构时，在受影响范围建立轻量 SEO 基线，修改后对比：

- URL 与 HTTP 状态；
- title / meta description；
- canonical；
- meta robots / X-Robots-Tag；
- hreflang（如适用）；
- JSON-LD/其他结构化数据类型与关键字段；
- H1 和主要可见文本是否仍存在；
- 关键内部链接；
- robots.txt / sitemap 对这些 URL 的影响；
- 原始 HTML 与渲染后 DOM 中关键 SEO 元素是否一致；
- 有条件时的 Core Web Vitals / 页面性能证据。

只记录本次影响范围，不因为“SEO drift”抓取整个互联网或给每个小按钮改动建立大型数据库。需要长期监控时再单独建立持久基线。

## 十一、真实验证：build 成功不等于 SEO 正常

SEO 实现完成后按实际影响至少做对应的真实检查：

- 请求真实 URL，确认状态码、跳转链和最终 URL；
- 查看原始 HTML 与浏览器渲染后的 `<head>` / 主要内容；
- 校验 canonical、robots、hreflang、Schema 是否指向真实目标且无冲突；
- JSON-LD 必须可解析；需要富媒体资格时再用当前官方验证工具核对；
- robots.txt / sitemap 要实际可访问、格式有效，且关键 URL 的包含/排除符合预期；
- 多语言至少抽查一个语言对的双向关系与 canonical；
- 商城至少抽查一个商品/分类/变体数据与结构化数据是否一致；
- 性能只有实测过才能报告具体结果；没有数据就写“未验证”，不能凭构建速度猜 Core Web Vitals；
- SEO 修复不得通过把页面改成另一个业务结果来制造“通过”。

编译通过、Lighthouse 某个单分数、页面返回 200、Schema 能 parse，都不能单独证明 SEO 完成。

## 十二、报告给不会 SEO 的用户

最终不要甩术语清单。按结果说明：

1. **修了什么**：例如“商品页现在能被正常收录”“多语言页面互相对应”“旧链接会跳到新地址”。
2. **影响哪些页面/路径**：列实际 route/URL/template。
3. **真实验证了什么**：状态、页面 head、sitemap、Schema、多语言关系、性能等。
4. **还没法验证什么**：例如需要 Search Console 权限、真实流量或等待重新抓取。
5. **风险/回滚**：只有实际存在时说明。

不承诺排名第几、多久收录、一定出现富媒体结果或一定被 AI 引用。搜索引擎最终抓取、索引、canonical 选择和展示都可能与站点提示不同。

## 十三、时效与来源优先级

SEO 规则变化快。涉及搜索引擎当前政策、支持的 Schema、富媒体类型、AI 搜索、Crawler token、CWV 指标、Search Console/API 能力等时：

1. 优先查 **Google Search Central / web.dev / Schema.org / 对应搜索引擎官方文档**的当前版本；
2. 再参考可靠的一手工具/API 文档；
3. 第三方 SEO 博客、评分工具和本 Skill 内置旧知识只能做线索，不能覆盖当前官方说明；
4. 如果无法联网核对时效规则，明确标记“需上线前按当前官方文档复核”，不要把记忆当最新事实。

本模块的方法结构参考了公开的 `AgriciDaniel/codex-seo` / `claude-seo`（MIT）中的技术 SEO、Schema、hreflang、drift、GEO 和按需路由思想，但不依赖第三方 Skill 运行、不复制其固定评分体系，也不继承其中可能过时或过度绝对的规则。
