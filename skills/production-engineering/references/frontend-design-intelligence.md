# 前端设计智能：方向、品味、交互与设计系统

本规则只在用户明确要求重新设计、精修、提升质感、UI/UX 审查、建立设计系统，或现有页面明显存在视觉/交互问题时加载。普通 Bug、后端任务、严格原样迁移不因为存在前端就自动加载。

它补充 `ui-design-workflow.md` 和 `frontend-interface-quality.md`，不替代源码遵循、功能保护、浏览器验收、无障碍、响应式与现有 Design System。目标是让前端设计有方向、有证据、有统一视觉语言，而不是把多个第三方 Skill 的风格模板叠在一起。

## 非设计师委托：由 AI 承担视觉判断和实现

用户说“我不会美工”“你来设计”“页面你看着做”且任务涉及新页面、视觉改版或明显精修时，视为已委托本次范围内的视觉方案。先读现有品牌、成熟页面、组件、真实内容和用户给的参考；自行选择一个有依据的主方向，用普通话简要说明页面重点与保留项，然后完成代表页的实现。不要求用户提供配色、字体或间距参数，不因没有 Figma 或设计稿而停工；无参考时明确按项目证据和产品场景设计，不冒充参考图还原。

只在品牌定位、目标人群或截然不同的结果确实无法从现有证据判断时，提出最多 2–3 个结果层面的选项并推荐一个，不把审美参数清单交给用户。现有界面要求原样保留时，只修用户指定问题；“不会美工”不授权改业务逻辑、接口、数据或整站换风格。

完成前在可用的隔离环境里对代表页面取实际截图并检查至少桌面与手机视口、关键状态和交互，按 `ui-visual-verification.md` 记录最影响使用的缺陷并做有限复查。浏览器不可用时继续能执行的前端实现与静态验证，明确标记视觉验收未完成，不让用户替 AI 做第一轮美工审核。

## 一、先判断这是品牌界面还是产品界面

先判断当前页面属于哪种设计语域：

- **品牌型**：官网、营销页、活动页、作品集、品牌展示。视觉本身承担表达与记忆任务，可以有更强的构图、节奏、字体和动效个性。
- **产品型**：后台、控制台、商城操作流、工具、设置、表格、表单、业务工作台。设计首先服务任务效率、信息层级、稳定位置和可预测交互。

同一个项目可同时包含两种语域，但不能把营销页的巨大留白、夸张动画和品牌构图机械搬进高密度后台，也不能把后台式卡片栅格套到品牌首页。

如果页面同时承担品牌和产品职责，明确主职责，再让次职责退居第二层；不要两套视觉逻辑抢同一屏注意力。

## 二、用三个设计旋钮约束结果，不凭“高级感”三个字

新设计或明显精修前，给当前页面形成 1–10 的三个内部设计参数，不要求用户理解术语；能从项目、用户目标和参考站判断时直接判断：

- **VARIANCE（变化度）**：1 是高度规整、强对称；10 是大胆、非对称、强构图。
- **MOTION（动效强度）**：1 基本静态；10 强叙事、强过渡、明显动态层次。
- **DENSITY（信息密度）**：1 展示型、留白多；10 高密度专业工作台。

这些值只用于约束设计选择，不直接写进业务代码。默认根据场景推断：后台通常较低变化度、中低动效、中高密度；品牌页可以提高变化度和动效；移动端根据可操作面积适当降低密度。

用户明确要求“更大胆/更克制/更紧凑/更有动效”等时，优先调整对应旋钮，而不是整套视觉推倒重来。

## 三、先形成设计语言，再选组件

开始大量编码前，至少回答这些问题：

1. 用户此屏最重要的任务是什么。
2. 第一眼应该看到什么，第二眼看到什么。
3. 页面属于哪种语域，三个设计旋钮大致落在哪里。
4. 当前品牌资产、颜色、字体、Logo、图标、现有组件和参考站提供了什么证据。
5. 哪些视觉套路明确不要出现。
6. 哪些交互/状态必须保持与旧系统一致。

不要从“我要用 Card / Tabs / Dialog”开始设计；组件是结果，不是设计方向。先定信息架构、视觉层级、节奏和交互，再用已有组件体系表达。

## 四、设计选择要有证据，不靠随机审美

设计时优先使用以下证据来源，按可靠度由高到低：

1. 用户当前明确要求与参考图/参考站。
2. 当前项目已有品牌系统、主题 token、设计文档和成熟页面。
3. 同类真实产品的已验证交互模式与平台约定。
4. 当前产品类型、目标用户、内容结构和数据密度。
5. 通用设计经验。

第三方 Skill 中的“风格库、配色库、字体组合、图标、图表、动效预设”只作为启发，不自动成为项目依赖，也不因为某套预设热门就直接套用。

如果需要联网查看设计趋势或平台规范，优先当前官方组件/平台文档和可信的一手来源；不要把搜索结果当模板复制。

## 五、长期/多页面设计要维护 DESIGN.md

当任务满足任一情况时，若项目根目录已有 `DESIGN.md` 就先读并增量维护；没有时，在用户已授权写项目文件且确有长期价值时创建：

- 多页面新设计或整套后台/前台重做；
- 新建/重构 Design System；
- 需要多人/多会话长期延续同一视觉语言；
- 代表页已经验证，后续会批量扩散到其他页面。

`DESIGN.md` 只记录稳定的设计契约，不记录任务进度。至少包含：

- 产品/页面语域：品牌型或产品型；
- 目标用户与核心任务；
- VARIANCE / MOTION / DENSITY 的当前基线及原因；
- 色彩与语义 token；
- 字体、字号、字重、行高和数字规则；
- spacing、gutter、内容宽度、radius、阴影层级；
- 组件和状态的共享规则；
- 动效原则、时长/节奏、减少动效策略；
- 响应式与移动端策略；
- 无障碍要求；
- 明确禁止的模板套路；
- 关键设计决定与依据。

任务状态、待办、已验证/未验证仍写 `PROJECT_ROOT/工作流程.md`。不要把两个文件混成同一份日记。

已有 `DESIGN.md` 时禁止整文件覆盖；只修改本次确实变化的设计契约。严格原样迁移不因为本规则自动创建新的视觉规范。

## 六、视觉品味来自一致选择，不来自装饰堆叠

优先建立一个明确视觉主张，再反复执行：

- 字体选择有性格但可读，正文和数据展示优先稳定；不要默认全站 Inter/系统默认字体只是因为省事。
- 色彩以语义和品牌为主，不为了“高级”默认紫蓝渐变、霓虹、玻璃拟态或纯黑背景。
- 形状语言一致：radius、border、shadow、icon stroke、控件高度、对齐规则有系统，而不是每个组件独立发挥。
- 构图有主次：不把所有模块都做成等权卡片，不让每个 section 都争当 Hero。
- 装饰必须服务品牌、层级或交互反馈；没有功能的噪声应删除。
- 一个大胆决定胜过十个随机“小设计感”。

在同一页面混用多套视觉风格通常比“略朴素但一致”更差。

## 七、产品 UI 的“贵”来自不可见细节

产品型界面重点检查这些用户不一定会主动说、但会直接影响“顺不顺手”的细节：

- 按钮、输入框、选择器、表格行、Toolbar 的高度与基线对齐；
- hover / active / focus / disabled / loading / pressed 状态是否连续；
- Dialog/Drawer 打开关闭、焦点回落、滚动锁定是否自然；
- 骨架屏与真实内容尺寸是否接近，避免加载后大跳动；
- tooltip、dropdown、popover 的出现方向、边界碰撞和关闭行为；
- 列表增删、排序、展开、折叠的空间关系是否可理解；
- 长文本、空值、异常值、大数字、小屏幕和系统缩放下是否仍稳定；
- 错误提示是否告诉用户下一步，而不是只报“失败”；
- destructive 操作是否在真正不可逆或高风险时才加强确认。

这些细节优先于继续加渐变、阴影、插画或复杂动效。

## 八、动效必须解释状态变化

动效只在以下目的之一成立时使用：

- 表达空间关系或层级变化；
- 帮用户理解对象从哪里来、到哪里去；
- 强化成功/失败/选择等状态反馈；
- 保持连续性，减少突然跳变；
- 品牌型页面中承担明确叙事作用。

普通产品 UI 默认短、克制、可打断；优先 transform/opacity 等低成本属性，避免大面积 layout thrashing。重复动画不应阻碍输入、点击和阅读。

必须尊重 `prefers-reduced-motion` 或项目等价能力；核心信息和操作不能依赖动画才能理解。

只有用户明确要求强动效、品牌展示或项目已有 GSAP 等体系时，才使用复杂 timeline/scroll-driven motion；不能为了“高级”给普通后台引入大型动画依赖。

## 九、Web UI 审查要覆盖真实可用性，不只看视觉

视觉审查至少覆盖：

- 使用语义 HTML/宿主语义组件，标题层级和 landmark 合理；
- 所有可交互元素可键盘操作，focus 清晰且不被裁切；
- icon-only 控件有可访问名称；
- 表单有 label、错误关联、必要的 autocomplete/inputmode；
- 点击/触摸目标足够，移动端不会因为元素太密难操作；
- hover 不是唯一信息入口，触屏有等价方式；
- loading 时避免重复提交，disabled 与只读状态语义清楚；
- 错误文案告诉用户怎么恢复；
- 外链、下载、危险操作的结果符合用户预期；
- sticky/fixed 元素不遮住内容、键盘、safe area 或底部操作；
- 横向溢出、文本截断、滚动容器、100vh/移动浏览器高度等边界经过真实视口检查；
- 动效有 reduced-motion 处理；
- 图片/图标有正确用途和尺寸，不用装饰性图片承担关键文本。

发现问题时按“阻塞任务 > 交互错误 > 可访问性 > 信息层级 > 一致性 > 纯装饰”排序修复，不平均分配时间。

## 十、审查/精修分四种动作，避免一上来重做

面对“太丑了、看起来不高级、哪里怪”这类反馈时，先判定适合哪种动作：

- **Critique**：指出最影响质量的 3–5 个问题及原因，不立即扩大范围。
- **Polish**：结构正确时，只修排版、间距、对齐、色彩、状态和微交互。
- **Distill**：界面太吵时，减少层级、装饰、重复容器和不必要控制。
- **Harden**：视觉基本成立后，补齐边界数据、响应式、键盘、无障碍、加载/错误/空状态。

只有结构、信息架构或设计语言本身已经错误时才进入 redesign；不要把所有 UI 问题都解释成“重做”。

## 十一、设计预检与交付门禁

新设计/明显重设计在批量扩散前，至少做一次预检：

1. 语域是否判断正确；
2. 三个设计旋钮是否与场景匹配；
3. 主任务和视觉焦点是否一致；
4. 设计系统是否已有单一来源；
5. 是否存在明显 AI 模板套路；
6. 代表页是否真实浏览器验证；
7. 键盘、移动端、长文本、空/错/载入状态是否至少抽查；
8. 关键动效是否有目的且可减少；
9. 多页面任务的 `DESIGN.md` 是否与实现一致；
10. 新视觉没有改变业务逻辑、权限、接口、数据和副作用。

不能因为截图好看就报完成；也不能因为 Lighthouse/构建通过就报视觉完成。

## 十二、吸收来源与边界

本规则只吸收通用方法，不复制第三方 Skill 的完整文本、命令系统、数据库或运行依赖。主要参考：

- Anthropic `frontend-design`：明确视觉方向、生产级实现、反通用 AI 审美；
- `nextlevelbuilder/ui-ux-pro-max-skill`：产品类型/风格/配色/字体/UX/图标/动效/图表/技术栈作为设计证据；
- `Leonxlnx/taste-skill`：变化度、动效强度、信息密度三旋钮，以及 redesign audit / pre-flight 思路；
- `pbakaus/impeccable`：品牌/产品语域、审查/精修词汇、Typography/Color/Motion/Spatial/Interaction/Responsive/UX Writing 的系统化检查；
- `emilkowalski/skills`：不可见细节、组件质量、动画决策和设计工程意识；
- `vercel-labs/web-interface-guidelines`：Web 交互、可访问性、表单、错误恢复、响应式和细节 QA；
- Google Labs `design-md`：用 `DESIGN.md` 固化稳定设计方向、token 与视觉规则。

外部项目更新不会自动改变本 Skill。需要吸收新版本时重新审查具体 diff，再决定是否更新本规则。
