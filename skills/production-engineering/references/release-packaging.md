# 打包与发布产物核对

用户要求打发布包、构建产物、打包给服务器更新，或打包并配合提交/推送时加载。目标是通用交付纪律：产物能对上当前代码、结构符合项目习惯、不把密钥和本机配置打进包。具体命令、系统平台和目录布局跟当前项目走，不写死某一种语言或某一种压缩方式。

## 一、何时用本文件

口语里出现「打包」「打个包」「发布包」「构建产物」「更新包」等，或用户把打包与提交/推送放在同一句话里时，按本文件核对。项目若已有发布脚本、CI 产物或制品库约定，优先沿用。

打包不等于已部署；提交、推送、合并主线仍要各自明确授权（见 `git-team-delivery.md`）。

## 执行范围：先沿用，不自动扩成整仓修复

- 已有脚本、目标和环境可用时，直接沿用；只读相关构建配置、产物约定和当前改动。清单仍按 `workflow-checklist.md` 触发，但建清单不等于全仓审查、全量重测或新搭一套环境。
- 先核对已有测试对应的源码、配置、依赖和环境；仍有效就复用。用户/项目必跑检查和本次受影响功能照常验证，不拿旧结果顶替失效证据，也不为提速跳过实际失败。
- 只有目标平台差异、原生依赖、脚本故障或缺少必要环境等有证据的原因，才补相应环境/修复；不因叫“Linux包”就一律搭新容器。必要时必须在目标环境验证，缺条件如实报告。
- 无关旧问题记建议；影响本次包可用性、安全或必要验收的失败才阻塞本次交付。用户中途新增要求照常记为必做；证据复用与重复停止统一见 `bounded-completion.md`。

## 二、打包前：产物要对上当前交付内容

1. 确认打进包的是**本次要交付的那份代码**（已保存；未提交内容是否打入，按用户授权或事先说明）。
2. 用项目既有构建/打包方式，不另起一套无关流程。
3. 记下可核对标识：Git 短 SHA（无 Git 则用内容哈希或构建时间），交付时用人话告诉用户。

## 三、包内容与目录形态

按项目习惯组织，并避免常见交付事故：

- 解压或安装后的目录结构应符合项目约定；若用户习惯「解开就能用」，就避免多包一层无意义的空顶层目录。项目脚本本身带一层时，打完抽查一次，确认和用户预期一致即可。
- **不要把真实密钥配置打进包**（如真实 `.env`、私钥、生产连接串）。示例用 `.env.example` / `.env.template` 等占位文件；真实密钥不进包、不进 Git。
- 默认不打：依赖目录、本地日志、缓存、数据库文件、本机绝对路径；用户明确要求且已脱敏时例外。
- 入口、示例配置、启动说明按项目需要补齐再交。

## 四、必要验收通过就交付

按产物类型完成适用项，不把“所有可能问题都消失”当完成条件：

1. 构建/打包实际成功，核对包存在、目录、入口、所需资源与密钥/运行数据排除。沿用项目要求；不另写一套无关打包系统。
2. 在独立临时目录实际解压或安装，从**产物本身**试代表入口，如运行命令、启动程序或请求页面/接口，按类型验证；只列目录、算哈希、编译通过不算可用性验证。涉及前端改动仍按前端规则做真实浏览器操作；不连接生产数据库或真实收费服务。
3. 出示一项可核对来源的证据：包内版本号 / Git 短 SHA / 本次对应文件，或能追溯到刚构建产物的校验和与构建记录。不能只凭文件名说是最新。
4. 已授权的提交/推送完成后核对实际结果，用 `verification-report.md` 五项白话汇报并停止。必要验收缺条件，明确区分“包已生成”和“能否运行未确认”，列缺啥，继续可独立完成的工作。

用户怀疑不是最新时，先出示标识，再按需重打。

## 五、和 Git 一起交付时

用户同时要求打包并提交/推送：

1. 固定本次实际打包输入及来源标识，优先从已提交源码构建；已有包能证明与**该标识对应的代码**一致时，核对后复用，不因提交动作本身重打。
2. 源码、依赖、资源、包内文档、构建配置/环境或嵌入版本等实际打包输入变化时，重新构建并重验受影响项；项目要求包对应最终HEAD时遵守其约定。
3. 包外的纯工作记录或发布记录提交，且已确认实际打包输入不变，不使包和业务测试自动失效。分别记录“包对应源码提交”和“远端最终提交”，不能伪称相同；不为记录自身无限追加提交、重打或重测。
4. 分别报告：Git 结果、产物位置、内含标识、是否含真实密钥配置（应为否）。同一逻辑改动及必要记录可一起提交，按 `git-team-delivery.md` 精准交付。

未授权推送时只打包并说明；不把「已打包」写成「已上线」。

## 六、长时间等待先查进展

开始时结合项目已有耗时、命令超时和目标约定检查点；等待期间查看进程状态与日志增量，有真实进展就继续，不按统一分钟数强杀正常构建。至少每分钟用一句人话说明当前步骤、新进展或具体卡点，不只反复说“正在处理”。

没有进展先区分下载、资源、缺配置或进程失效，做一次最小诊断；连续两轮没有新增证据或验收进展，停止同一路径盲重试，按 `bounded-completion.md` 转有限诊断或报告具体阻塞与恢复条件。不能换个日志/脚本/“最终验证”名称重置重试，不为消除无关问题反复重打。
