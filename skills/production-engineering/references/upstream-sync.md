# 派生项目上游同步与二开保护

当前明确授权与清单原文恢复例外统一遵守 `source-policy.md`；记录长度按 `workflow-checklist.md`，不重复增加执行层。

本规则用于已经基于第三方/官方/开源/商业源码进行二次开发的派生项目，需要选择性吸收上游 Bug 修复、新功能、兼容修正或安全补丁的场景。这里的“上游（upstream）”指派生项目所来源或持续参考的原项目，不要求一定存在 Git fork 关系；“派生项目”指当前已经有自己业务、功能、UI、配置、数据和改动的版本。

核心原则：**同步上游不等于把当前项目更新成上游最新版。默认是选择性吸收目标改动，并保护派生项目现有成果。**

## 一、触发与范围

用户说“同步官方这个修复”“吸收上游这个功能”“把原项目最近这个 Bug 修复合进来”“把 upstream 某个 PR/commit 的功能带过来但别动我的二开”等，进入本规则。

先把目标限定到用户点名的 Bug、功能、PR、commit、版本差异或明确范围。用户说“做到完成”表示把**当前已确认目标及其必要依赖**完整吸收和验证，不自动扩大成“追平全部上游版本”。

若用户只提供 release note、截图、网页说明或版本号，必须继续找到可验证的上游源码、diff、commit、PR 或对应行为证据；不能仅凭发布说明猜实现。固定来源 SHA 和验收范围，必要缺口、证据复用与收尾遵守 `bounded-completion.md`；续作不追逐最新上游或重新验全部已通过切片。

### 有限审查与实施清单

固定上游终点还要固定比较起点/模块、候选 ID 与总数。用户未要求全历史时，按已核实的上次同步来源或指定版本差异筛选，不回溯全部历史；二开版本号不能冒充上游同步起点，无证据时先查 Git/旧记录，仍有结果歧义才问。
选择性回迁记录不证明起点以前已全部同步；历史未覆盖项如实保留，不因此扩大本轮区间。

默认先分类再实施，不边审边补。分类为已实现、需要回迁、不适用、另行决策；只有需要回迁及有证据的必要依赖进入实施清单。续作记录已分类 K/N、剩余候选索引和实际当前项，不只写 AUDIT-REST“进行中”。明确完整审查须保留全分母，不能任意截断；所选补丁目标不能悄悄变成完整审查。具体收尾和用户修改目标按 bounded-completion 执行，未覆盖不写成已同步。

## 二、同步前先建立可恢复基线

写入前核对当前项目根、Git 状态、当前分支、未提交修改、远端和恢复点，遵守 `project-write-boundary.md` 与第四章 Git 规则。

- 当前派生项目已有用户修改默认受保护；不能为了同步上游覆盖、回滚或丢弃。
- 同步工作使用现有任务分支；没有合适分支才建独立分支，不直接在主线开发。
- 基线必须可以恢复：优先使用当前已确认提交 SHA、分支或 tag；非 Git 项目先做可恢复备份。
- 只有用户明确要求“先把当前状态提交/推送到 main/master 作为恢复点”且对应 Git 授权已经给出时，才更新主线；该授权只用于建立这次同步前的基线，不自动授权同步完成后把开发分支再次合进主线。
- 记录同步前基线 SHA/版本，后续报告必须能指出如何恢复到同步前状态。

## 三、先读上游真实改动，再决定如何吸收

上游仓库、压缩包、参考源码或演示环境默认只读。先确认上游来源、版本和目标改动的身份，再读取真实 diff 与必要上下文。

至少弄清：

1. 上游这次真正修了什么问题或新增了什么外部可见能力。
2. 改动涉及哪些文件、调用链、接口、配置、依赖、数据库、状态和测试。
3. 哪些变化只是上游自己的重构、格式化、目录调整或其他无关改动，不能顺带带入。
4. 上游改动依赖的前置 commit/接口/schema 是否也是当前目标的必要依赖。

不要只看“上游改了哪个文件”，要理解**语义变化**。派生项目可能已经把对应逻辑移动、重构或扩展到别处，应找到当前项目里真正等价的实现点。

## 四、默认补丁式吸收，不整仓覆盖

**按差异选择吸收方式，不固定手工第一，也不为了少冲突重做已经安全可用的补丁。** 先核实共同基线、目标提交、路径历史、必要依赖及当前实现；补丁已生效或存在等价修复时验证后跳过，不重复实现。

| 实际情况 | 处理方式 |
| --- | --- |
| 提交独立、依赖齐全、当前差异兼容 | 直接 cherry-pick 或应用可审查 patch，不先手工重写 |
| 部分文件/改动已吸收，其他部分仍需要 | 只应用缺失部分，保留上游来源与适配证据 |
| 同路径存在二开或实现已移动/重构 | 按修复原理在等价位置融合，不整文件覆盖 |
| 文件原文一致、没有二开差异，目标要求引入新版本 | 核对路径历史、完整依赖及差异后，可采用该文件的目标版本；不能仅凭同名判断 |
| 明确要求跟进整个上游版本 | 核实完整差异后按授权 merge/rebase；不从单个修复推断整仓升级 |

操作失败先查实原因；冲突不靠 ours/theirs 一刀切。选择方式不改变二开、数据保护和范围验收。

以下行为默认禁止，除非用户明确要求且已经审查影响：

- 直接用上游同名文件覆盖派生项目文件。
- 为了“跟官方一致”重置当前分支或 checkout/restore 掉派生项目改动。
- 用户只要某个修复/功能时直接 `merge upstream/main`、整仓 rebase、全量同步最新版。
- 因上游删除了代码、字段、接口或功能，就自动在派生项目同步删除。
- 把上游无关重构、格式化、依赖升级、UI 改版一起混进目标补丁。

符合表中条件时直接引入，不额外停下来等待用户审批工具选择；结果冲突、范围扩大和高风险缺授权仍按下一节处理。

## 五、冲突时优先保护二开成果

对每个上游目标改动，把当前派生项目差异分成：

- **可直接吸收**：当前代码仍与上游目标结构兼容，可做最小补丁。
- **需要融合**：当前项目在同一路径增加了自己的业务/接口/UI/数据逻辑，需要把上游修复原理融合进现有实现。
- **结果冲突**：上游目标行为与派生项目已经明确的产品行为无法同时成立。

前两类直接按最小兼容方案实施；第三类先按 `novice-clarification.md` 用人话说明“保留二开结果 / 改成上游结果 / 兼容两种结果”的差别和推荐，不能 AI 自己一刀切。

派生项目已有的新功能、支付方式、权限、佣金、多语言、后台配置、接口扩展、数据库兼容等都属于现有成果；同步上游不得把它们当“偏离官方”自动删除。

## 六、接口、数据库、配置和依赖继续走兼容过渡

上游改动如果涉及 API、字段、数据库、消息格式、缓存、配置、第三方依赖或客户端协议，继续遵守 `behavior-preservation.md`、`database-upgrade-safety.md` 与 `configuration-localization.md`：

- 旧新优先共存，不因上游新实现直接切断派生项目旧路径。
- 数据库仍采用 expand / contract；不能为了匹配上游 schema 直接删列、重建库或覆盖历史数据。
- 上游新增配置先判断应属于部署级 `.env`、后台运行时配置还是代码常量；不能照抄上游硬编码。
- 上游新文案/页面进入派生前台时继续遵守当前项目多语言约束。
- 新依赖只引入目标改动真正需要的部分；不能为了一个修复顺便升级整套依赖。

## 七、测试必须证明两件事，而不是只看编译

同步完成的判定必须同时满足：

1. **上游目标真的生效**：原 Bug 的失败证据不再出现，或新增功能的真实用户流程可以完成。
2. **派生项目自己的能力没有被破坏**：本次影响路径以及与上游补丁直接相邻的二开功能仍正常。

不能用 build/compile/typecheck 成功、页面能打开、接口返回 200 代替真实功能测试。根据实际项目做受影响范围的运行验证，例如：

- 前端：启动真实开发/测试服务，在浏览器操作目标页面、关键状态与二开交互。
- API/后端：使用真实路由和实际请求走完整处理链，验证成功和关键失败路径。
- 数据库：在安全环境验证旧数据、新数据、迁移兼容和必要事务；未经授权不得拿生产库试错。
- 后台任务/回调/消息：验证真实触发链和幂等/错误路径，不只调用内部函数。

发现报错、功能退化或二开能力被破坏，继续在当前分支修复并重新验证；失败补丁遵守 `bugfix-fast-loop.md` 的证据与回退要求，不叠加猜测。

## 八、目标模式的完成门禁：启动给用户测试，然后停

当用户明确要求目标模式、持续做到完成、最后启动给他测试时，完成顺序固定为：

**核实来源与范围 → 按授权保留恢复能力 → 读取上游真实改动 → 补丁式吸收 → 真实功能测试与二开回归 → 交付影响清单 → 停止等待用户测试。**

构建成功不代表真实功能通过。启动/预览先确认授权与数据库隔离；可能触发现有库迁移时用前端 mock 或新建临时库，不能为了收尾默认启动后端。用户明确放弃指定改动且不备份时按 source-policy 执行。

用户要求启动给他测试时，必须把可安全运行的项目启动好，并提供用户实际可访问的本地/测试入口；无法启动时必须明确说明阻塞，不得把“代码写完”当完成。仅要求补丁交付或收尾时，不额外增加常驻服务启动任务。

交付说明保持简洁，至少包含：

- 本次吸收的上游来源（版本/commit/PR/明确范围）。
- 吸收了什么、明确没有吸收什么。
- 影响了哪些页面、接口、后台功能或任务，以及对应页面路径/URL/接口路径。
- 为保护二开做了哪些适配。
- 实际运行测试了哪些流程，结果如何；未测试项明确列出。
- 同步前恢复点 SHA/版本和当前开发分支。
- 给用户测试的访问地址/启动状态。

到这里**立即停止**。除非用户随后再次明确授权，不自动继续优化、不清理旧实现、不扩大同步范围、不把开发分支合并到 `main/master`。

## 九、轻量记录上游同步账本

长任务或需要以后继续同步时，在现有 `工作流程.md` 当前任务区块记录必要来源，不另起复杂管理系统：

- upstream 来源与版本/commit/PR；
- 本次吸收项、未吸收项；
- 当前派生适配位置；
- 冲突和保留的二开能力；
- 恢复点、测试证据与待用户验收项。

不得记录密钥、密码、完整生产日志或敏感第三方凭据。账本只用于追踪选择性同步，不自动授权以后继续同步同一个上游的其他改动。
