# 根目录工作流程清单

用户明确要求把每次要做的事写到项目根目录 `工作流程.md`，做完一项、验证一项、打勾一项。它是用户可见的唯一任务清单，不是聊天里的临时计划，也不是 `.github/workflows`。本规则定向补充原文第二章续航：小改也记录简短清单，但不因此升级完整通道或强制运行状态助手。

## 位置与适用范围

实现、修复、重构、迁移及已授权的工程交付，在首次任务写入前，先核实项目根目录、项目规则、现有文件和 Git 差异，再创建或增量更新根目录 `工作流程.md`。这里的根目录是本次正在开发的目标项目根目录，不是 `CODEX_HOME`、`~/.codex/`、Codex 应用目录或技能安装目录。先从用户指定的项目路径、当前工作区和项目入口确认；真实工作树根目录只是定位线索，多项目仓库不能机械把上级 Git 根当作当前子项目根。非 Git 按已确认的项目根目录；多项目各自记录。跨框架迁移有参考源码和目标工程两份目录时，写在目标工程，参考源码目录默认只读；原位迁移就写原项目根目录。不得因为命令在子目录运行而写错位置，不写到用户主目录、临时下载目录或项目外。根目录不明确先只读查证；同名目录、符号链接、来源不明的已有同名文件或写入冲突，先暂停该处并说明，不能覆盖或跟随到其他项目。

普通聊天不创建清单。只读、先讨论、不要改文件时不创建或更新，已有文件可在相关范围读取；只有用户明确允许单独写工作清单时才写这一个文档，不能由此修改业务代码。安装技能只提供模板和短规则，不替用户扫描并给所有项目创建清单。

同项目默认只有这一份可见总清单。已有根目录同名文档先读再合并，保留用户说明和历史；其他位置的旧记录先核对并在根目录建立入口，不直接删除或移动。换路径或沿用其他文件名需用户明确要求，不能静默退回隐藏目录。无写权限时报告实际阻塞，不能只在聊天列计划就宣称已经写入。

## 一项一个状态

使用普通 Markdown 复选框加中文状态，稳定编号用于跟踪，示例不是已执行的结果：

```markdown
- [ ] W001【待做】尚未开始的具体事项。
- [ ] W002【进行中】正在处理的事项；下一步：说明具体动作。
- [ ] W003【待验证】实现已写完，必要验证尚未通过。
- [ ] W004【阻塞】缺失条件或验证失败；原因：写清问题与恢复条件。
- [x] W005【已完成】该项实际完成且适用验证通过；证据：命令、结果摘要或可核对文件位置。
- [ ] W006【已取消】用户明确取消；依据：确认来源；不计为已完成。
```

任务先列必做事项和验收，不复制全部工程规范。明确的新增需求继续追加，发现必要遗漏先补清单再执行；范围外建议标为待确认，不默认扩成当前任务。关键歧义先查已提供源码，仍无法判断时标阻塞并问具体问题。每项都要说明交付对象或验收标准，不写“完善一下”这类无法验收的条目。

开始一项前标为进行中；做完立即更新该项，不能等全部做完才回填。代码写完但未测是待验证，失败是阻塞；只有实际完成且对应验收验证通过才打勾。调研项以可核对的源码/文档事实验收，不要求每个事项都跑测试；同一真实验证覆盖多项时复用证据，不重复执行。父项必须等适用子项均通过；保留旧实现、确认废弃和迁移完成按原迁移规则，不靠打勾替代。

默认一次推进一个逻辑事项，确实独立并行时标明负责方和不同工作区，单一协调者合并同一清单，避免相互覆盖。新任务追加独立标题与任务编号；继续旧任务更新原区块，不重编号、不重置未完成项、不删失败和取消记录。修复后重新验证才能重勾，源码或验收变化导致旧结果过期时重开受影响项并说明。

## 恢复与完成

当前任务区块保留目标项目根目录、目标、源码基线、允许改变和必须保留的内容、禁止操作、当前项、下一步、阻塞及必要证据位置。长任务的架构决定和旧验收标准不能压缩成模糊的一句话。每次继续、换会话、上下文压缩或询问进度，先读根目录当前任务区块，再按需核对相关源码、Git 差异和证据；不能只凭聊天回忆，也不能把历史完成记录当作新任务已完成。

逐项状态与实际文件冲突时先纠正记录，不能按过期勾选继续。当前任务有待做、进行中、待验证、阻塞或未经确认的取消项，不能报告整个任务完成；历史或其他任务的未完事项不错误阻塞本任务。最终汇报给出根目录实际路径和当前未完项，不拿百分比代替验收。

## 与现有证据机制协作

`工作流程.md` 管待办、进度与用户约束；完整任务的旧 `task-state.js` 管版本指纹和执行凭据，整项目迁移台账管旧功能及逐项验收。后两者按原条件使用，在根目录清单记路径和任务编号，只记指针与必要摘要，不维护三份互相独立的待办。已有任务状态的目标/来源/下一步引用同一个清单区块；旧命令与文件兼容，不擅自覆盖或迁走。

清单打勾不替代 `check` / `finalize` 的迁移检查，也不会自动调用这些程序。旧状态助手的指纹可能包含根目录文档：先记录实际业务验证结果并更新清单，再完成最后的文档差异检查；修改清单后旧指纹失效时如实重新核验，不手填成功或排除文件绕过。仅进度文档变化可以核对源码未变、原验证仍适用后检查该文档，不因一个勾机械重跑全部业务测试；源码、配置、测试或环境变化仍按影响重验。最后一次核验后不要无意义刷新时间戳。

用户已明确要求的根目录清单默认作为可交付项目文档保留；只有当前任务同时获准提交/推送时才随相关改动精准提交，写清单不自动授权远端操作。用户明确不提交时保留本地并说明，不为了隐藏它改 `.gitignore`。不写密钥、个人数据、完整日志或敏感配置；公开前检查文档内容。

提交/推送项必须等实际操作成功且引用核对后才打勾，不能预先声明成功。包含本次提交自身的记录可在后续文档提交中补记或保留待同步并如实报告，不能虚构未来提交 SHA，不能为“记录记录自身”无限递归提交。

## 保持轻量

小改也记，但通常一到三项即可；新增事项与状态变化在必要时写入，同次完成项与下一项状态可一次保存。当前任务区块和所需规则批量读取，不每条消息全仓扫描、不轮询文件、不启动后台服务、不另起模型调用。历史仍在原文件中按区块读取；确需归档先保留可追溯入口并确认，不自动丢弃记录。

空白模板在 `templates/workflow.example.md`，填入真实任务再创建；不复制本技能仓库根目录的维护历史。Markdown 语法参见 [GitHub 任务列表](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#task-lists)。本清单是执行规则和记录，不是自动发现全部业务能力或保证模型绝不遗漏的程序。
