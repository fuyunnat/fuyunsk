# 单 Skill UI 设计、实现与验收工作流

本文件把 UI 设计、shadcn/shadcn-vue 组件使用、反模板化约束和浏览器验收统一收进 `production-engineering`。前端任务不要求再安装其他 UI Skill 才能获得这些能力；第三方 Skill 只作为方法来源参考，不是运行依赖。项目真正使用的 shadcn/ui、shadcn-vue、Tailwind CSS、Headless primitives 等仍属于业务项目依赖，新增或升级时继续遵守依赖、安全、Git 与写入边界规则。

## 一、先判定 UI 模式，禁止混着做

实现前先从用户最新要求、真实源码、演示站和当前项目判断本次属于哪一种：

1. **忠实迁移模式**：用户明确要求保留原貌、照原站做、样子别变或只换框架/语言。目标是复现，不重新设计；原布局、颜色、字体、间距、素材、文案、交互、状态和响应式属于验收条件。**仅仅提供了源码或演示站，不自动等于要求保留旧视觉。**
2. **新设计模式**：用户明确要求“UI 全重写”“重新设计”“换一套界面”或允许自由设计，且没有要求保留旧视觉。旧源码/演示站仍用于盘点功能、字段、流程和交互，但视觉可以重做；仍必须服从当前 Design System、真实业务功能与产品语义，不得套通用模板。
3. **精修模式**：现有页面功能和结构基本成立，用户只要求“更好看”“去 AI 味”“优化 UI”。优先局部调整层级、密度、排版、间距、状态和组件一致性，不顺手重写业务或换技术栈。

同一个项目可以不同页面处于不同模式，但同一页面不能一边声称原样迁移、一边擅自换皮肤。若“有源码/演示站”和“重写 UI/优化 UI”等表述同时存在，而视觉是否保留会明显改变结果，必须按 `novice-clarification.md` 用人话反问，让用户选择“视觉也保留 / 只保留功能重做视觉 / 仅精修结构”等结果；不能因为用户不懂技术就替他猜。

## 二、一个 Skill 内完成框架识别与 shadcn 适配

不要为了获得 UI 能力去执行 `skills add`、复制第三方 Skill 或把外部 Skill 目录塞进业务项目。本技能自己负责项目识别、设计约束、组件选择和验收；只有业务代码真正需要时才安装 UI 依赖或组件。

### React / React 兼容宿主

新设计且没有相反要求时使用 shadcn/ui + Tailwind CSS。开始前先读取真实的 `components.json`、`package.json`、lockfile、Tailwind 配置/入口样式、别名和已有 `components/ui`；不要凭记忆猜版本或组件 API。

如果项目已经具备 shadcn CLI 且当前环境允许无副作用读取，可用 `shadcn info --json` 获取框架、Tailwind、alias、base、图标库和已安装组件。需要组件前先查项目已有实现、官方文档/registry 或 CLI 的 docs/search/view 能力，再决定是否 `add`；只添加当前功能需要的组件，不整库下载，不覆盖已定制组件。已有 `components.json` 时不得为了省事重新 `init`；任何会覆盖组件的参数都必须先审查差异和恢复点。

### Vue / Nuxt

用户明确指定 Vue 时保持 Vue。新设计、用户偏好 shadcn 风格、项目又没有冲突的既有组件体系时，**优先使用 shadcn-vue + Tailwind CSS 作为 Vue 对应实现**；这不代表把官方 React shadcn/ui 组件塞进 `.vue`，也不代表把 Vue 项目切成 React。

先读 `components.json`、`package.json`、lockfile、Tailwind、alias 和已有 UI 组件。项目已经配置 shadcn-vue 时优先复用；CLI 可用且读取安全时可用 `shadcn-vue info --json`，需要组件前先查 docs/已有组件，再按需 `add`。已有项目不得无审查重新初始化、`--overwrite` 或批量 `--all`。如果项目已有成熟且不同的 Design System，不能因为本默认偏好强制迁移；只有当前任务确实授权建立/迁移 UI 基础时才调整。

### 其他框架

保持用户指定框架和当前项目结构；使用 Tailwind CSS、语义 token、宿主已有组件或可维护的可访问 Headless primitives 实现同一设计契约。不得为了追求“官方 shadcn”切换框架，也不得谎称使用了并不存在于该宿主的官方组件。

## 三、新设计先做极短 Design Brief，再写代表页

忠实迁移模式不重新发明视觉 Brief；直接从源码和运行基线提取。新设计或精修模式在大量写 UI 前，必须从真实业务中形成一个简短设计约束，能从项目查到的不要反问用户：

- 产品类型与核心用户是谁。
- 这个页面最重要的 1–3 个任务是什么。
- 信息密度：紧凑、标准还是偏展示型；后台默认紧凑/标准，不做营销页密度。
- 视觉气质：例如专业、克制、可信、轻量；不能只写“现代高级”。
- 主次层级：什么必须第一眼看到，什么属于次级信息。
- 已有品牌色、字体、素材、Design System、参考站或禁止变化项。
- 明确禁止的模板套路和本页不能牺牲的业务能力。

Brief 的作用是约束决策，不是再写一篇报告。目标明确后直接实现代表页。

## 四、多页面先建立 Design System，不允许每页自由发挥

在批量做后台、管理台、运营台或多页面新设计前，先建立最小可执行的视觉契约，并落到项目已有主题/token 位置：

- `background / surface / elevated / border` 层级。
- `foreground / muted / accent / destructive / warning / success` 等语义颜色。
- 字体层级、字重、行高和数字展示规则。
- spacing scale、内容最大宽度、页面 gutter 和 section gap。
- radius 层级；圆角表达层级，不是每个容器都一个大圆角。
- 控件高度：按钮、输入框、筛选器、表格行、工具栏保持统一。
- 阴影只用于真正有浮层关系的元素；普通 Card 不靠重阴影制造层级。
- 桌面/笔记本/平板/手机的布局策略。
- 表格、表单、Dialog/Drawer、空状态、错误状态、loading 的统一契约。

优先使用 CSS variables、Tailwind theme/token、组件 variant 和项目既有主题能力；禁止页面里出现大量无来源的随机颜色、随机像素、随机圆角和各写各的 class 套路。

## 五、反 AI 模板硬约束

以下不是绝对禁止某个视觉元素，而是**没有产品依据时不得作为默认套路**：

- 不默认使用“深蓝/纯黑大侧栏 + 浅蓝/浅灰大背景 + 巨型白 Card”作为后台壳。
- 一个数字不要占据巨型统计 Card；概览卡必须与真实信息密度相称。
- 不把每个 section 都包成 Card，不做 Card 套 Card，不靠边框把页面切成无数盒子。
- 不默认使用浏览器式多标签页承载所有页面；只有真实多文档/多工作区流程需要时才用。
- Empty 状态不能为了一个图标占据几百像素空白；要与表格/列表密度和下一步操作匹配。
- 后台不做巨大 Hero、营销式大标题、无意义装饰插画和过量留白。
- 不滥用渐变、毛玻璃、大阴影、超大圆角、高饱和随机色和无意义动画。
- Badge 只表达稳定状态/分类，不把普通文字都做成彩色胶囊。
- 图标必须有语义和一致尺寸；不能为了“丰富”给每行文字塞装饰图标。
- 侧栏、顶部栏、筛选、表格、分页、操作列必须优先扫描效率和稳定位置。
- 组件库默认 Empty、Card、Tabs、Sidebar 只是零件，不得未经设计直接拼成整页。

出现这些模式不自动判错；如果真实产品、现有 Design System 或用户参考明确需要，可以使用，但要与整体契约一致。

## 六、组件优先组合，不重新造基础控件

先复用项目已有 Button、Input、Select、Table、Dialog、Drawer、Tabs、Form、Tooltip、Dropdown、Pagination、Skeleton、Toast 等基础组件及其 variant；缺少时优先从当前 shadcn/shadcn-vue registry 或项目认可的 registry 查找。已有组件能通过组合解决时，不重新造一套视觉近似但 API 不一致的控件。

页面层负责信息架构和业务组合；请求、状态、校验、格式化、权限、数据转换按职责分离。Design System 组件只处理共享视觉与交互契约，不把业务逻辑塞进 `components/ui`。修改共享 UI 基础前检查主要使用方，并验证旧页面。

## 七、代表页是视觉门禁，不是演示摆设

多页面新后台先选一个最能暴露问题的代表页，优先包含导航、指标/摘要、筛选、表格或列表、状态、弹窗/表单中的若干项，而不是只挑最简单的空页面。

代表页至少检查：

- 信息层级是否一眼能读出主任务。
- 信息密度是否符合后台/产品场景。
- token、字体、间距、圆角、控件高度是否统一。
- 表格/表单/筛选/操作区是否对齐、稳定、可扫描。
- loading、empty、error、disabled、permission denied 等状态是否自然。
- 长文本、真实数据、极少数据和较多数据下布局是否仍成立。
- 桌面宽屏、普通笔记本、平板和手机是否没有明显错位/遮挡/溢出。
- 键盘、focus、Dialog/Drawer 焦点和图标可访问名称是否成立。
- 是否出现“组件库拼装感”“AI Admin 模板感”或与参考产品明显脱节。

代表页未通过时，禁止把同一视觉方案批量复制到其他页面；只暂停 UI 扩散，不阻塞独立的后端、接口和数据层工作。代表页通过后，将共享 token/组件作为后续页面基线，后续发现问题优先修共享契约，不让每页各自补丁化。

## 八、浏览器在环：边改、边运行、边批判

前端长任务不能只写代码和跑 build。环境安全且已有运行方式时保持本项目开发服务运行，给用户稳定预览地址，并在真实浏览器里检查。

忠实迁移模式：原版/演示站与新版在相同浏览器条件、可比视口和可比数据下逐页对照；不一致先修新版。新设计/精修模式：以 Design Brief、Design System 和代表页基线作为对照，不凭“看起来差不多”批量推进。

每个可见页面的循环：读取源码/参考 → 实现 → HMR/重启 → 浏览器实际打开 → 检查正常态与关键状态 → 宽屏/笔记本/移动端抽查 → 修正 → 必要功能测试 → 才标记验证完成。构建成功、组件能渲染、单张新版截图、AI 自己说“好看”都不能替代这一步。

如果有截图、视觉浏览器或可交互预览能力，必须利用它做视觉审查；发现层级、间距、密度、溢出、空状态、模板味问题时直接修到代表页基线一致。没有浏览器能力时明确“视觉未验证”，不能把静态代码检查冒充最终 UI 验收。
