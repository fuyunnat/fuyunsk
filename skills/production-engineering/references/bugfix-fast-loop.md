# Bug 快速修复闭环

无进展修复的停转、证据失效与全部做完再停遵守 `bounded-completion.md`；升级诊断不能重置重复试错计数。

本规则用于用户明确要求“修 Bug / 修复 / 解决报错 / 按钮没反应 / 功能不对 / 这里有问题”等需要真正修改代码的故障任务。目标是尽快形成“复现 → 最小修复 → 针对性验证”的闭环，不把普通 Bug 拖成长期审计或全仓研究，也不靠连续猜测试错碰运气。

## 一、修 Bug 默认是修复任务，不是只读诊断任务

用户明确说“修、解决、改掉、修复”时，在当前项目和既有授权边界内，默认允许为了该 Bug 做必要的普通代码修改；诊断只是修复前的短阶段。不得因为读取了 `diagnosis-feedback-loop.md` 就把整个任务降格成只读。

只有用户明确要求“先分析/只排查/不要改代码”，或触及生产、数据库破坏性操作、支付、权限、密钥、跨项目、主线等需要单独授权的高风险写入时，才保持只读或等待确认。

## 二、先看懂原因再动手（2026-10-13 修订）

旧版“第一次改代码前只允许一个相关源码读取批次加一个针对性复现/验证批次”已废止：它让 AI 没看懂就下手，造成反复改错。现在的要求是**先找到原因，再改一次改对**：

1. **先复现**：能在本地或测试环境让 Bug 出现，就先亲自复现一次，记下复现步骤和看到的现象；已有失败测试、堆栈、浏览器报错或日志可直接作为起点。
2. **读完整条相关路径**：从触发点顺着调用链读到出错点，包括数据从哪来、经过哪些处理、在哪一步变了样；需要多看几层就看几层，但只看与这条路径相关的代码，不扫无关模块。
3. **日志不够就先补日志**：按 `observability-debugging.md` 补在出问题的路径上，复现一次再改。线上报错先分清是哪一层，不在这里重复分层表。
4. **能用一句话说清根因再改**：例如“列表接口把空数组当成 null 返回，前端 `.map` 报错”。说不清就继续定向取证，不靠猜测改代码。会留下后果的改动，按 `delivery-feedback.md` 先说清再改。
5. 不得反复读同一段代码、反复总结而不产生新信息；每一轮查证都要比上一轮更接近原因。

## 三、证据优先，禁止盲目试错

项目不能拿来“猜一个改一个”。每次真正修改前必须能回答三件事：**为什么怀疑这里、改动会影响什么、改完马上怎么验证。**

允许尝试最小修复的前提：

- 症状明确；
- 修改点与失败路径存在直接证据关联；
- 修改范围局部且容易恢复；
- 不触及未授权业务规则、高风险数据或外部副作用；
- 有办法马上验证修复是否有效。

不得为了试错同时改多个互不确定的点，也不得把多个“也许有效”的补丁叠在一起再测试。确需实验性改动时，只允许单变量、可撤回、立即验证；验证失败先恢复该无效改动，再收集新证据，不能留着失败补丁继续猜。

第二次修复只有在第一次失败后取得了**新的、能区分假设的证据**时才允许。没有新证据就继续定向诊断，不做第二次盲改。

修复必须优先改最小必要位置，不顺手重构、清理技术债、换库、改接口或重写邻近逻辑。

## 四、自己确认修好了才算完，失败再扩大一层

修复后**用修复前的同一套复现步骤亲自再试一次**，看到 Bug 不再出现，才算修好；再跑相关测试和直接受影响的功能。不能只凭“代码看起来对了”或“构建通过”就告诉用户修好了，也不能把第一次验证交给用户去试。

确实无法自己复现或验证时（例如只在用户的线上环境出现、需要用户账号），要明确告诉用户“这一步我没法亲自确认”，说明已经做了什么、请用户按哪几步试、出问题时把哪段日志发回来。

如果第一次修复失败：

1. 保留失败证据，撤回或修正无效尝试；
2. 只把排查范围扩大一层，例如从组件到调用方、从服务到仓储、从单接口到相邻状态；
3. 形成新的可证伪假设并取得新证据后，才允许第二次最小修复；
4. 不允许无上限地“再看看”或“再试一个”。连续两次有依据的最小修复均失败，或证据开始互相矛盾时，升级为深入诊断，并向用户简短说明卡点和下一步。

## 五、行为锁和兼容保护不能变成全量盘点

`behavior-preservation.md` 在 Bug 任务中只保护本次受影响路径及其直接相邻行为。不得修一个按钮前先盘点整个系统的 API、权限、状态机和数据库。

修复的目标本身就是把错误行为改成用户已经明确的正确行为；这不算“擅改逻辑”。与该 Bug 无关的业务结果继续锁定。若修复必然改变另一个用户可见结果，而当前要求没有覆盖，按 `novice-clarification.md` 反问一次。

若修复点同时承载旧客户端、旧 API、旧字段、旧数据、旧配置或旧版本调用，必须遵守 `behavior-preservation.md` 的兼容优先规则：**修目标 Bug 不等于授权切断旧路径。** 优先做能同时支持旧新路径的最小修复，并各验证至少一个相关旧路径和新路径；技术上无法兼容时先说明结果差异，不能用直接删除/替换旧路径来快速“修好”。

## 六、Bug 修复的进度要求

不要长时间只输出“正在分析”。开始时一句说明当前症状和第一步即可；拿到关键证据后直接改。每次扩大排查范围都必须有新证据或上一轮失败作为理由。

修 Bug 时只需读本文件、`observability-debugging.md` 和 `quick-core.md` 就能开始；只有触及数据库、权限、支付、部署或多模块时才回到完整规则批量读取。工作清单保持极短：普通 Bug 通常只记一个结果项，必要时再拆“定位/修复/验证”；开始登记一次，最终验证后一次更新即可。只有阻塞、跨会话或任务明显扩大时才中途更新，不能因为维护清单、写报告、建立完整迁移台账而延迟第一处代码修复。

## 七、何时允许深入诊断

以下情况可以进入 `diagnosis-feedback-loop.md` 的完整闭环：

- 无法稳定复现且没有可靠错误证据；
- 偶发并发、性能退化、数据竞争或跨服务问题；
- 两次有依据且有新证据支持的最小修复均失败；
- 故障跨多个边界且真正根因未知；
- 继续试改会触及高风险数据、权限、支付、生产或大范围副作用。

即使进入深入诊断，也必须围绕具体假设收集证据，不进行无目标全仓扫描，不以生产环境作为随意试错场。

行为锁不能变成修复前的全量盘点；只查本次相关入口和受保护行为。
