# Bug 快速修复闭环

本规则用于用户明确要求“修 Bug / 修复 / 解决报错 / 按钮没反应 / 功能不对 / 这里有问题”等需要真正修改代码的故障任务。目标是尽快形成“复现 → 最小修复 → 针对性验证”的闭环，不把普通 Bug 拖成长期审计或全仓研究。

## 一、修 Bug 默认是修复任务，不是只读诊断任务

用户明确说“修、解决、改掉、修复”时，在当前项目和既有授权边界内，默认允许为了该 Bug 做必要的普通代码修改；诊断只是修复前的短阶段。不得因为读取了 `diagnosis-feedback-loop.md` 就把整个任务降格成只读。

只有用户明确要求“先分析/只排查/不要改代码”，或触及生产、数据库破坏性操作、支付、权限、密钥、跨项目、主线等需要单独授权的高风险写入时，才保持只读或等待确认。

## 二、先建立最短证据，不要求先完全理解系统

开始时只做与症状直接相关的最小查证：

1. 读取报错、相关入口、调用链最近一层和必要配置。
2. 能安全复现时复现一次；已有明确失败测试、堆栈、浏览器错误、日志或用户给出的稳定现象可以直接作为失败证据。
3. 找到一个可验证、局部、可恢复的高概率原因后，立即进入最小修复，不继续为了“完全确认所有可能性”扫描全仓。

普通 Bug 在第一次改代码前，原则上只允许一个相关源码读取批次加一个针对性复现/验证批次。只有仍没有可执行假设时才追加第二轮定向证据。不得连续多轮搜索同类文件、重复读同一调用链、反复总结而不产生新的可证伪信息。

## 三、足够证据即可试最小修复

不要求“根因 100% 证明”才允许改代码。满足以下条件即可尝试最小、可恢复的修复：

- 症状明确；
- 修改点与失败路径存在直接证据关联；
- 修改范围局部；
- 不触及未授权业务规则、高风险数据或外部副作用；
- 有办法马上验证修复是否有效。

修复必须优先改最小必要位置，不顺手重构、清理技术债、换库、改接口或重写邻近逻辑。

## 四、修完马上验证，失败再扩大一层

第一次修复后立即运行最小相关验证：失败测试、原复现步骤、相关接口、浏览器路径或模块测试。通过后再做必要的受影响回归；不要先跑全量审计才看第一刀有没有用。

如果第一次修复失败：

1. 保留失败证据，撤回或修正无效尝试；
2. 只把排查范围扩大一层，例如从组件到调用方、从服务到仓储、从单接口到相邻状态；
3. 形成新的可证伪假设后再次最小修复；
4. 不允许无上限地“再看看”。连续两次修复尝试都失败，或证据开始互相矛盾时，才升级为深入诊断，并向用户简短说明卡点和下一步。

## 五、行为锁不能变成修复前的全量盘点

`behavior-preservation.md` 在 Bug 任务中只保护本次受影响路径及其直接相邻行为。不得修一个按钮前先盘点整个系统的 API、权限、状态机和数据库。

修复的目标本身就是把错误行为改成用户已经明确的正确行为；这不算“擅改逻辑”。与该 Bug 无关的业务结果继续锁定。若修复必然改变另一个用户可见结果，而当前要求没有覆盖，按 `novice-clarification.md` 反问一次。

## 六、Bug 修复的进度要求

不要长时间只输出“正在分析”。开始时一句说明当前症状和第一步即可；拿到关键证据后直接改。每次扩大排查范围都必须有新证据或上一轮失败作为理由。

工作清单保持极短：普通 Bug 只需要“复现/定位、修复、验证”三项或更少。不得因为维护清单、写报告、建立完整迁移台账而延迟第一处代码修复。

## 七、何时允许深入诊断

以下情况可以进入 `diagnosis-feedback-loop.md` 的完整闭环：

- 无法稳定复现且没有可靠错误证据；
- 偶发并发、性能退化、数据竞争或跨服务问题；
- 两次有依据的最小修复均失败；
- 故障跨多个边界且真正根因未知；
- 继续试改会触及高风险数据、权限、支付、生产或大范围副作用。

即使进入深入诊断，也必须围绕具体假设收集证据，不进行无目标全仓扫描。
