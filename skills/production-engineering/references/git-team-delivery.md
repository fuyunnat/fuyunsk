# 团队 Git 交付专项

本专项补充多人协作仓库里的提交、推送、评审、合并与回滚纪律。它只在 Git 交付阶段按需加载，不替代原文、仓库约定、分支保护或用户当前指令，也不会因为被读取就扩大远端写入权限。

## 一、先固定真实交付基线

开始远端交付前先确认远端、稳定主线、当前分支与最新主线提交。稳定主线必须来自仓库默认分支、项目文档、分支保护或团队约定，不能只凭经验猜 `main` 或 `master`。

- 创建任务分支或准备 PR 前，先获取远端最新引用并记录实际基线 SHA。
- 当前分支含有其他未合并任务时，先识别叠加范围，不能把别人的工作带进当前交付。
- 工作区或目标提交里存在用户已有改动时，不覆盖、不回滚、不格式化，也不把它们混入本次提交。
- 远端主线在交付过程中发生变化时，先重新读取和比较，不盲目 `pull`、`merge`、`rebase` 或强行更新。

## 二、按逻辑单元提交

提交应当是可审查、可验证、可回滚的逻辑单元，而不是按文件数、修改行数或时间机械切分。

- 同一功能强相关的实现、测试和必要文档可以放进同一个提交。
- 多个互不相关的功能、修复、配置变化应拆开，不能最后塞进一个大提交。
- 小修、测试修正和同一功能的文案微调不要制造无意义的微型提交。
- 提交前检查精准 diff、暂存文件、敏感信息、生成物、日志、缓存、本地配置和计划外格式化。
- 优先遵循仓库现有提交规范；没有明确规范时可使用 Conventional Commits，具体结果默认用中文写清楚。
- 没有实际验证证据时，不把提交描述成“已完成”或“已通过”。

## 三、推送不等于合并

远端保存、发起评审和进入正式主线是三层不同状态，必须分别报告。

- 普通协作交付默认推送当前任务分支；“提交到仓库”“同步 GitHub”“上传仓库”本身不等于允许合并主线。
- 推送后说明实际远端分支和 commit，并说明该提交是否已经进入稳定主线。
- 禁止使用强推、删远端分支、改写共享历史来让交付“看起来干净”。
- 推送失败时保留本地恢复点并报告真实错误，不伪造远端成功。

## 四、直接进入主线只接受明确授权

只有用户或仓库流程明确要求“提交到 main / master”“合并到主库”“正式用这个版本”时，才进入主线写入或合并流程；该授权只覆盖当前已说明的改动，不自动授权后续主线写入。

执行前必须再次确认：

1. 远端主线 HEAD 与刚刚验证的基线一致，或已经重新审查它的新变化。
2. 即将进入主线的 diff 只包含当前任务所需文件，没有用户已有改动、未知提交或无关格式化。
3. 与风险匹配的验证已经执行；存在 CI 时检查真实 CI 状态，不能拿旧结果代替。
4. 回滚目标清楚，能够通过新的 revert/修复提交恢复。
5. 更新必须是正常快进或仓库允许的合并方式；禁止用 force 绕过并发变化、分支保护或评审。

如果主线在最后确认后又移动，停止本次直接更新，重新比较新的 HEAD；不能为了完成任务机械覆盖团队的新提交。

## 五、PR 保持一个任务一条评审线

需要 PR 时，以已确认的稳定主线为 base、当前任务分支为 head；同一任务后续补修更新同一个 PR。

创建或更新 PR 前检查 `base...head`：

- 文件列表和提交都属于当前任务。
- 必要测试、构建、静态检查和手工验收已按实际条件执行。
- CI 状态使用当前 head 的真实结果；没有 CI 就明确写“未发现自动化 CI”。
- PR 标题和描述与实际 diff 一致，不夸大验证范围。
- 描述至少说明改了什么、为什么改、怎么验证、剩余风险和如何回滚。

PR 创建成功不等于已经合并。未经明确授权，不自动点击 Merge，也不自动删除远端分支。

## 六、团队并发与冲突处理

多人仓库的核心目标是保留其他人的新工作，而不是让本地历史保持漂亮。

- 发现主线、任务分支或 PR head 被别人更新时，先获取实际差异和提交来源，再决定是否需要整合。
- 只有理解冲突两边的业务意图后才解决冲突；不能只选“ours”或“theirs”让命令通过。
- 无关独立变化可以保留并继续；会改变当前任务结果、测试基线或授权边界的冲突必须显式处理。
- 已经共享的历史默认通过新提交修正，不重写旧提交。
- 不能因为 CI 绿色就忽略 base 已变化后的行为回归。

## 七、回滚使用新的可审计改动

共享仓库回滚默认通过 `revert` 或新的修复提交完成，不通过强推把历史改没。

- 整个坏提交都应撤销时，优先 revert 精确提交或 PR。
- 只有单个文件或代码段需要恢复时，先看该文件后续历史，避免顺手抹掉后来正确修改。
- merge commit、重命名、生成文件或跨文件强耦合改动不能机械反向应用；上下文不清时停止自动回滚。
- 回滚后重新执行与影响范围匹配的验证，并把恢复点和仍保留的变化说明清楚。

## 八、每个 Git 检查点都要说清状态

每次提交、推送、PR、主线合并或回滚后，用中文简短报告：

- 实际做了什么、为什么做。
- 涉及哪些文件或功能。
- 执行了哪些验证，哪些没有条件执行。
- commit、分支或 PR 的真实位置。
- **是否已经进入稳定主线**，不要只给 hash 让用户自己猜。
- 出问题时如何恢复，以及是否仍有待办或阻塞。

“已提交”“已推送”“PR 已创建”“已进入 main”“已部署”必须对应不同的真实状态，禁止混写或提前宣布。
