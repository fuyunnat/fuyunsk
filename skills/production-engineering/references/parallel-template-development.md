# 前端模板并行二开与防遗漏

用于“基于现有前端再做一套新模板、旧模板不要动、功能一个不能漏”这类任务。它不是普通 UI 改版，也不是整项目重写；目标是在**同一套业务与后端能力上并行开发新的前端模板**，让旧模板继续可用，直到用户明确决定切换或下线。

典型触发语：
- “重新二开一套前端模板，旧的别动。”
- “再做一套新版商城前台，不要覆盖现在这个。”
- “基于现有模板重新设计，但功能一个不能漏。”
- “V1 保留，另外做 V2 给我测试。”

普通页面小改、只改一个组件、只换颜色或只修 Bug 不加载本文件。

## 开工先定本批阶段：先视觉，后业务接入

默认按 `frontend-stack.md` 分阶段。视觉阶段先完成本批外观、布局、主题、展示组件、导航和本地交互，在真实浏览器预览、检查桌面/手机与关键视觉状态；不能边写视觉边大规模接真实接口或业务。视觉阶段不以全站功能盘点、逐字段/API审计或完整CRUD验收为前置；仅核对当前页面结构和必要状态，后续业务接入前再补齐功能分母。

有用户认可且可安全运行的完整模板时，先原样运行，保留其布局、主题和共享组件。没有完整模板时先做代表页。按 `frontend-delivery-loop.md` 提供可打开的预览地址，告诉用户可以从哪里开始点。先在桌面和手机浏览器实际点击导航、按钮等关键控件，有表单就填写测试值并触发校验。示例数据、模拟状态和未接功能的按钮要明确标注，视觉完成不等于业务完成，台账业务状态不能标成 `verified`。

用户安排进入后续业务接入阶段后，按下文逐页验收。用户明确功能优先或先接接口时遵从当前顺序；已有页面小改继续保持已接业务，不要求解绑或改成模拟。阶段授权和停止点按用户要求执行，已明确连续完成则不逐项重问。

## 一、核心原则：旧模板是只读基线，新模板独立并行

默认把现有模板视为受保护来源，不在其目录中“边改边迁”。开始实现前先确定：

- `PROJECT_ROOT`：当前真实项目根目录。
- `SOURCE_TEMPLATE_ROOT`：旧模板根目录或明确的旧模板入口集合。
- `TARGET_TEMPLATE_ROOT`：新模板独立目录/入口，不能与旧模板目录重叠。
- 旧模板基线：Git 提交 SHA；非 Git 项目使用可恢复备份和内容哈希。
- 新模板的访问方式：独立路由、主题选择器、独立构建入口或项目已有等价机制。

默认禁止写入 `SOURCE_TEMPLATE_ROOT`。如果新模板确实需要修共享后端、共享 API 客户端、公共类型或公共业务模块，必须先证明它不是“为了方便直接改旧模板”，并验证旧模板仍正常。

不能用以下方式完成任务：
- 复制新模板后删除旧模板；
- 直接在旧模板目录大改，再把它重命名成 V2；
- 让新旧模板共用一个会互相覆盖的入口、静态资源目录或构建输出；
- 为了复用组件而把旧模板改造成新模板依赖，导致旧模板行为改变；
- 用户未授权时切换默认生产模板、删除旧路由或停止旧模板构建。

## 二、先盘点“功能分母”，再开始批量开发

防遗漏的关键不是记住页面名，而是建立固定的功能分母。以下完整盘点用于业务接入及完整交付阶段；视觉阶段不强制先完成全站盘点。进入已授权的业务接入前，对旧模板做交叉盘点，至少覆盖：

1. **页面与路由**：首页、列表、详情、搜索、登录注册、个人中心、订单、支付结果、消息、帮助、活动、错误页等真实入口。
2. **导航入口**：顶部/底部菜单、侧栏、Tab、快捷入口、深链、返回路径、外部跳转。
3. **交互**：按钮、弹窗、抽屉、菜单、筛选、排序、分页、轮播、收藏、分享、复制、上传、下载、确认与撤销。
4. **状态**：正常、loading、empty、error、disabled、只读、未登录、无权限、库存不足、请求超时、重复提交等。
5. **表单与校验**：字段、默认值、必填、格式、错误提示、提交 payload、二次确认、防重。
6. **数据与 API**：请求地址、参数、返回字段、缓存、本地状态、分页、排序、错误码、刷新与重试。
7. **权限与用户差异**：游客/登录用户、角色、地区、等级、会员、灰度开关等可见性和操作差异。
8. **业务副作用**：下单、支付、退款、优惠券、积分、消息、上传、导出、回调等不能只看 UI。
9. **响应式与设备**：桌面、手机、必要的平板/窄屏，以及移动端专属交互。
10. **多语言与本地化**：语言切换、文案、货币、时间、数字、图片、动态内容和 fallback。
11. **公开页面 SEO**：title、description、canonical、robots、sitemap、hreflang、Schema、公开 URL 与内链。
12. **视觉与资源**：Logo、图标、字体、图片、主题变量、暗色模式、动画、骨架和品牌资源。

不能只从目录、README 或路由表推断完整功能。至少用两类证据交叉确认，例如：路由/菜单 + 页面源码、页面源码 + API 调用、源码 + 现有测试、源码 + 允许访问的运行页面。

找不到证据的条目标为“未知”，未知不能自动当“不需要”。

## 三、固定台账：分母只能增加，不能缩水

业务接入前创建或沿用项目已有的机器可读台账，例如 `docs/template-inventory.json`。视觉阶段仅复用本批页面清单，不为展示样子强建全站业务台账。格式可参考 `templates/template-inventory.example.json`。

每个旧能力必须有稳定 `id`，至少记录：

- `name`：功能名称；
- `sourceLocations`：旧模板真实入口/源码位置；
- `behavior`：用户可观察结果；
- `states`：需要覆盖的关键状态；
- `dependencies`：依赖 API/权限/共享模块；
- `requiredChecks`：必须真实验证的用例；
- `targetLocations`：新模板对应位置；
- `status`：`pending / implementing / implemented / verified / approved-omit`；
- `evidence`：验证证据；
- `approvalSource`：只有 `approved-omit` 时必填，必须对应用户明确授权。

**固定分母规则：**

- 初次盘点后的功能数量是当前分母。
- 开发途中发现遗漏入口，只能追加新条目，不能删除旧条目来维持“100%”。
- 追加必做须有原目标关联和来源证据，或用户明确新增要求，按 `bounded-completion.md` 固定范围；无关功能、风格建议或上游新变化不进入本轮分母。
- `implemented` 不等于 `verified`。
- 未找到对应新实现的旧功能不能标完成。
- 只有用户明确说“不需要这个功能”才能标 `approved-omit`。
- “旧模板本来就很少用”“看起来可以不要”“新版设计不适合”都不构成省略授权。

完成公式必须满足：

`旧模板已盘点总能力 = verified + approved-omit`

并且 `pending / implementing / implemented / unknown = 0`。

这是**整体完成**条件，不是每项结项的等待条件。每个能力自身 `requiredChecks` 全部通过就独立标 `verified`，不等其他模块或外部服务。未全过的，在原项旁保存各检查的通过/失败/未测及证据；缺条件单列检查 ID、已测/未测、所缺条件与恢复第一步，整体保持未完成。沿用现有状态和台账，不改枚举、不把阻塞当省略；共享依赖失败则保留受影响项待验证。

## 四、新模板必须是新实现，不是覆盖式换皮

新模板可以重新设计视觉、布局、组件和前端技术实现，但默认继续遵守 `behavior-preservation.md`：业务结果、接口语义、权限、数据、副作用和关键流程不因“换模板”而改变。

先完成并交付视觉阶段。进入已授权的业务接入阶段后，逐页或按一个跨页业务闭环推进，每个闭环接好就测，例如：

`公共壳层 → 登录/鉴权 → 首页 → 列表/搜索 → 详情 → 核心业务流程 → 个人中心 → 辅助页面 → 异常状态`

每完成一个闭环就：

1. 对照旧模板该功能的真实行为；
2. 接现有接口、权限、校验与业务操作，沿用已验收的新模板布局和组件；
3. 在授权的测试环境里，使用真实接口与代表性测试数据，在桌面和手机浏览器复测预览时的关键操作。检查成功、失败、权限和适用的加载、空数据、长内容状态。核对布局、首次打开、切换页面和提交的响应，发现明显卡顿时记录可比较的耗时；
4. 确认旧模板对应路径仍能正常工作；
5. 台账从 `implemented` 更新到 `verified`。

分别记录每页演示和接入后的结果，再进入下一页。缺真实接口、测试账号或数据等条件时，将受影响项标为未验证，写清缺什么，其他独立页面可以继续。用示例数据通过的项目只记为演示通过。

**业务接入阶段用户反馈功能明显不全、对不上旧版、或新入口打不开/空白时**：先暂停继续铺新页面或只做视觉精修，回到功能分母与旧模板对照；未 `verified` 的项不要标完成。首页或关键路由空白、白屏必须处理；业务交付承诺下只有壳没有业务属于未完成。视觉阶段已标注的未接功能不因此自动升级为接入任务，仍要补齐内页展示组件与可操作的本地交互，不能只画外壳就称所有页面外观完成。

## 五、共享代码边界：可以复用，但不能把旧模板绑死

新旧模板可以安全复用稳定的公共业务层、API SDK、类型、i18n 基础设施和纯工具函数，但要区分：

- **业务共享层**：确实属于两个模板共同依赖，可以复用；修改时必须回归旧模板。
- **视觉/页面实现**：默认各自独立，避免 V2 的样式和组件改动改变 V1。
- **模板专属状态/路由**：不要为了少写代码塞进全局共享层。

如果必须调整公共层才能支持 V2，先记录受影响的 V1 功能，并把 V1 回归加入 `requiredChecks`。共享层变更不能绕过旧模板保护。

## 六、视觉重做与功能保持要分开验收

用户允许“重新设计模板”时，只代表视觉和已确认的交互呈现可以变化，不代表功能可以少。

每个代表性页面至少分别验证：

- **功能对照**：旧入口是否都有新入口，按钮/流程/API/权限/状态是否等价；
- **视觉质量**：新模板自己的布局、响应式、可访问性、loading/empty/error 等是否达标。

旧模板截图不是新模板视觉目标，但旧模板的功能和状态仍然是行为基线。

先完成一个代表性页面或业务闭环并验证设计语言，再批量推广，避免整站做完才发现组件方向不对。

## 七、多语言、SEO 和商城专项不能在换模板时丢失

如果旧模板或项目已有多语言，新模板必须继续使用项目 i18n/fallback 机制，不能把用户可见文案重新硬编码成单语言。

如果是公开可索引模板，追加 `seo-engineering.md` 的 SEO Guard；明显改变路由、模板、SSR/SSG、head、商品/分类模板时做 SEO Drift。不能因为 V2 页面能打开就把 canonical、Schema、hreflang、sitemap 或旧公开 URL 丢掉。

商城模板额外核对：
- 商品/分类/品牌/搜索/购物车/结算/订单/优惠/库存/变体；
- 价格、币种、促销、税费、运费；
- 登录前后、售罄/下架/错误/支付失败等状态；
- Product/Offer/Breadcrumb 等结构化数据与真实业务数据一致。

## 八、真实验证：新模板通过，还要证明旧模板没坏

构建成功、类型通过、页面 200、单张截图都不能作为完成证据。

按实际项目能力使用浏览器、端到端测试、接口测试或代表性真实交互。至少证明：

- 新模板的每个必需功能有真实验证证据；
- 旧模板受影响的共享能力仍可用；
- 新旧模板可在同一代码版本并行启动/访问；
- 切换机制如果存在，不会误把测试模板覆盖生产模板；
- 桌面/移动和关键 loading/empty/error 状态已覆盖；
- 公开模板适用的 SEO 和多语言保护未回归。

无法执行的项必须保持“未验证”，不能因为时间长就改成通过。

## 九、最终查漏门禁

交付前做一次逆向查漏，不从 V2 看“做了什么”，而从 V1 台账逐项问“这个在 V2 哪里”：

- 每个旧页面是否有对应结果；
- 每个旧路由/入口是否有迁移或明确保留策略；
- 每个按钮/弹窗/状态/API 是否有对应；
- 权限、失败路径、空状态、移动端是否遗漏；
- 多语言、SEO、配置、共享资源是否遗漏；
- 新发现是否已经追加到分母；
- `implemented` 是否全部有真实证据升级为 `verified`。

可以使用 `scripts/template-inventory-check.js` 对台账做结构和证据完整性检查；它不会自动发现业务遗漏，也不会替代浏览器/业务测试。通过脚本只说明“已登记分母没有未结项”，不代表模型凭空证明了项目绝无遗漏。

## 十、运行交付与停止点

用户要求“启动给我测试”时：

1. 启动旧模板和新模板可区分的访问入口；
2. 给出新模板 URL/路由和必要测试路径；
3. 报告本次已验证功能数量、`approved-omit` 数量、未验证/阻塞数量；
4. 列出本次影响的页面/共享模块；
5. 给出恢复点和当前工作分支；
6. **停止等待用户测试。**

除非用户随后明确授权，不自动把新模板设成默认模板，不删除旧模板，不合并工作分支到 `main/master`，不做生产切换。

## 十一、和其他模式的关系

- 只改现有模板一个页面：普通前端模式，不加载本文件。
- 在同一项目新增一套并行 V2 模板：本文件。
- 整个项目换语言/全量架构重写：`project-migration.md`。
- 二开项目吸收上游模板修复：`upstream-sync.md`。
- 公开模板 SEO：按需追加 `seo-engineering.md`。

本模式可以借鉴整项目迁移的“固定分母、逐项验收、发现遗漏只能追加”思想，但不会因为新增一套前端模板就自动升级成整项目迁移。
